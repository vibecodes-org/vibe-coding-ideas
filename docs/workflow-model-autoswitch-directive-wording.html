Auto-switch to the backup model — final wording

This feature has no screens. Its user experience is four pieces of text: the notice at the top of a switched claim, the sentence that teaches the orchestrator how to report "the model itself was down", the note left in the step thread when a step is rescued, and the note when it is not. Everything in a Final box is verbatim; <angle> placeholders are model names filled in at run time.

Golden rule (AC-6): when there is no unavailability marker for this board today, none of the text below appears anywhere. The claim directive is byte-for-byte what ships today. The only place that always carries the new text is the fail_step tool description (item 2), which is not part of the directive.

1 · The switch notice (top of a switched claim)

Prepended immediately before MANDATORY MODEL:, joined by a single space, only when a switch is active. Every word here is read on every switched claim, so it is kept to three sentences: what died, what to use, when it ends.

Final · switch notice≈ 330 chars · Claude and Codex share it
MODEL SWITCH: "<dead>" was reported unavailable on this board earlier today (credits, overload, rate limit, or not on this plan), so this step is directed at the configured backup "<backup>" instead. This is deliberate and current; follow it. The switch lapses at midnight UTC, when "<dead>" is tried again automatically. MANDATORY MODEL: …
  • Requirements §8: "on this account" → "on this board" (the marker is per board).
  • Contains the literal word unavailable (AC-3 test), names both models, states the lapse and that the primary is retried.
  • "midnight UTC" replaces PR #255's "end of the day" — an orchestrator can act on a clock time; "end of the day" is ambiguous across timezones.
  • "deliberate and current; follow it" pre-empts the orchestrator "correcting" the model back to the tier's usual choice from CLAUDE.md or its own memory.
  • Prefix is MODEL SWITCH:, not AUTOMATIC MODEL SWITCH: — shorter, and it sits next to MANDATORY MODEL: so the two capitalised labels read as a pair.

Confirmed against modelTierClause() in mcp-server/src/tools/workflows.ts: both variants open with "MANDATORY MODEL:" and take the resolved/fallback pair by value, so the notice reads correctly in front of either with no other change. Codex's execution object carries the swapped values separately (Requirements §4).

One wrinkle for Implementation, not for the wording. Because the swap makes the old primary the new fallback, the unchanged directive sentence now says "If "opus" is unavailable … use model: "fable"" — i.e. fall back onto the model the notice just called dead. This is what Requirements §4 specifies (a last-resort second try is better than nothing) and the notice's "deliberate and current" makes the ordering clear, so no extra sentence is added. Implementation should be aware and not "fix" it by adding words to the directive.

2 · Teaching the signal (fail_step only)

Requirements §8.2 asked where the "pass model_unavailable: true" instruction lives. Confirmed: only in the fail_step tool description and its parameter description — never in the directive. Reason: the directive must be byte-identical with no marker (AC-6), and the moment an orchestrator needs this sentence is the moment it is deciding how to fail, which is when it reads the fail_step schema. Schema lives in mcp-server/src/register-tools.ts (tool description) and failStepSchema in mcp-server/src/tools/workflows.ts (parameter).

Final · sentence appended to the fail_step tool descriptionafter the existing "Pass `model_used` = …" sentence
…(self-reported — VibeCodes records it but does not verify it). If the step failed because the MODEL ITSELF could not be reached (out of credits, overloaded, rate-limited, not on this plan) — not an ordinary failure like a bug or a failing test — pass `model_unavailable: true`: the step returns to pending and is re-run on the tier's configured backup model, and later steps on this board are steered away from the unavailable model until midnight UTC. A step is rescued this way at most once; a second such failure leaves it failed.
Final · `model_unavailable` parameter descriptionz.boolean().optional().describe(…)
Set true ONLY when the step failed because the directed model could not be reached — out of credits, overloaded, rate-limited, or not on this plan. Never for ordinary failures (a bug, a bad prompt, a failing test). When true, the step returns to pending and is automatically re-run on the tier's configured backup model, and later steps on this board are steered away from the unavailable model until midnight UTC. At most once per step: a second model-unavailable failure leaves the step failed. Ignored for steps with no model tier and for awaiting_approval rejections.
  • Both texts lead with the exclusion ("not an ordinary failure") because the real risk is over-use: an orchestrator tagging a test failure as "model unavailable" would silently re-run it on a different model.
  • Tightened from PR #255's drafts: "steered away" replaces "directed away" (matches the notice's "directed at"), "midnight UTC" replaces "end of the day", and the at-most-once rule is stated in both places.
  • The final sentence of the parameter text tells the caller the two cases where the flag does nothing (Requirements §4), so it is never a surprise.

3 · The step-thread comments (read by people)

These are the only text a human sees. Nick opens the step thread after losing a step; the comment must tell him what happened, what will happen next, and whether he needs to do anything — without knowing what a marker, a tier or a claim is. Posted as a plain step comment (same mechanism as the cascade-reset note). Markdown bold for the two model names so they can be picked out at a glance.

Final · rescue comment (first model-unavailable failure)
**Switched to the backup model.** This step couldn't run because **<dead>** was unavailable (for example out of credits or overloaded). It has been put back in the queue and will be re-run on the backup, **<backup>**. Other steps on this board will use **<backup>** too until midnight UTC, when **<dead>** is tried again. This automatic retry happens once per step — if it fails on **<backup>** as well it stays failed and needs a person to look.
Final · second failure comment (rescue refused)posted alongside the normal failure comment
**No automatic retry this time.** This step was already re-run once on a backup model and has now failed again because **<model>** was unavailable. It has been left failed. Check your model credits or plan, then reset or re-run the step.

<model> here is the model that failed on the second attempt (normally the backup). The free signal (a completed step that self-reports running on the backup) posts no comment — the step's own output already states the substitution, and a second note would be noise.

4 · Flow

1
Step dies — the model itself could not be reached
Credits out, overloaded, rate-limited, or not on the plan. Not a bug, not a failing test.
↓
2
Orchestrator calls fail_step with model_unavailable: true
It learned to do this from the tool description (item 2). Server writes the marker: which model died + when, for this board.
↓
3a
First time for this step → back to pending
Rescue comment posted (item 3). Run stays running.
3b
Already rescued once → stays failed
"No automatic retry" comment posted. Marker still refreshed.
↓
4
Next claim of that step is directed at the backup
Switch notice (item 1) prepended before MANDATORY MODEL; the backup is the directed model, the old primary becomes the fallback.
↓
5
Every later claim on this board today is redirected the same way
Only tiers that resolve to the dead model. Other tiers, other boards, and Auto steps see today's directive unchanged.
↓
6
Midnight UTC — marker lapses, primary tried again
No notice, no comment. If it is still down, the next failure repeats from step 1 (once per step).
No marker = byte-for-byte unchanged (AC-6). A board with no same-day marker never sees the notice, never sees the comments, and gets exactly today's MANDATORY MODEL text. A marker for a different model, a lookup error (AC-7), or a reciprocal chain that would switch onto the dead model all resolve to today's directive too.

Free signal (no wording)

When a step completes and reports model_used = the tier's backup, the server writes the same marker silently. Nothing new is said to anyone; later claims simply start carrying the switch notice.
