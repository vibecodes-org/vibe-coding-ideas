Admin-configurable platform model-tier defaults

Stop hard-coding tier→model defaults in three lockstep places. Give super-admins a UI to set them (frontier→Opus now, future family swaps with no deploy), and make every user-facing “Default (Fable)” label derive from the live setting.

Building on the Requirements step. Requirements defined the problem (defaults hard-coded across MODEL_TIER_TO_SUBAGENT_MODEL + MODEL_TIER_FALLBACK at workflows.ts:63-64 and the display mirror MODEL_TIER_PLATFORM_DEFAULT_MODEL at constants.ts:41), the 10 ACs, the greenfield platform_settings store, super-admin-only R/W, three claim-time read sites, and three open questions. This step designs what Nick sees and how the read slots in, and proposes answers to OQ1–OQ3 for the Design-Review gate. It does not re-derive the requirements.

Discrepancy flagged for the gate. Requirements says the edit flow is “3 tiers (default + fallback each).” The code’s MODEL_TIER_FALLBACK is keyed by resolved model alias (fable→opus, opus→fable, sonnet→opus, haiku→sonnet), not by tier (workflows.ts:64). A tier has one default; the fallback belongs to whatever model that default resolves to, shared across tiers. So the UI can’t honestly show “fallback per tier.” This design splits the surface into Panel A — Tier defaults (3 rows) and Panel B — Fallback chain (model→model pairs), which matches the code and still satisfies AC “fallback map editable.” Confirm this split at the gate.

2 · Novel-family guard (typo defence)

Free text is the whole point (a new family needs no schema change) — but a typo (opsu, sonnett) silently sends a bad Task-tool model into every claim. Guard: known aliases are one-click; a novel value requires an explicit confirm before Save unlocks. This is the Hick’s-Law split — the 99% common case (pick a known model) stays one tap; the rare, dangerous case (invent a family) gets friction.

Architectural note for the Design-Review + Implementation steps. Those three consumers are client components calling synchronous, pure functions in constants.ts. The live default is server/DB state. So the mirror can’t simply stay a sync constant. Recommended shape: the platform defaults become a small object passed down from the server (the same way map/isSuperAdmin are already SSR’d as props), and the pure helpers (modelTierGloss, tierDefaultsToCopy) take the defaults object as an argument instead of importing the constant. Keep the current constant as the seed / typed fallback so nothing crashes if the fetch is absent. This preserves testability (the helpers stay pure) while removing the “keep in sync” trap.

4 · Data & flow — where the read slots in

All three claim-time sites already do the identical pattern for the per-user override (workflows.ts:1015, 1135, 1313): a scoped .select("model_tier_map").eq(id).maybeSingle() guarded by if (model_tier). The platform-default read slots in right beside it, in the shared resolver so stdio + remote MCP behave identically.

1
Claim — claim_next_step fires. If step.model_tier is null (Auto), nothing changes: no read, no clause (FR-12 preserved).
2
Read platform defaults — a new getPlatformModelDefaults(ctx.supabase) helper reads the platform_settings row. Missing row → return the seed constants. Per-request, no cache (see OQ2).
3
Read user override — unchanged: existing model_tier_map lookup, override precedence preserved.
4
Resolve — resolveModelTier(tier, userMap, platformDefaults) gains a third arg. Precedence unchanged: valid user override → else platform default (now from DB) → fallback from the (now DB-backed) fallback chain. Invalid stored value → log + fall through, never throw.
5
Emit — modelTierClause() builds the same MANDATORY MODEL directive, now with the live model. The orchestrator spawns the subagent on it.

One helper, two call environments: mcp-server/src/index.ts (service-role) and route.ts (per-user RLS). The platform_settings row must be readable by both (public/authenticated select) and writable only by super-admins (RLS write policy on is_super_admin) — so a bot in RLS mode can still resolve defaults at claim time.

5 · Open-question proposals

OQ1Recommend: relax to string

model_used z.enum at workflows.ts:1061 & :1236. Relax to z.string().max(40) + soft-validate against the known set, log unknowns, never reject. Rationale: the enum ["fable","opus","sonnet","haiku",…] makes “new family, no schema change” a lie — the moment a novel default ships, the orchestrator can’t honestly report model_used. Soft-validate keeps telemetry clean without blocking. Matches the same tolerance resolveModelTier already shows unknown values.

OQ2Recommend: per-request read, no cache

Cache TTL / staleness bound. Read the row per claim, no cache. Rationale: the per-user model_tier_map read already runs per claim beside it — adding one more indexed single-row read on the same low-volume path costs nothing measurable, and correctness beats staleness (a super-admin flipping frontier→Opus must hit the very next claim per AC). No cache = no invalidation code, no “why is it still Fable” support tickets. Revisit only if claim volume ever makes the read hot.

OQ3Recommend: single jsonb row

Storage shape. platform_settings(key text primary key, value jsonb not null, updated_by uuid, updated_at timestamptz); this feature is one row, key = 'model_tier_defaults', value { defaults: {frontier,standard,cheap}, fallback: {opus,fable,sonnet,haiku} }. Rationale: jsonb absorbs free-text families and a new tier/model with zero migrations (the whole point) — matches the model_tier_map / notification-preferences jsonb precedent already in the schema. updated_by/updated_at give the audit line for free. Typed columns would need a migration per new family, defeating the feature.

7 · Open questions for the Design-Review gate

  • Panel A/B split — confirm the fallback chain is edited as model→model pairs (Panel B), not “per tier,” since the code keys fallback by resolved model. This corrects the Requirements phrasing.
  • Sync helpers → props — accept that modelTierGloss / tierDefaultsToCopy take a defaults argument and the three client consumers receive SSR’d defaults, keeping the constant as typed seed/fallback.
  • OQ1 string relax — sign-off to widen model_used to string + soft-validate (touches telemetry, worth an explicit yes).
  • Fallback editing scope — is Panel B in the MVP, or ship Panel A (tier defaults) first and defer the fallback editor? AC lists “fallback map editable”; flag if we want to phase it.
  • Audit depth — is the single “last changed by” line enough, or do we want a full change log? (jsonb + updated_by covers the line; a log needs a second table.)
