Claude sessions tidy up their memory sooner: a new 150k choice

The only thing you'll see is a 150k button at the start of the Claude "Memory limit" row, on your Settings screen and on the Admin page, taking the place of the unused 500k button so the row keeps six buttons. Then the site's choice moves from 300k to 150k, so new and resumed Claude sessions summarise their conversation at about 150,000 tokens instead of about 270,000. Everything else on these screens stays as it is. The buttons are clickable so you can read the help lines.

The new button is underlined in blue in this mock only.

1. Settings → Model Tiers → Terminal sessions

You haven't picked your own memory limit, so you follow the site's choice. After the change the Default button reads "site: 150k". The Codex row underneath already has a 150k button and doesn't change.

3. What changes for the helpers that do each step

The memory limit is set once for the whole Claude session, and the helpers that do each workflow step live inside that session. Their own limit (400,000) can only make them tidy up sooner, never later. So at 150k, a step helper that grows past about 150,000 tokens will also summarise itself partway through its step.

How often, measured on this Mac over the last 7 days: about 1 in 4 step helpers grew past 150,000 (186 of 782). About 1 in 13 grew past 200,000 (58). None went past 300,000, and only 10 helpers summarised themselves all week. A summary keeps the helper going, but it can drop detail it was holding, which is the "lose its place mid-step" risk the card asks us to watch.

5. Your decisions

  1. Which size for the site setting?
    • 150k, as you approved on the earlier card. The main window re-reads the least, but about 1 in 4 step helpers would also summarise mid-step.
    • 200k, already a button today, so it could be switched on in Admin now with no build. A smaller saving on the main window, and about 1 in 13 step helpers affected.
    Recommended: 150k as approved, with a one-week check that also counts step helpers that summarised mid-step, and drop to 200k if any step loses its place. Either way it's one click to undo.
  2. Swap 150k in for 500k, or add it as a seventh button? Nobody uses 500k (no user has picked their own size, and the site uses 300k). With seven buttons, the Admin page's first button ("Not set / Claude's own") no longer fits on a phone and its second line gets cut off (measured in this mock at phone width: it needs about 63 pixels and gets 57). With six it fits exactly as it does today. Recommended: swap, so the row keeps six buttons like the Starting effort row above it. Anyone who later wants 500k can still type /autocompact in the terminal.

  3. Who flips the site setting after the release? Recommended: you, on the Admin page (one click and Save), or the test step does it in your browser with your OK. It records who changed it and when, and undoing it is the same click. The other way, a database change shipped with the release, is harder to undo and needs its own approval.
