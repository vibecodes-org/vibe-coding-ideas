Unarchive Tasks

UX design for the board's "Allow the unarchiving of tasks" card. Builds on the Product Owner requirements; grounded in the live components: src/components/board/task-card-menu.tsx, board-task-card.tsx, board-toolbar.tsx, task-detail-dialog.tsx, board-context.tsx

Reviewed and approved as-is by Product Owner — see §6

1What the code does today

  • Card menu (task-card-menu.tsx): ⋯ trigger → Move to top / Move to bottom / (Launch Claude Code) / Convert to conversation / Archive / Delete. Both Convert and Archive are gated behind !task.archived, so an archived card's menu degrades to Move ×2 + Launch + Delete — the requirements' "almost empty menu". Archive uses lucide's Archive icon and runs the optimistic recipe: ops.archiveTask() rollback fn → ops.trustRemoval() → updateBoardTask(…, { archived: true }) → logTaskActivity("archived"), with rollback + toast.error on failure.
  • Archived card look (board-task-card.tsx): whole card gets opacity-50 (line 486) plus a small inline Archive-icon + "Archived" text in the metadata row (line 559). Drag is disabled (disabled: !!isArchived) and the drag handle is hidden.
  • Toolbar toggle (board-toolbar.tsx:245): "Show/Hide archived (n)" button, rendered only when archivedCount > 0. Unchanged by this design.
  • Detail dialog (task-detail-dialog.tsx:932): existing toggle already uses ArchiveRestore + "Unarchive" and logs the "unarchived" activity type. Unchanged — and it fixes our icon/label vocabulary.
  • Board context (board-context.tsx): has archiveTask(taskId, columnId) returning a rollback fn; there is no unarchive op yet — the engineer adds a mirror-image unarchiveTask.

2Interaction flow

Precondition worth stating: the card menu is only reachable when the archived card is visible, i.e. "Show archived" is already on. So there is no "where did it go?" moment — the card restores in place, in the same column and position, and simply sheds its archived styling. That visible restyle is the success feedback; no success toast (Archive doesn't toast either — the card's disappearance is its feedback, and symmetry keeps the mental model clean).

TriggerToolbar "Show archived (n)" is on; archived card visible with dashed/dimmed treatment (§4).
MenuUser taps ⋯ on the card. Menu now leads with Unarchive (§3).
ClickOne click, no dialog. Optimistic: card restyles to live instantly; updateBoardTask(id, ideaId, { archived: false }) fires.
SuccessCard is live, draggable again, same position. logTaskActivity("unarchived"). If it was the last archived task, the toolbar toggle disappears (existing archivedCount > 0 gate) — expected, nothing left to show.
FailureServer action rejects → rollback fn restores archived styling in place.
RecoveryCouldn't unarchive task
Same voice as the existing "Couldn't archive task". Card is still visible and archived — the user retries from the same menu. No dead end, no trapped state.
Realtime echo guardUnarchive is a state change, not a removal, so trustRemoval is the wrong guard. The new ops.unarchiveTask must make the local flip win over a lagging Realtime snapshot the same way trustMove protects moves — otherwise a stale echo re-dims the card for a beat and the interaction feels broken.

Menu for an archived card. Unarchive is first — it is the only reason anyone opens this menu on an archived card (recognition over recall; Fitts: primary action lands where the pointer already is, at the top nearest the trigger).

Spec

  • Label: "Unarchive" — matches the detail dialog exactly. Specific verb, clear information scent; not "Restore" (collides with delete-recovery semantics we don't have).
  • Icon: lucide ArchiveRestore (already imported in task-detail-dialog.tsx) — same box silhouette as Archive with an up-arrow, so the pair reads as semantic opposites at a glance. Size/spacing identical to siblings: className="mr-2 h-4 w-4".
  • Position: first item, gated task.archived — the exact structural mirror of the existing !task.archived Archive block. Archive and Unarchive are never visible together.
  • Behaviour: one click via onSelect, no confirmation dialog (constructive, instantly reversible — Archive itself has none; a dialog here would be pure friction).
  • Hide "Move to top / Move to bottom" when task.archived. Dragging is already disabled for archived cards; offering position moves on a card that's hidden from teammates with the toggle off is an incoherent affordance and pure Hick's-Law noise. Fewer items = faster to the one that matters.
  • Item padding: reuse the existing responsive py-2.5 sm:py-1.5 — mobile rows stay comfortably tappable.

4Archived card visual treatment

5Accessibility & mobile confirmation

  • Contrast (AA): removing whole-card opacity is the fix, not a side effect — all archived-card text lands on text-muted-foreground, which passes 4.5:1 in both zinc themes (figures above); the dashed border is a ≥3:1 non-text cue by shape, not colour.
  • No colour-only signalling: archived state = dashed border + icon-and-text badge + menu wording; failure = toast text, not just red.
  • Keyboard: Radix DropdownMenu already gives full arrow-key/Enter/Escape support; Unarchive is a plain DropdownMenuItem, so it inherits it. The ⋯ trigger already has focus-visible:opacity-100 + ring.
  • No hover-only affordance: the ⋯ trigger is always visible on mobile (sm:opacity-0 applies only ≥sm) — unchanged.
  • Touch targets: trigger is h-11 w-11 (44px) on mobile; menu items keep py-2.5 mobile padding. Unarchive adds nothing smaller.
  • Screen readers: "Unarchive" as the accessible name is self-describing; the badge already reads "Archived" inline in the card's text flow.

6Product Owner review

Verdict: approve as-is. Every requirement and acceptance criterion is met: one-click unarchive from the card menu, restore in place with no data loss, archived cards visually distinct, optimistic update with rollback + toast + activity log entry, existing entry points (toolbar toggle, detail-dialog button) untouched.

Two things worth naming rather than hiding: the Realtime echo guard in §2 is the one place a subtle bug could slip in, so the engineer should follow that note exactly; and the light-theme contrast figure in §4 (4.7:1) is close enough to the 4.5:1 floor to be worth a quick visual spot-check during build.

One small addition beyond the brief: hiding "Move to top / bottom" on archived cards (§3) wasn't asked for, but removes an affordance that no longer makes sense once dragging is disabled. Flagging it here so it isn't a surprise in testing — not scope creep, just a loose end this design also tidies up.
