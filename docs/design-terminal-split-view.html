Terminal split view — two panes, one keyboard

UX design for task df7a0134 · workflow step 2 of 6 · builds directly on the approved Requirements step (ProdOwner, 2026-08-20)
2-pane split · 50/50 · opt-in toggle Exactly one pane owns the keyboard Tabs stay the default Never unmount an xterm

The Requirements step already locked the shape of v1: an opt-in toggle (tabs stay the default), two panes only, a 50/50 split, exactly one pane owning keyboard input, focus signalled by border + words + dimmed chrome + cursor shape (never colour alone), popped-out sessions never claim a pane, never unmount an xterm, and a width floor that falls back to tabs. This document does not relitigate any of that — it turns each decision into concrete pixels, tokens and flows, and answers the three questions Requirements left open (§7): pane assignment with 3+ sessions, whether a per-pane swap control is needed, and the exact px floor.

One genuine late addition from Nick (2026-08-20), received during this design step: split view must also be reachable by direct manipulation — drag a tab and dock it to the left or right half, the way panels dock in an IDE. That is designed in §6 as a second entry route; the toggle remains the primary, keyboard- and touch-accessible path. It supersedes any earlier assumption that the toggle is the only way in.

4 · Pane header anatomy

Left→right, mirroring the shipped session header so nothing has to be relearned: focus-state chip (new, always first — it is the answer to “where will my keys go?”, so it sits where scanning starts) · status pill (existing component, compact glyph-only under 560px pane width) · session name (new in the header — with two panes visible each needs its own name; deriveTabLabel() output, CSS-truncated, full text in title) · controls: Pop out, Read-only, End (the existing three, icon-only below 560px pane width with their existing aria-labels; every target keeps ≥ 24×24px hit area with padding). The host / session-id mono text is dropped from pane headers entirely — it is already hidden below sm today and is the lowest-value item at 480px.

The header is a click target for focus like everything else in the pane (§5.3) — with one carve-out: clicks on the three control buttons act without first moving focus (ending or popping out the Watching pane must not first steal the keyboard from the pane you're typing in).

The 3-session case is visible in wireframes B/C: the third session stays a plain tab, fully live, reachable by one click; the two paned tabs carry “L”/“R” badges so the strip answers “which two am I seeing?” without looking down. (Superseded — under Requirements v3 D2 a third open session gets a third pane, never a leftover pane-less tab; see §10.)

5 · Interaction flows

5.1 Entering split

Two routes reach the same state: the toggle (below — the deliberate, keyboard/touch-accessible route) and drag-to-dock (§6 — direct manipulation). Both end in identical pane state, refit, focus and persistence; only the announcement wording differs.

Click ◫ toggleor keyboard-activate it in the strip→ Panes assigned: active tab → left, most-recently-active other eligible → right→ Both xterms refit + PTY resizesame forced refit bring-back already uses→ Focus stays with the previously active sessionno surprise keyboard move→ Announce: “Split view on. Fix login redirect loop left, Terminal: view multiple… right. Typing goes to Fix login redirect loop.”

Leaving split (toggle again): the focused pane's session becomes the single active tab; one refit; announce “Split view off. Showing Fix login redirect loop.” Preference persists via localStorage using the dock-height contract (never-throw, validate on read).

5.2 Clicking a tab while split

  • Tab of the focused pane — no-op (already selected); no announcement.
  • Tab of the unfocused pane — focus moves to that pane. Identical to clicking into it (§5.3).
  • Tab of a third session — its session replaces the unfocused pane's content and takes focus (a tab click has always meant “attend to this one”). The replaced session stays mounted and live as a plain tab. The pane you were typing in stays visible and demotes to “◇ Watching”. Both panes refit only if geometry changed (it didn't — 50/50 is stable), so this is a pure re-parent of already-mounted views, never a remount. (This “third session as a plain tab” situation is 2-pane-era: it no longer arises once §10's all-or-nothing rule applies — three open sessions means three panes; see §10.)

5.3 Clicking into the unfocused pane

Click anywhere in the paneoutput, header, padding — control buttons excepted→ Real DOM focus routed to that pane's xterm→ All four signals flip atomicallyborder+glow, words, brightness, cursor→ aria-selected moves to its tab→ Announce: “Typing now goes to Terminal: view multiple open sessions…”

The click that focuses a pane is swallowed — it must not also select text or reach the PTY as a stray event. Focus and visual state share one source of truth (the pure module's focusedPaneKey), verified against real document.activeElement — no split-brain.

5.4 Keyboard: moving focus between panes

Chord: Ctrl+Shift+← focuses the left pane, Ctrl+Shift+→ the right. Absolute, not cyclic — it names the destination, so it is idempotent (pressing “left” while left is a silent no-op; no announcement spam) and spatially honest. It is intercepted in both panes via xterm's attachCustomKeyEventHandler (returning false so it never reaches the PTY) and by a dock-level keydown for when DOM focus is on pane chrome. Works only while split; in tabbed mode the keys pass through untouched.

5.5 Pop-out while split

Pop out the unfocused pane: it leaves the dock (existing pop-out flow); if a third eligible session exists, the most-recently-active one fills the vacated pane (still unfocused); otherwise split suspends and the surviving session renders full-width — the mode preference is kept, and split resumes automatically when a second eligible session appears (launch, reconnect, or bring-back). Pop out the focused pane: same, plus focus moves to the surviving pane and is announced. A popped-out session never occupies a pane (shipped invariant): its tab shows the existing ⧉ violet treatment and is excluded from pane eligibility.

5.6 A session ends while split

The pane keeps its slot and renders the existing ended panel in place — scrollback intact, Resume available, ■ glyph in tab and status pill. Nothing collapses under the user mid-read. If the ended pane was focused, focus moves to the live pane (announced: “Session ended: vibecodes · a3f2. Typing now goes to Fix login redirect loop.”). Closing it via the tab ✕ follows the existing confirm flow; on close, a third eligible session back-fills the pane, else the survivor goes full-width as in §5.5.

5.7 Resize while split

Dock-height drag and window resize refit both panes (each pane's existing ResizeObserver sees its own container change — verify a PTY resize is sent per pane, per Requirements AC11–12).

5.8 Narrowing below the width floor

Dock body < 961px→ Tabs render; both sessions stay mounted; preference untouched→ Amber notice (once, dismissible) + announce: “Window too narrow for split view — showing tabs. Split returns when wider.”→ Body ≥ 981px → split restores itself, refit, announce “Split view restored.”

The 20px hysteresis band (fall back <961, restore ≥981) prevents mode-flapping while dragging a window edge across the boundary. Pressing the toggle while below the floor stores the preference and shows the same notice — the button is never disabled (mockup D).

6 · Second entry route: drag a tab to dock it

Nick's request, verbatim: “can we have a drag and drop version as well, where i can drag a tab and it can latch onto the right or left — just like a panel behaves in something like an IDE.” This is the VS Code / JetBrains panel-docking convention, so the design copies that grammar rather than inventing one (Jakob's law): a drag ghost of the tab, translucent drop zones over the halves of the dock body, the hovered half lights up, release docks, Esc or releasing anywhere else cancels.

6.3 Drop outcomes

  • From tabbed mode, drop on a half: split turns on with the dragged session in that half; the other half takes the previously active session (if the dragged one was active, the most-recently-active other eligible session — same MRA rule as §7 Q1). Preference stored, both panes refit + PTY resize — the toggle's exact pipeline (§5.1).
  • Already split, drop a third tab on a half: that half's session is replaced (it returns to being a plain live tab). Unlike the tab-click rule (§5.2), the user chose the side explicitly, so the drop may replace either pane — including the focused one.
  • Drag a paned tab back into the strip and release: split ends — the return path. The dragged session becomes the single active tab (it is the one in hand); the other pane's session returns to a plain tab; preference updates to tabs, one refit. Mid-drag the strip highlights as a drop target (“Back to tabs” indicator line) so the destination is legible before release.
  • Focus after any drag-dock lands: the just-dropped pane takes keyboard focus — direct manipulation is the strongest possible statement of attention — and every §3 signal applies to it instantly. Live region: “Split view on. Terminal: view multiple… docked right. Typing goes to Terminal: view multiple…” (or “…docked left…” / “Split view off. Showing Fix login redirect loop.” for the return path).
  • Popped-out tabs are not drag-docking sources: a popped-out session never claims a pane (shipped invariant), so its tab never activates a docking drag — press-and-move on it does nothing beyond the existing click behaviours. It may still be reordered along the strip.
  • Dragging a tab out of the browser window: out of scope. Pop-out already covers “this session in its own OS window”, with the relay's single-attach machinery behind it; a drag-out gesture would be a second, worse path to the same result. Explicitly not designed.

6.4 Accessibility and implementation notes

  • The toggle is the accessible equivalent, stated plainly: drag-and-drop is pointer-only here. dnd-kit's keyboard sensor is deliberately not wired to tabs — arrow keys already navigate the tablist, and a keyboard drag mode would fight both that and the terminal's key handling. Keyboard and switch users reach the identical end state via the toggle + Ctrl+Shift+←/→; touch users via the toggle (long-press drag works but is not the recommended path).
  • Reuse @dnd-kit, don't hand-roll pointer events: it is already a project dependency doing drag-and-drop on the board, and it supplies exactly the pieces this gesture needs for free — the 8px distance and 250ms touch activation constraints, Escape-to-cancel, portal drag overlays, and collision detection for the zone/reorder target swap. A bespoke pointer-event layer would re-implement all of that and drift from the board's behaviour.
  • Hard invariant for the engineer: the drop handler mutates only the pure module's pane-assignment state; the panes are already-mounted xterm instances that get re-laid-out by CSS, exactly as the toggle does. A drag must never cause a remount — the “placeholder tab + portal ghost” pattern above exists precisely so the real tab (and its session view) never leaves the tree — and the drop must trigger the same forced refit + PTY resize that entering split via the toggle does.

7 · The three open questions, answered

Q1 — Pane assignment with 3+ sessions

Adopt Requirements' recommendation, with the focus rule made explicit. Panes hold the active tab + the most-recently-active other eligible session (eligible = mounted, not popped out; ended sessions remain eligible — they hold readable scrollback). Clicking a third tab replaces the unfocused pane and takes focus. Rationale: the unfocused pane is by definition the one the user is not typing in, so it is the only slot that can change without risking a mid-keystroke context switch; and a tab click has meant “make this the one I'm attending to” since tabs shipped — split view must not quietly change what a click means (recognition over recall). MRA beats list-order because it matches “the two things I was just working with”, the same recency logic the chooser already uses. (Historical answer for the 2-pane feature as shipped. Superseded for 3+ sessions by Requirements v3 D2 — every open session gets a pane, so no session is ever left as an unpaned tab alongside visible panes; see §10.)

Q2 — Per-pane “swap session” control

Not in v1. The tab strip is already a complete, visible, familiar switching surface one glance above the panes, and §5.2 makes it the swap mechanism for free. A per-pane dropdown would be a second, competing way to do the same thing (Hick's law), would cost header space that does not exist at the 480px floor, and would need its own keyboard/a11y surface. Revisit only if real usage shows people popping out sessions just to rearrange panes.

Q3 — Exact px floor for a ~60-column pane

MIN_PANE_WIDTH_PX = 480; split requires a dock body ≥ 961px; restore at ≥ 981px (20px hysteresis). Derivation from shipped values, not taste: xterm runs at fontSize: 12.5 in SF Mono/Menlo-class faces (use-terminal-session.ts:704–708), whose advance width is ≈0.602em → ≈7.53px per cell; 60 columns ≈ 452px, plus the container's px-3 padding (24px) and the 2px focus border ≈ 478px → rounded to 480. Two panes + 1px divider = 961px. The constants live in the new pure module beside the pane-assignment logic, with a comment tying them to the font metrics so a future font-size change knows to revisit them.

8 · Accessibility

  • Tablist stays coherent: the strip keeps role="tablist" / role="tab"; aria-selected="true" tracks the focused pane's tab — exactly one selected at all times, in both modes. The other paned tab is plain aria-selected="false"; its visibility is conveyed by its pane's own semantics, not by inventing a second “selected”.
  • Panes: each pane wrapper keeps role="tabpanel" + aria-labelledby its tab, and both visible panels drop hidden/aria-hidden; non-pane sessions keep today's hidden treatment. Each pane additionally exposes focus state in its accessible name via a visually-rendered, programmatically-associated chip: accessible name resolves to e.g. “Fix login redirect loop — typing here” / “Terminal: view multiple… — watching”. The a11y tree can never report two typing panes because the name derives from the single focusedPaneKey.
  • “L”/“R” tab badges carry aria-label="in left pane" / "in right pane" — words, not position-by-colour.
  • Live region (the existing shared polite announcer, one message per event, never per re-render): split on/off (§5.1), drag-dock landings and the drag return path (§6.3), focus moves — click or chord — (“Typing now goes to …”), width-floor fallback and restore (§5.8), session-ended focus handoff (§5.6). Background-tab attention announcements (shouldAnnounceAttention) continue unchanged; a paned session counts as “active” for that rule (its state is on screen — announcing it would double-speak).
  • Keyboard reachability: the toggle is a real button in the strip's tab order with aria-pressed; Ctrl+Shift+←/→ moves pane focus; the existing arrow-key tab navigation is untouched. Focus-visible rings on all pane controls at both dim levels (§3 contrast row).
  • Drag-to-dock is pointer-only by design (§6.4): every state it can produce is reachable via the toggle and the chord, so no keyboard drag mode is added — one that fought the tablist's arrow keys and the terminal's key handling would be worse than none.
  • Never colour alone: every focus signal has a non-colour twin — words (chip), shape (solid vs hollow cursor), weight (name), and the border is presence/absence, not hue-vs-hue.

9 · What the engineer must not break

  • Never unmount an xterm. Mode switches, pane swaps, drag-docks, floor fallback and pop-out are all CSS/layout re-arrangements of the always-mounted TerminalSessionViews — scrollback, socket and connection state survive every transition in this document. The drag gesture in particular: source tab stays mounted as a placeholder, the ghost is a portal clone, and the drop mutates only pane-assignment state, then fires the same forced refit + PTY resize as the toggle (§6.4).
  • One keyboard owner, enforced not implied. useTerminalSession's auto-focus on expand/refresh must be routed: exactly one pane gets the focus grab; the other gets refit without it. Visual focus state must derive from the same single source the DOM focus does.
  • Refit + PTY resize on every geometry change: enter/leave split, pane swap, back-fill, floor fallback/restore, dock-height drag, window resize.
  • Popped-out sessions never claim a pane, and their mid-preemption status is never read as ended/errored.
  • Chooser and overlay discipline untouched: inline browse still CSS-hides the whole session container (both panes); every dialog stays dismissable.
  • The chord never reaches the PTY, and no other key is newly intercepted — a terminal that eats keystrokes is broken.
  • Sessions with no recorded folder keep their existing chooser/reconnect behaviour — split view changes nothing about eligibility rules beyond pop-out exclusion.
  • Pure logic in src/lib/terminal/ (suggested: split-view.ts — pane assignment, eligibility, focus ownership, width floor + hysteresis, persistence read/write) with unit tests, mirroring terminal-tabs.ts; the dock stays event wiring. Everything behind NEXT_PUBLIC_TERMINAL_ENABLED.
  • Tab semantics: dedupe, per-tab close/confirm, cap refusal, task-launch choice and “+” behave identically in both modes; aria-selected stays singular.

10 · v3 addendum — a third pane, and the all-or-nothing rule

2 or 3 panes — never more, never a partial mix Tabs line up with panes, edge for edge 4th session → the whole dock is tabs

This section is the Requirements-v3 addendum for task eda6598b (“a third one goes missing instead of getting its own pane”). §1–9 above remain the record of shipped v1 and are unchanged, but v3 supersedes four specific v1 decisions. The reason is one rule:

The all-or-nothing rule (Requirements v3, D1–D2)

Split renders only when every open dock session has its own pane — 2 sessions → 2 panes, 3 sessions → 3 panes. If that is impossible (a 4th dock session, or not enough width for the current count), the dock is entirely plain tabbed mode — no panes anywhere. There is never a state where panes are visible and any session's tab exists without a pane under it. Side by side is allowed for 3 or less, full stop.

10.0 What v3 supersedes in §1–9

  • §1 “Pane assignment (3+ sessions)” and §7 Q1 — dead. There is no “active + most-recently-active, third stays a tab” pick, because a third dock session now always gets its own pane (or the dock is fully tabbed). Nothing is ever left tab-only while panes show.
  • §5.2's third bullet (“tab of a third session replaces the unfocused pane”) — unreachable. While split renders, every tab has a pane; a tab click only ever moves focus.
  • The half-width tab groups (splitTabGroups, the task-c108ae4a fix) — generalised and tightened: the strip becomes exactly N pane-aligned tab columns (§10.2), and no un-paned tab may live among them. Popped-out sessions move to a compact affordance in the pinned utility cluster (§10.4).
  • “Open — not shown” tab indicators (an interim concept from this card's earlier drafts) — removed from scope entirely. The state it labelled can no longer occur.

Everything else stands: the four focus signals, never unmounting an xterm, popped-out sessions never claiming a pane, mobile never splitting, the toggle + drag entry routes, and ≤2-session behaviour byte-identical to shipped v1 (the one visible ≤2 change: a popped-out session's affordance moves out of the tab columns, §10.4).

A popped-out session has no pane to align to (it lives in its own OS window), so it may never sit among the pane-aligned tab columns — that would recreate “a tab without a pane”. It becomes a compact violet ⧉ chip in the pinned utility cluster: aria-label="1 session popped out: Recreate staging…", title lists the name(s), click brings that window to the front (the existing pop-out focus affordance). It does not count toward the 3 (D3's axis is dock-resident sessions only): 3 in the dock + 2 popped out still renders 3 panes. In tabbed mode the popped-out session keeps its existing violet tab treatment unchanged. This chip placement applies at every pane count — the one visible change to shipped 2-pane split, and only when a pop-out exists.

10.6 Notes for the engineer (delta to split-view.ts)

  • New constants beside the shipped pair, same derivation comment: SPLIT_FALLBACK_BODY_PX_3 = 1442 (3 × 480 + 2 dividers), SPLIT_RESTORE_BODY_PX_3 = 1462. resolveWidthFloor takes the pane count so each count checks its own boundary pair.
  • isSplitRenderable becomes the all-or-nothing gate: preferred && dockCount >= 2 && dockCount <= 3 && widthFitsCount && !mobile. eligibleCount's meaning shifts from “enough to fill 2 panes” to “every dock session gets a pane”.
  • splitTabGroups, applyTabClickToSplit's replace branch, and the MRA pane-picking in enterSplitAssignment/reconcileSplitAssignment are superseded: assignment is simply all dock sessions in strip order. Backfill logic reduces to “re-derive panes from the strip”.
  • Count transitions are synchronous with the open/close action — the 4th session must never render a pane for even one frame. Width transitions keep the measured-then-flip behaviour with hysteresis.
  • Everything in §9 still binds: never unmount an xterm (the 3↔tabs flip is CSS re-layout of mounted views), one keyboard owner, refit + PTY resize per geometry change, chord never reaches the PTY, popped-out never claims a pane, all behind NEXT_PUBLIC_TERMINAL_ENABLED.
