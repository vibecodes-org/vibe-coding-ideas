00Summary

The article's thesis holds in one place and doesn't in another. The finding isn't "adopt the article" or "reject it" — it's that VibeCodes has two different failure modes mixed into the same prompt surfaces, and they need opposite treatment.

→Generic textbook knowledge dressed up as project rules (persona "Expertise" sections — SOLID, N+1s, caching strategy, Core Web Vitals) is exactly what the article says to cut: Opus-5-class models already know this, and telemetry shows zero VibeCodes-specific content in it. ~80% of a persona prompt is this category.
→A single hard behavioral mandate (spawn a fresh subagent, don't inline) exists because a capable client — Claude Code itself — was observed choosing convenience over correctness in production, per the commit that hardened it. That's not a knowledge gap the model needs "less constraint" to solve; it's an incentive problem the model resolves the wrong way when unconstrained. Cutting this because it reads as verbose would very plausibly regress the exact behavior it was written to stop.

Full change list is in §03 — 10 rows, ordered by impact/effort, including one explicit keep-as-is and one item explicitly deferred past 3 months.

Verdict on the P0 decision

"Migrate persona content into skills" (expensive) — not "rewrite personas shorter" (cheap) alone. A blind character-count trim would cut the same generic-knowledge content the article targets, but throws away real (if generic) domain guidance some models still benefit from (see Q3). The right move is the one the schema already supports: extract the Expertise sections into ~10–15 role-clustered skills (roles cluster tightly — Backend/Data/DevOps personas share most of their bullets), leave Goal + the one product-context sentence inline, and let claim_next_step's existing available_skills mechanism do the progressive disclosure it was built for.

Q3What breaks if we strip constraints, given we don't control the model?

The article's advice is explicitly scoped to advanced models. VibeCodes personas execute on whatever the calling user's key resolves — BYOK keys of unknown vintage, or a platform tier that today maps frontier→opus / standard→sonnet / cheap→haiku (confirmed live in platform_settings.model_tier_defaults, matches the seed in src/lib/platform-model-defaults.ts:41-42 — the one line the brief permits on model-tier mapping: Opus 5 resolves under the existing "opus" alias, with fallback.opus = "fable". No further action, per scope.)

Model-conditional-safe

Trim the repeated "don't inline" reinforcement (Q1 prototype)

This is an orchestrator-level instruction interpreted by whatever client runs claim_next_step (today: Claude Code). It isn't executed by the persona's own model at all — safe to slim regardless of which model the step's subagent resolves to.

Model-conditional-risk

Stripping persona "Expertise" sections

A weaker BYOK model may not reliably self-initiate a get_agent_skill_content call to recover the guidance — nothing today forces or nudges that round-trip for anything but the 2 skills that already exist. Gate the migration behind either (a) always keeping a one-line skill pointer in the persona prompt (already in the §02 prototype), or (b) detecting tier and only fully stripping for frontier.

No surface audited requires a global "slim only for Opus 5" gate — the two prototype rewrites in §02 are both safe under (a) above without new tier-detection plumbing.

Q4Which of the 85 tool registrations duplicate instructions that live elsewhere?

mcp-server/src/register-tools.ts has 85 server.tool(...) registrations (confirmed by count). Four concrete, named duplication/drift cases found across the workflow-tool family:

1 — Drift, not just duplication

claim_next_step's static description contradicts its own dynamic instruction

mcp-server/src/register-tools.ts:1217 tells the caller: "If bot_id is set, call set_agent_identity with that bot_id before executing the step." That was true before the subagent model shipped. The tool's actual runtime instruction field (mcp-server/src/tools/workflows.ts:931-947) now says the opposite — spawn a subagent, and only call set_agent_identity as the last-resort exception. A literal client reading only the static description would reproduce exactly the inlining failure Q1 investigated.

2 — Same rule, two places

"Never self-approve" stated in both the tool description and the dynamic instruction

register-tools.ts:1292 (approve_step description) and workflows.ts:989-993 (claim_next_step's HUMAN APPROVAL REQUIRED block) both independently state the human-only rule. Two copies, two places to go stale — same class of risk as #1, just not yet drifted.

3 — Repeated across 61 rows, not just 2 files

"Reassign yourself before starting work"

Stated once in CLAUDE.md's Board Task Workflow section, then restated verbatim inside all 61 structured persona prompts (supabase/migrations/00105_improve_agent_prompts.sql). For a workflow-driven step, it's largely moot — claim_next_step already binds the step to a pre-assigned bot_id by construction; there's nothing left to "reassign." The instruction only still matters for the (now rare) direct board pickup outside a workflow.

4 — Progressive-disclosure guidance, restated per-claim

Skill-loading instructions duplicated between the static and dynamic layers

get_agent_skill_content's static description already says "Progressive disclosure: only call this when you need the skill's detailed instructions." claim_next_step's dynamic skillsInstruction block (workflows.ts:892-909) restates the same guidance ("Load ONLY the skills that are relevant... do not load all of them") every single claim. Lower priority than #1–3 since the two never contradict, just repeat.

The article's cheapest-win framing — "make parameters more expressive instead of narrating rules" — doesn't have a strong candidate in this tool family: persona_used/model_used/skills_used are already typed enums/free-text fields carrying exactly the signal needed, not prose. The actual cheap win here is de-duplication (rows 1, 2, 3 above), not parameter redesign.

Q5 — rule-heavy AI-feature prompts

src/lib/enhance-prompts.ts (enhance/enhance-create) is already lean — a single-sentence framing + optional kit-context suffix, no rule lists. Not a target.

One candidate found in src/app/api/ai/generate-tasks/route.ts:159-165: the large-idea decomposition nudge includes 2 worked JSON examples of task shape, even though the call already uses a structured-output schema (GeneratedBoardSchema) that could carry a description-length constraint directly (article rule 3: examples → interface design). Q6 — are seeded personas still what's live, or have they drifted?

Both, depending which axis. The template is current (migration 00105_improve_agent_prompts.sql is the newest persona-content migration, dated after 00065). But migrations don't back-fill existing rows: 29 of 95 live bot_profiles rows are still on the older freeform "You are a..." style (some pre-00065, some plausibly user-authored for specific ideas like the Football Results App and YCS personas) — never touched by 00105's UPDATE, which targeted specific seed IDs only.

This is a data-repair problem, not a migration gap: the seed template is fine, but there's no mechanism that reconciles already-created per-idea agent copies when the platform template improves. Some of those 29 rows are likely deliberate user customization, not staleness — a blanket rewrite would be destructive (see change-list row 8, deliberately deferred).

  composition over inheritance, depend on
  abstractions not concretions, but don't
  over-engineer for hypothetical futures.

  loading, database joins, or batching — never loop
  queries inside a map.
- Choose the right caching strategy:
  stale-while-revalidate for UI data, ISR/SSG for
  public pages, server-side cache for expensive
  computations. Cache invalidation is harder than
  caching — always have a strategy.
- Design APIs with consistent conventions: plural
  resource names, proper HTTP verbs, pagination via
  cursors not offsets for large datasets, idempotency
  keys for mutations.
- Index database columns used in WHERE, JOIN, and
  ORDER BY clauses. Composite indexes should match
  query column order. Use EXPLAIN ANALYZE to verify.
- Use optimistic UI updates with rollback for
  user-facing mutations — never make users wait for a
  round-trip when you can show intent immediately.
- Keep bundle sizes small: dynamic imports for heavy
  components, tree-shake aggressively, avoid
  importing entire libraries for one function.
