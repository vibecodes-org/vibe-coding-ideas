Reading a task never starts it

UX Design step — task 7b0c94c6 — 25 Sep 2026 — branch feat/read-only-task-reads

In one sentence: when Claude opens a card to read it, the wording it sees now says "this is just reading — report back and stop; only start the card if the human clearly asked you to work it", so a loose "yes" can no longer turn a read into a claim.

What this is. A wording-only change to the text that connected Claude sessions read from the VibeCodes MCP server. There is no user-visible UI change: nothing on the website, no new setting, no database change. Four strings change (three of them in one file), one stays as it is, and one line is added to CLAUDE.md.

Builds on the Requirements step. It found the same root cause I confirmed in the code: every instruction the agent gets after reading a task presumes work is about to start ("Do NOT begin implementation directly — use claim_next_step…", "Before starting work, pick the team agent…"). None of them say that reading on its own starts nothing. I keep the Requirements strings almost verbatim and make three small edits, each explained below.

1. What went wrong (the incident, in short)

  1. Human: "pull the board". Claude called get_board and gave a good summary. Correct.
  2. Claude ended with a loose question: "Want me to pick it up and read the card properly?" — "pick it up" and "read it" are two different things in one question.
  3. Human: "yes". Claude called get_task, then read the instruction: "Do NOT begin implementation directly. Use claim_next_step(task_id)…" — which reads as "the right way to start is claim_next_step". It claimed step 4 and spawned a subagent.
  4. Human: "what is happening, we are supposed to be reading the cards in Verify".

So two things need fixing in the words the agent sees: (a) the tool text must say reading is not starting, and (b) the agent needs a tie-break rule for ambiguous consent — if unsure, ask; never claim on a guess. Point (b) is the one addition I make beyond Requirements, because the trigger in the incident was exactly an ambiguous "yes".

3c. register-tools.ts — get_task description (full)

`Get single task detail including workflow steps, comments, and recent activity. This is a read-only call: it never claims, assigns or moves anything, and reading a task is not permission to start it. Only act on a task (claim_next_step, update_task, move_task) when the human has explicitly asked you to work that specific task. Once you have been asked to work it and it has pending workflow steps, follow the workflow_instruction in the response — use claim_next_step to execute steps sequentially rather than implementing directly. Each workflow step carries its own \`comments\` array — the step's latest discussion, failure reports, and approval notes (newest first, max 10; type 'output' mirrors are excluded because the step's \`output\` field is canonical). If a step's \`comments_truncated\` is true, older comments exist beyond the 10 returned; \`comment_count\` is a raw total that also counts hidden output-mirror rows, so never compare it to comments.length — the full thread is visible in the web UI. ${LIVE_DATA_SENTENCE}`

3d. steering-copy.ts — SERVER_INSTRUCTIONS (full)

"VibeCodes board data is live and shared: humans and other agents change it while your session runs. Every board tool response is a snapshot stamped with generated_at — treat it as already aging. Before acting on board state (choosing, moving, or completing anything), call the tool again for current state. Never re-read an earlier response from your transcript, never save responses to files for later, and never write scripts to parse tool output — present it directly. Tool calls are cheap; stale reads cause double-claimed tasks and lost work. Reading board data (get_board, get_task, get_my_tasks) never starts work: when asked to read, review or pull something, report back and stop; only claim, assign or move a task when the human has explicitly asked you to work that specific task."

4. Conversation flows — what Claude should do and say

These are the "screens" of this design. Each shows the trigger, the tool calls, and the end state. The rule underneath all of them: read → report → stop. Work only on an explicit ask. Unsure → ask.

Flow 1 — "pull the board", then a loose "want me to read it?" → "yes"

Human: "pull the board"

  1. Claude calls get_board, summarises what is in progress / waiting / blocked. read only
  2. Claude may recommend a next card, but the closing question must have one meaning. Say: "Want me to read E5.22 in full (no changes), or start working it?" Not: "Want me to pick it up and read the card properly?"
  3. Human: "yes" (to the ambiguous version, if it was asked anyway).
  4. Claude calls get_task. The response now says "Reading this task does not start it. Report back and stop unless… if unsure, ask — do not claim."
  5. Claude reports what the card says (steps done, what is next, open questions) and ends with: "That's the read. Say 'work E5.22' if you want me to claim the next step." no claim_next_step, no update_task, no move_task

End state: board unchanged. The human decides. This is the incident, fixed.

Flow 2 — "read the cards in Verify"

Human: "read the cards in Verify"

  1. Claude calls get_board with the Verify column (by name), then get_task for each card there. read only
  2. For each card, Claude reports what it is waiting on from the human: steps done vs not run, any step sitting at "awaiting approval", the latest comment or failure note, attachments, due date.
  3. Example line: "E5.23 Sanity publish loop — all steps done, waiting on you to confirm the publish-to-live test genuinely ran, then move to Done."
  4. Claude stops. It does not approve steps, move cards, or reassign. If a card looks wrong (in Verify with 0 of 6 steps run) it says so and asks what the human wants.

The server-wide sentence ("when asked to read, review or pull something, report back and stop") covers this even before any single card is opened.

Flow 3 — "work task X" (the orchestrator loop, unchanged in behaviour)

Human: "work E5.22" / "pick up E5.22" / "yes" to "start working E5.22?"

  1. Claude may call get_task for context. The instruction's second half applies: "Once asked to work it: do NOT begin implementation directly — use claim_next_step(task_id)…"
  2. Claude calls claim_next_step, hands the persona subagent the work_token, runs the step, calls complete_step with the claim_token, loops. as today
  3. Claude tells the human what it claimed and why, in plain words, as it does now.

The explicit ask names the task, so the "unless" clause is satisfied. Nothing about claiming, tokens or approval gates changes.

Flow 4 — task with no workflow: read vs work

Read: Human: "what's on the trademark card?" → get_task → Claude summarises the card and its comments → stops. No update_task, no assignee change. The new opening ("Reading it does not start it — report back and stop unless…") applies.

Work: Human: "do the trademark card" → get_task → Claude picks the best-fitting team agent and calls update_task with assignee_id so the board shows who is on it → does the work → move_task to the done/verify column when finished. as today

Flow 5 — task with an unresolved workflow suggestion unchanged

Read or work, the answer is the same: Claude tells the human the card has a workflow suggestion waiting to be kept, replaced or removed, and that only a human can resolve it. No claim, no self-assign. The existing string already says this.

The one habit change for Claude: never end a board summary with a two-meaning question. If the offer is to read, say "read"; if it is to start, say "start working". And if a human's reply could mean either, ask one more time rather than claiming.
