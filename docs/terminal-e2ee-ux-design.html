Terminal E2EE — rollout & failure UX

Task: “Terminal P2: end-to-end encryption of the PTY stream (GA gate)” · UX Design step · 2026-09-01

The crypto work is invisible when it succeeds. This document designs the four moments it becomes visible, implementing the UX half of FR-5 from the Requirements deliverable: the Phase A “negotiated, fall back to plaintext” indicator, the Phase B fail-closed connect state, the mid-session integrity-failure termination, and the call on whether an encrypted session gets a positive badge. Everything reuses existing dock patterns — status pills (dockStatusMeta), the sky helper-update nudge family and shared HelperUpdateButton, and the centred StateOverlay panels — no new UI vocabulary is introduced.

0 · The four design calls, up front

SurfaceDecisionWhy
1 · Phase A plaintext fallback A quiet zinc header chip (open-padlock icon + “Not encrypted end-to-end”) that lives for the session, plus a dismissable sky nudge bar with the shared “Update now” button, shown once per session on connect. During rollout most users will be in this state; amber everywhere would read as “the product is broken”. Zinc-with-icon is honest but calm. The nudge reuses the exact helper-update pattern (button + copy family) per the hard rule that every update affordance is the same component.
2 · Phase B fail-closed connect A centred in-panel state (like TimeoutPanel), not a modal. A modal variant is specced only for surfaces that are already dialogs; it closes via X, Escape, and outside-click. The failure happens inside the dock at connect time — the dock body is the context, and project rules say render in the panel unless a live tab needs protecting. A panel can’t trap anyone. Where a dialog is unavoidable, the never-trap rule is explicit.
3 · Mid-session integrity failure Clean terminate → amber “Secure link interrupted” pill + calm overlay offering Reconnect. Never rose “Error”, never garbled output. Per FR-5 this state must be distinct from ordinary errors, and the honest first hypothesis is a network glitch, not an attack. Amber = “something needs attention”, rose = “something is wrong with you/your setup”. Reconnect is the recovery, so it’s the primary action.
4 · Positive “is encrypted” indicator No persistent lock icon. Confirmation lives in the Connected pill’s tooltip (“End-to-end encrypted — the relay can’t read this session”) and as a line in the My sessions panel row detail. Rationale in §5 — the marked state should be the exception, not the rule.

2 · Surface 1 — Phase A: “not end-to-end encrypted yet” (non-blocking)

Two layers with different lifetimes. The chip is the persistent, glanceable truth marker — it sits in the session header next to the status pill and lives as long as the session (so a security-conscious user can always check). The nudge bar is the actionable layer — it appears once when the session connects without E2EE, carries the shared “Update now” button, and is dismissable (X). Dismissing the nudge never removes the chip: the caveat stays visible, the nagging stops.

The chip uses the open-padlock icon so the meaning survives without colour (WCAG: never colour alone). The nudge bar is the exact visual family of the existing helper-update notices (left sky rule, bg-sky-500/5, 11.5px sky text) and its button IS HelperUpdateButton — clicking it runs the shared confirm → quiesce → download flow, including the “your running sessions will end first” confirm. No new update path is invented.

Behaviour details

  • Chip tooltip (hover/focus — the chip is a focusable element): “Traffic to this session is protected in transit, but the relay server can technically read it. Update the helper to close that gap.” Honest about what “not E2E” means without implying the session is unsafe on the wire.
  • Narrow dock (<~480px panel width): chip collapses to icon-only with the same tooltip and an aria-label; it never pushes the status pill out.
  • Dismissal scope: per session (state in the dock, like the existing reconnect note’s dismissedReconnectNote). A new session on the same old helper shows the nudge again — that’s deliberate; it’s the only pressure toward updating before Phase B.
  • Split view / pop-out: chip renders in each session’s own header; the nudge renders once per session view, not once per pane arrangement.
  • Announcement: the nudge bar is role="status" (polite) — it must not steal focus from the terminal, where the user is likely mid-keystroke.

3 · Surface 2 — Phase B: encryption required, helper too old (fail closed)

When TERMINAL_E2EE_REQUIRED is on and negotiation fails, the connect attempt stops before any plaintext flows (FR-5: “never a silent downgrade”). The user sees this in the dock panel as a centred state — the same surface as the existing timeout and session-ended panels — with an amber “Update needed” pill in the header. Framing matters: this is not an error in something the user did; it’s a one-time chore with a one-click fix, so the copy leads with the fix, not the failure.

“Update now” is the shared HelperUpdateButton flow. “Not now” returns the tab to the neutral ready/ended state — the terminal simply stays unavailable, exactly as the task allows. The dock’s collapse, tab close, and Escape all work throughout; there is nothing modal to trap anyone.

Why a panel, not a dialog — and the dialog variant anyway

Two project rules point the same way: “only use an overlay when a live tab genuinely needs protecting; otherwise render in the panel”, and modals break context (this design system avoids them for content that can be inline). A connect failure has no live tab to protect. The panel also survives the user wandering off — it’s still there, un-dismissed, when they come back, which a dialog isn’t.

One surface is already a dialog: launching from a task’s shortcut menu / launch-choice dialog. If the requirement is detected at that stage, the same dialog swaps to this content rather than opening a second one — and per the hard-learned rule it is dismissable every way:

Dialog variant: identical copy and actions. Closes via the X, Escape, and outside-click — all three, in every mode. Closing = “Not now”: no state is lost, nothing was minted, the user can reopen the launch path whenever they’re ready. Focus lands on “Update now” on open and returns to the triggering element on close.

4 · Surface 3 — mid-session integrity failure (calm terminate)

An established encrypted session receives data that fails verification. Per FR-5 the session terminates distinctly and nothing unverified is ever written to the PTY or xterm — so the scrollback beneath the overlay is intact, verified output up to the moment of the stop. The overlay follows the existing StateOverlay recipe (icon · title · body · actions) and the header pill goes amber, deliberately not the rose “Error” pill: rose says “broken”, amber says “paused for a reason”. The copy names the most likely cause first (network corruption) and mentions tampering only implicitly (“couldn’t verify”), because alarming a user over what is almost always a glitch is a worse failure than under-dramatizing a real attack — the protective action (terminate + fresh keys on reconnect) is identical either way, and the user’s job is the same: reconnect.

“Reconnect” reuses the existing reattach-mint path (same as the chooser’s Reconnect) with a fresh key exchange. “Browse sessions” is the existing escape hatch to the My sessions panel. If reconnect fails verification again immediately, fall through to the ordinary connection-error handling — repeating this overlay in a loop would train users to ignore it.

What this state must never do

  • Render partial/garbled bytes and then show the overlay — the terminate happens before any unverified write (FR-5).
  • Use the rose Error pill or the word “attack”, “tampered”, or “security breach” in first-line copy.
  • Auto-reconnect silently. A verification failure is the one connection state where the user should consciously resume — unlike the Wi-Fi-drop state, which does auto-reconnect. That asymmetry is the “distinct termination” FR-5 asks for, expressed in UX.

5 · Surface 4 — the positive indicator: recommend no persistent lock

Call: don’t add a lock icon to the header. Put confirmation one hover away instead.

  • The marked state should be the exception. Once enforcement lands, 100% of sessions are E2EE — a lock on every header is chrome that means nothing (browsers walked this exact path: Chrome removed the padlock in 2023 because users either ignored it or misread it as a quality endorsement). The Phase A “not encrypted” chip already makes non-E2EE the marked, visible state; its absence is the signal.
  • Header space is contested. The session header already carries the name, the status pill, and (Phase A) the caveat chip, in a panel that can be split into panes. Every permanent addition costs truncation at narrow widths.
  • The guarantee is still checkable. Security-conscious users get explicit confirmation in two existing surfaces, at zero pixel cost when idle:

7 · Version-skew matrix (AC-6 / AC-7)

None of the copy above names a version number, claims the update “adds encryption” as a dated fact, or assumes the web app and helper deployed together. Concretely:

Old helper · new web app (Phase A)Negotiation says no; plaintext fallback.§2 chip + nudge. The primary rollout experience.
Old helper · new web app (Phase B)Fail closed before connecting.§3 panel/dialog. “Update now” always fetches the current helper, so the copy never needs a version.

8 · State coverage & accessibility checklist

  • All states handled: negotiating (indistinguishable from the existing amber “Connecting…” — no new spinner state; negotiation adds no user-visible phase), success-encrypted (§5: unmarked + tooltip), success-plaintext (§2), fail-closed (§3), mid-session failure (§4). Empty/loading states are unchanged — this feature adds no new fetches to the dock’s first paint.
  • Never colour alone: every pill/chip pairs icon + label (open padlock = not E2EE, shield = update needed, shield-alert = interrupted, closed padlock = confirmed E2EE).
  • Contrast: all copy tokens ≥4.5:1 on the dock’s #0c0c0e/#0a0a0b grounds (zinc-400 body 7.6:1; sky-300 nudge text 9.8:1; amber-400 pill 9.0:1; the sky-solid button’s text-sky-950-on-sky-500 6.6:1).
  • Keyboard: chip is focusable (tooltip on focus); nudge dismiss X is a real button; overlay actions are in normal tab order; dialog variant traps focus within itself while open but closes on Escape — never traps the user.
  • Screen readers: nudge = role="status" (polite); the §3 and §4 state changes announce via the panel’s existing aria-live region with the pill label + title, not the full body.
  • 375px / narrow panel: chip → icon-only + tooltip; nudge bar wraps its button below the text; overlay copy is already max-width-constrained and centre-scrolls (existing overflow-y-auto overlay behaviour).
  • Realistic data: mockups above use a real-length session name; a long name truncates in the header (existing behaviour) before any chip does — the caveat chip never disappears in favour of the name.
