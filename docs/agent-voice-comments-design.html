Agents comment in their own voice while doing the work
and the ambient identity slot gets retired — design

Step 2 of 6 (UX Design) · Author: Compass · 2026-08-08 · Rev 2 — folds in the two Design Review conditions. Builds on the Requirements doc (step 1). Repo: vibe-coding-ideas, branch master.

0 · The design in one paragraph

Since the claim-token protocol shipped, the agent does the work but Nick gets the byline: every comment posted during a workflow step lands under the human's account, and the subagent has no way to speak as itself at all. The fix: claim_next_step hands out a second token. The orchestrator keeps the existing claim_token (ct_…) for completing the step, exactly as today. The new work_token (wt_…) is the one it gives to the subagent. Any add_task_comment or add_step_comment call that includes a valid work token posts under the step's assigned agent — name, avatar, Bot badge, the lot. No token means a normal human comment, same as today. A stale or wrong token gets a clear error, never a silently misattributed comment. Because the token is checked against the step row on every call, attribution comes from verifiable claim state — there's no session-level "current identity" left to drift. That makes set_agent_identity and the mcp_agent_sessions slot fully redundant, so we retire them, which also kills the persona-mismatch warning that currently fires on every healthy completion. And the board UI needs zero changes: bots already render properly everywhere — they just never get to be the author during workflow runs today.

1 · The mechanism: two tokens, one new parameter

1.1 Why a second token

The obvious shortcuts all fail. Handing the subagent the claim token would give it the power to complete the step — the exact thing the protocol withholds from it on purpose. Trusting a plain "post this as agent X" parameter is self-report, which is how we got the 121-step misattribution audit. And checking only "is this step in progress?" would let any session on the team speak as the persona while a step happens to be running, whether or not it's doing the work. So: a separate token, minted at claim time, that proves you're inside the claim without letting you end it.

OptionVerdictWhy
A. Dedicated work_tokenCHOSENProves participation in the claim without sharing the completion capability. Multi-use, so the subagent can comment as often as it likes; dies with the claim, so "is this token valid?" is a single testable question.
B. Reuse the claim_token for commentsRejectedThe subagent would end up holding the completion capability the protocol deliberately denies it (workflows.ts:933).
C. No token — just check the step is in progressRejectedAnyone on the team could voice the persona while the step runs. That binds attribution to timing, not to doing the work — the ambient slot's failure mode, one step removed.
D. Keep set_agent_identity and have the subagent call itRejectedThat's the mechanism this card retires. Session-scoped identity is what drifted under concurrency and produced the audit mess.

Clearing at all five sites keeps the rule honest in the data itself: a work-token hash exists if and only if the step is in progress under a live claim — not just enforced by a status check at read time.

1.3 What agents actually see

The MCP tool surface is the UI here, so it gets the same care as a screen. No new tools — agents already know add_task_comment and add_step_comment. Each grows one optional parameter, and claim_next_step explains it at the moment it matters.

1.4 How a comment gets attributed

This logic lives in the shared tool handlers (comments.ts and workflows.ts), which both transports run. That's what makes stdio safe: its service-role client bypasses RLS, but it can't bypass code it's running.

  1. No work_token? Author is ctx.userId. Byte-identical to today.
  2. Token starts with ct_? Reject immediately with err-5. Fail fast, name the mix-up.
  3. Find the step. For add_step_comment, fetch the step by its step_id param. For add_task_comment, look up task_workflow_steps by task_id plus the token's hash — scoped to the task, so no new global index, and you structurally can't voice step A's persona on task B.
  4. Verify (constant-time, reusing verifyClaimToken against work_token_hash): hash matches, step is in_progress, step has a bot_id. Any failure gets the matching error from §1.6. We reject rather than quietly falling back to human attribution — a caller who asked for agent voice and didn't get it needs to know.
  5. Attribute. author_id = step.bot_id, and the same identity flows downstream:
    • logActivity gets an optional actorId override, so the activity timeline shows the agent (it already knows how to render bot actors).
    • notifyMentions gets an actorId too: mention notifications carry the agent as the actor, and self-suppression keys on the speaker, not the connection. Concretely: when Compass writes @Nick, Nick gets notified — even though it was Nick's own JWT that made the call. decision 1, §7

No back door into completion: the comment path never touches step status, output, or run state, and a work token presented to complete_step fails its token check — with the helpful err-6 rather than a generic refusal. Commenting is a write to a comment table, full stop.

1.5 RLS: who may author as which bot

In remote mode every insert runs under the human's JWT, so the database is the last line of defence. Today's policies let you author as a bot you own. That's almost right, but it breaks on collaborator runs: the step's bot may belong to a different team member than the person whose session is executing the run, and the owner-only rule would block exactly the comments this feature exists to create.

The policy this design sets: a team member may author as a bot that's on the idea's team. The precise "are you actually inside the claim?" check stays in the tool layer — RLS can't verify tokens — but RLS caps the blast radius: never someone else's bot on an idea you're not part of. One additive migration, deployed before the code:

Task comments have always had a looser insert policy than everything else — it checks team membership and never looks at author_id at all (migration 00039 even left itself a note about it). The review made closing this non-optional, and the safety check is done: there are only two insert paths into the table (the web comment form and the MCP tool), and both write authors the tightened policy still allows. Net effect: you can never author as a bot outside the set of bots you own plus bots on teams you belong to (database, remote mode), and never as any bot without a live work token for that bot's in-progress step (code, both modes). Edit and delete stay owner-scoped, unchanged — in a collaborator run, the human who executed the step can't edit the resulting bot comment; the bot's owner can. That's the right shape for a board that's supposed to be a trustworthy record.

1.6 The error catalog

Every rejection says what happened, why, and what to do next. None of them changes any state. Each one also logs a structured warning — that's where the operator signal for attribution funny-business now lives (§4.2).

err-1 · step no longer in progress (add_step_comment, known step)
"Step "<title>" is no longer in progress (status: completed). Its work token was retired when the claim ended — the agent's voice covers only work under a live claim. If you are the working subagent, stop and report back to your orchestrator. If this note still matters, resend it WITHOUT work_token to post it as the human account."
err-2 · token superseded (step in progress, hash mismatch)
"This work token is not the current one for this step — the step was re-claimed and a fresh token was minted (last claim wins). Your run may have been restarted. If you are the working subagent, stop and report back to your orchestrator rather than retrying."
err-3 · no matching step (add_task_comment, hash lookup empty)
"This work token doesn't match any in-progress workflow step on this task. Either the step finished, failed, or was reset (tokens retire with the claim), or it was re-claimed with a fresh token, or the token belongs to a different task. If you are the working subagent, report back to your orchestrator. To post as the human account instead, resend without work_token."
err-4 · step has no assigned agent (defensive; normally unmintable)
"This step has no assigned agent, so there is no agent voice to post in. Resend without work_token to comment as the human account."
err-5 · claim token passed to a comment tool
"That's a claim_token (ct_…), which authorises complete_step/fail_step and stays with the orchestrator. Comments take the work_token (wt_…) from the same claim_next_step response. If you weren't given a wt_… token, ask your orchestrator for it, or omit work_token to comment as the human account."
err-6 · work token passed to complete_step / fail_step
"That's a work_token (wt_…) — it can voice comments but can never complete or fail a step. complete_step requires the claim_token (ct_…) that the orchestrator kept from claim_next_step. If you are the subagent: you don't complete steps — return your deliverable to the orchestrator instead."

2 · How it plays out

2.1 The happy path

  1. Orchestratorclaim_next_step(task_id) → step assigned to persona P, persona_prompt, claim_token, work_token, and the AGENT VOICE instructions.
  2. OrchestratorSpawns a fresh subagent: persona prompt, step description, prior-step context, and the work token (plus the task/idea/step ids). Keeps the claim token to itself.
  3. SubagentPosts progress as it works: add_step_comment(step_id, idea_id, "Auth flow mapped; two edge cases found…", work_token) → appears as P.
  4. SubagentAsks a question on the task: add_task_comment(task_id, idea_id, "@Nick is the legacy import in scope?", work_token) → appears as P; Nick is notified with P as the actor.
  5. SubagentReturns its deliverable. (The instructions tell it to post any final notes before returning — the voice ends at completion.)
  6. OrchestratorMay post its own coordination note with the same work token → also appears as P.
  7. Orchestratorcomplete_step(step_id, claim_token, output, …) → claimed_by = P as today, both token hashes cleared, voice retired. No warnings in the logs.
  8. HumanReads the thread as an actual team conversation (§3).

2.2 When things go sideways

2.3 Clients that can't spawn subagents

Some clients have no Agent/Task tool and do the step inline. Today they're told to call set_agent_identity — that instruction has to go, and it turns out it was never needed: completion attribution already comes from the claim token, and the work token doesn't care who holds it, only that they're inside the claim. So the fallback keeps full agent voice. The rewritten EXCEPTION text:

EXCEPTION (the ONLY one): if your client genuinely has no subagent/Agent tool at
all, do the step inline in this conversation. No identity switch is needed or
possible: completion is attributed to the assigned persona by the claim_token
automatically. Adopt the persona_prompt as your working style, pass the
work_token on any add_task_comment/add_step_comment you make so they post in the
persona's voice, and when done call complete_step with the claim_token, stating
verbatim in your output: "Completed inline — no subagent capability." If you DO
have an Agent/Task tool, this exception does not apply to you.
  1. Clientclaim_next_step → both tokens land in the same (only) context.
  2. ClientWorks inline; comments with wt_ → voiced as P.
  3. Clientcomplete_step with ct_ → claimed_by = P. Only uses tools that still exist after retirement. No warning fires.

3 · What the human sees on the board

Nothing changes in the UI code. Nothing. Bots are shadow users rows, and every surface already branches on is_bot: task comments (task-comments-section.tsx:345-377 — avatar, Bot icon, tooltip with name and role), step comments (step-detail-dialog.tsx:362-388), the activity timeline (activity-timeline.tsx:187), and the notification bell (notification-bell.tsx:227-230). The rendering path for agent-authored comments has been sitting there working the whole time — agents just never get to be the author during workflow runs. This feature changes which rows get written, not how rows render. That's also why history is automatically safe: no renderer changes, no query changes, no data rewrite, so every pre-existing comment renders exactly as before.

4.2 Killing the warning without losing the signal

The persona-mismatch warning fires on every healthy completion because it compares the step's bot against the ambient slot, and the protocol guarantees the slot is empty. Once the slot is gone, the comparison isn't a drift detector — it's a constant. So:

  • Delete the warning blocks in complete_step (workflows.ts:1155-1171) and fail_step (:1355-1366). A compliant run now logs zero warnings, and claimed_by keeps being written from the token relationship exactly as today.
  • The real signal moves to where anomalies actually show up now: failed token checks. Nobody can act as the wrong persona any more — what they can do is present a bad token, and that's loggable:
    • every err-1…err-6 rejection logs logger.warn("work token rejected", { tool, stepId, taskId, reason, callerUserId, ownerUserId });
    • the existing claim-token rejections in complete_step/fail_step get the same structured warning (today they only throw);
    • the persona attestation fields (persona_used/persona_honored) and the compliance alerts stay untouched.
  • The tool log stays honest: mcp_tool_log.user_id becomes "who's connected" (the human, or a stdio install's static bot) — stable and truthful. "Which agent wrote this?" is answered by the comment row's author_id and the activity row's actor_id, which are now genuinely the agent.

4.3 Rollout order

The constraint: a client running on old instructions must degrade to an error or a human-attributed comment — never to a wrong-persona one. This order guarantees that at every point along the way:

  1. Migration 1 — additive, lands firstThe work_token_hash column, is_idea_agent(), and both policy changes from §1.5. Old code ignores all of it.
  2. Phase A — one deploy, both transportsEverything behavioural: mint and verify work tokens, all instruction rewrites, the sweep, the warning deletion, the discussion agent_id param, set_agent_identity stubbed to a deprecation error, slot reads removed. Stale clients degrade safely: old instructions calling set_agent_identity get an instructive error and their comments post as the human (today's behaviour); steps claimed before the deploy have no work-token hash, so they can't be voiced until re-claimed — fail-safe, not fail-weird.
  3. Verify in prodOne real workflow run on vibecodes.co.uk: voiced comments from subagent and orchestrator, zero persona-mismatch warnings in the Vercel logs, notification actor is the agent.
  4. Phase B — next releaseRemove the tool registration, delete bot-identity.ts and dead plumbing, take the guide tool-table rows out, tidy the comments.
  5. Migration 2 — after Phase B is liveDROP TABLE mcp_agent_sessions. Forward-only, same pattern as dropping users.active_bot_id.

Q1 — do workflow-less tasks (agent = assignee) get agent voice?No. The self-assign instruction is rewritten to explicit assignment (§4.1); comments there stay human-attributed."Doing the work" is defined by a claim, and these tasks have none. Giving them a voice would mean either unverified self-report (the door we just closed) or inventing a second claim-like mechanism inside this card. If Nick wants it, it should be its own follow-up card — an assignee-scoped token is a clean shape for it. decision 3, §7
Q2 — which surfaces?Task + step comments get the work-token voice. Discussion replies get an explicit verified agent_id — as the replacement for the mention flow, not an extension of the workflow feature.§4.1. Idea comments and votes stay out, per the requirements' scope.
Q3 — do no-subagent fallback clients get agent voice?Yes, full voice.The token doesn't care who holds it, only that they're inside the claim. Denying inline clients would be an arbitrary regression. §2.3.
Q4 — orchestrator commenting with no step claimed?Human attribution, confirmed.No token, no voice — and there's no ambient state left to mis-fire.
Q5 — fix historical misattributed comments?No, confirmed.No renderer or data change touches history; it all renders as before.
Q6 — collaborator runs where the bot belongs to someone else?A team member may author as a team agent — but only through a live work token. RLS enforces the team boundary; code enforces the claim. Includes the (now mandatory) task-comments tightening.Owner-only would break collaborator runs outright; team-scoped is the boundary the requirements' own security constraint anticipated. §1.5. decision 4, §7
Q7 — what happens to approve_step's bot guard?Keep the guard, replace the message (no more set_agent_identity reference; it points at web-UI approval or a human-account connection).Cheap, still protects stdio bot installs, and keeps "approval is a human act" enforced rather than assumed. §4.1.

7 · Decisions

Settled at the design review — now conditions of the design

  1. The board_task_comments insert tightening ships. No longer optional. The insert-path check is done: two paths (web comment form, MCP tool), both compatible with the tightened policy. Same migration as the work-token column (§1.5).
  2. work_token_hash is cleared at all five sites that clear claim_token_hash: complete_step (:1207), fail_step (:1401), cascade reset (:1514), approve_step (:1681), reset_workflow (:1907). The last two were missing from the original lifecycle; reset_workflow was a genuine stale-token gap (§1.2). The unit tests in §6 cover all five.

Still open — Nick decides at this gate

  1. Mentions notify the owner even when it's his own JWT posting (§1.4): when an agent writes @Nick, Nick gets the notification, because self-suppression now keys on the speaker (the agent), not the connection. Recommend: yes — otherwise agent-to-owner questions silently vanish, which defeats the point of agents asking questions.
  2. agent_id on add_discussion_reply (§4.1): the one place scope grows beyond task and step comments, as the replacement for the mention-reply flow. Recommend: yes — the alternative is losing agent-voiced mention replies entirely.
  3. No agent voice on workflow-less tasks for now (§5, Q1): follow-up card if wanted. Recommend: defer.
  4. Collaborators may voice team agents through a live token (§1.5, Q6): a team member executing a run may post as the step's assigned bot, even if someone else owns it. Recommend: yes — owner-only breaks collaborator runs.
