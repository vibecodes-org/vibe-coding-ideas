The launch button and your choice of agent: three ways to let people pick — and prefer — Claude Code or Codex

Card "Launch button assumes Claude Code — let people choose their agent". Builds on the step-1 audit (docs/launch-button-agent-choice-ux-audit.md). Mockups only — nothing here is built. Compass, 8 Sep 2026.

What this is actually about. Building on the audit's framing correction (§0, §2): Codex launching already shipped. It sits in the green button's dropdown (both agents, both places to run) and in the task card's ⋯ menu. The two real gaps are:

  1. The green primary button can only ever do one thing — start Claude Code in a terminal window.
  2. The app already remembers which agent you prefer (per account, set when you toggle the picker in the browser terminal) — but no one-click button ever reads it. A Codex user pays an extra click on every launch, forever, and the closed button never hints that another agent exists (audit gaps 1–3).

So the question for these proposals is: how should the primary button let you pick and prefer your agent, without ever switching agents silently, and without re-introducing the "remembered default beat my explicit click" bug (audit gap 11, card 72830a60)?

Rules every option below obeys (from the audit §5 — not re-opened here)

  • The label is the contract. Whatever the green button says is exactly what a click does (FR-15: "no silent agent-switching"). If it starts Codex it says "Launch Codex".
  • Explicit beats remembered. Any item you click by name launches exactly that, and does not rewrite your remembered preference (FR-4a; the precedence PR #272/#281 established).
  • Nothing is added to the launch link. All three options reuse the existing Claude-terminal, Codex-terminal and browser launch paths as-is; no new URL parameter, so the link budgets (1900 / 2048 chars) are untouched.
  • The signed-off dropdown layout stays (agent × where-it-runs, two labelled groups). Where an option touches it, that is called out explicitly as a change for Nick to approve.
  • Nobody gets trapped. Every menu and popover closes on Escape, outside click and a close control.
  • Unknown reads as enabled. The button can't know if Codex is installed until the helper is live; a Codex primary click runs the same pre-flight the dropdown item does today (too-old helper / Codex missing → toast with "How to install Codex").

Button states

Closed: "Launch Claude Code" or "Launch Codex". No other visual difference — deliberately, so the toolbar doesn't shout. Hover/focus unchanged. There is no "unknown" state: the label follows the account preference which is always known.

What a click does

Starts the named agent in a terminal window — today's destination. For Codex it runs the existing pre-flight (helper too old / Codex missing → toast with "How to install Codex"; no folder → the folder dialog, then continues the launch instead of stopping — fixing gap 8's "re-click" dead end).

First-timer vs repeat user

A first-timer sees exactly today's button. Nothing new to learn; ↓ Enter in the menu still does yesterday's thing. A Codex user sees "Launch Codex" the moment they've toggled the picker once — and the one-time toast (with Undo) tells them why, so the change is never a surprise even though it happened away from this button.

Click cost

  • Your default agent, terminal window: 1 (both agents — the fix)
  • Other agent, or browser: 2 (unchanged)
  • Change default: 2 (chevron → "Switch to …")

Discoverability

Better, but honest about the limit: a brand-new user still won't know Codex exists until they open the chevron. The footer line and the renamed chevron label ("More ways to launch") add scent inside the menu, not on the closed control. The picker in the browser terminal remains the other place people find Codex.

Mobile

No launch on phones (both agents need the Mac) — see the shared mobile fix below. Nothing about the preference is phone-specific.

Accessibility

  • Label change is announced naturally by the button's own text.
  • Group headings become real menu labels (shadcn DropdownMenuLabel inside role="group") so screen readers get "Claude Code, group" — fixes audit gap 7 in the right layer.
  • "Your default" is text, not colour-only. Footer "Switch to Codex" is a menu item, keyboard-reachable.
  • Chevron aria-label: "More ways to launch" (was the vague "Launch options").

Audit constraints

Satisfies FR-15 (label changes to match), FR-4a (explicit clicks never rewrite the preference; the footer link is the only explicit write from this menu), the precedence rule, link budgets (nothing added). Strains: the "remembered pick written by any picker" rule means the green button can change because of something you did in the browser terminal — mitigated by the toast + Undo, but it is the one behaviour in A that Nick should consciously accept.

What a click does

Opens the picker. Nothing launches until you pick a destination — so backing out is always free (never-trap rule). The destination buttons are 44px tall and the whole thing works on a phone-width screen, though it still wouldn't be shown on phones.

First-timer vs repeat user

Best first-timer read of the three: the two agents are visible the instant you click, side by side as equals. Repeat users pay for that every single time — the picker remembers their agent, but they still have to click "In a terminal window".

Click cost

  • Any agent, terminal window: 2 — one more than today for every Claude user (the majority)
  • Any agent, browser: 2 (+ chooser if sessions exist), same as today
  • Change default: 0 extra — toggling the picker is the change

Discoverability

Excellent. The word "agent" on the closed button plus two named radios on open means nobody can miss that Codex exists.

Mobile

Same as today: hidden. The popover itself would fit at 375px if a phone launch ever became possible.

Accessibility

  • Popover is a role="dialog" with a label; focus lands on the selected radio (matches the shipped picker's keyboard rules: ←/→ switch, Tab moves on).
  • Beta chip is text + colour. Selected radio is tick + underline + text weight — not colour alone.
  • No split button means one fewer 28px-wide target.

Audit constraints

Satisfies FR-15 trivially (no agent in the label), FR-4a, precedence (the destination click is always explicit), link budgets. Strains: it replaces the signed-off split button and folds the approved agent × place menu into a new shape — a bigger "approved UX change" than A or C; and it regresses the one-click launch that today's users rely on. It also makes the browser-chooser look redundant when it appears a second time (two "Run it with" pickers in a row for browser launches with existing sessions).

Recommendation

RecommendedA — the button follows your pickFixes the actual gap (a Codex user's remembered choice is finally honoured by the one-click button) with the smallest visible change, keeps today's experience byte-for-byte for every new and Claude-preferring user, and honours FR-15's exact licence: the label changes to match. The one behaviour to consciously accept is that toggling the picker in the browser terminal flips the green button — made safe by the one-time toast with Undo.
C as a follow-on, not a competitorOnce A ships, C's Settings section is a cheap, natural addition ("where can I see and change this?") and gives the menu footer a second, more conventional home. Do it after c9837bbb lands to avoid stepping on the same Settings area. Don't make the chooser toggle stop persisting — that would re-split the notion of "default".
B — not recommendedThe best first-impression, but it charges every Claude user an extra click on every launch to solve a problem only Codex users have, and it's the largest change to UX that was signed off two days ago.

The trade-off in one line: A gives Codex users their one-click launch and never surprises anyone at the moment of clicking — at the cost of the button's label being able to change because of a toggle made elsewhere (announced by toast, undoable).

If A is approved, the precedence rule to write into the build card (verbatim)

  1. The green button launches the agent named in its label, in a terminal window. Its label is always the account's remembered agent. Nothing else influences it.
  2. Every dropdown item launches exactly what it says, regardless of the remembered agent, and never changes the remembered agent.
  3. Only two things write the remembered agent: any "Run it with / Start fresh with" picker (as today), and the menu footer "Switch to …" link (new). Both are explicit user acts.
  4. The first time the label changes because of a picker toggle (not the footer link), show the toast once, with Undo, then never again.
  5. A primary Codex click runs the same pre-flight as the dropdown's "Codex › In a terminal window" today, and when a folder is missing it opens the folder dialog and continues the launch after save.

Out of scope, noted for later

  • Remembering the destination (terminal window vs browser) as well as the agent — audit gap 4. Worth its own card; the primary would then read "Launch Codex in browser". Not needed to fix this card.
  • The task-detail header icon stays Claude-only per FR-15; under A it would more honestly follow the remembered agent too (label + tooltip), a one-line change to fold into the build card if Nick agrees.
  • Guide pages and the stale "My sessions" empty-state copy belong to the guide-accuracy card (cacc6f1e).
  • The identifier rename tail (component, hook, event name, guide URL) — audit gap 10 — is engineering hygiene, not UX, and should not block this.
