Terminal helper lifecycle — UX design

Card cc74a067 · step 2 “UX Design” · builds on the Requirements step (completed 10 Aug 2026) · Compass, UX Designer

The helper must be reliably there when a terminal is wanted and reliably gone when it isn’t. This design resolves both halves with one rule: the helper’s life is the life of its sessions, plus one quiet minute — and always-on becomes an explicit, visible opt-in later, not an accident of never exiting. The design covers both v1 (clean lifecycle) and the always-on follow-up so the follow-up extends this design rather than replacing it.

1 · The six decisions

Each open question from Requirements, answered with a concrete recommendation, the rejected alternative, and why.

QuestionRecommendationRejected alternativeWhy
1 · Default posture Quit-when-idle by default. Always-on is an explicit opt-in in the follow-up. v1 Always-on by default with an off switch. The OS relaunches the helper on any vibecodes:// link, so idle-exit costs the user one click they already make — zero friction lost. Always-on-by-default repeats the exact trust failure of the incident (“a process I never asked for never leaves”), and login-item consent is a moment users should walk into knowingly, not discover.
2 · Linger window 60 seconds after the last session ends. New sessions during the window cancel the timer. v1 Immediate exit (0 s); long linger (10–15 min). 60 s absorbs the common “end one, immediately start another” churn without a relaunch, and matches the card’s acceptance criterion (“within ~1 min, pgrep finds nothing”). Immediate exit makes rapid restarts feel stuttery; a long linger recreates “mystery resident process” — the thing story 2 exists to kill.
3 · Quit / status affordance Invisible helper + web-controlled status: a “Helper” row in the existing My sessions panel (status, version, machine, Stop). The menu-bar icon ships with the always-on opt-in only. v1 Permanent menu-bar icon from v1. Under quit-when-idle the helper is only alive while sessions run — a permanent desktop surface would advertise a thing that’s usually not there, and the web app is already where sessions are seen and ended (one mental home, not two). Once always-on exists, a resident background app should follow the Docker Desktop / Tailscale convention and show a menu-bar presence — so the icon arrives exactly when residency does.
4 · Update quiescence “Update” tells the helper to stand down first. No sessions: helper exits immediately, then the download starts. Live sessions: inline confirmation in the web app; on confirm, sessions end, helper exits (no linger), download starts. v1 Start the download regardless and let the Finder “in use” dialog be the error surface; or silently kill live sessions. The whole incident was the Finder dialog being the error surface. Quiescing first makes drag-to-Applications always succeed. Sessions are never killed silently — the user confirms with a plain statement of consequences, honouring story 1’s AC (“nothing is silently killed mid-work”).
5 · Crash handling Log-and-exit, no dialog. The helper writes a crash log and exits. The web app is the notice surface: a rose banner in the affected session view (if one was open) and a “stopped unexpectedly” state in the Helper row. v1 A visible-but-non-blocking native error window. Any native window keeps the process alive and recreates “in use”. The user’s attention is in the browser — the session going down is the symptom they actually see, so that’s where the explanation and the one-click recovery (“Relaunch”) belong. The crash log preserves diagnosability without a hostage process.
6 · Slicing v1 = clean lifecycle (stories 1, 2, 3, 6 + the Helper row as minimal story 5). Follow-up = always-on (story 4 + full 5: opt-in, login item, menu-bar icon). Ship always-on in v1. Matches the Requirements recommendation: the incident is recurring pain and cheap to fix; always-on is consent-sensitive and must sit on a trustworthy exit story. Everything in this document that the follow-up needs is designed here (§4 flow F, §5b) so it extends v1’s surfaces instead of redesigning them.

3 · Interaction flows

Actors: User Web app Helper macOS

A · The upgrader — update with active sessions v1

  1. UserClicks Update now on the update nudge (session view banner or Helper row) while 2 sessions are running.
  2. Web appShows the inline confirmation (§5c): “Your 2 running sessions will end first…”. Nothing has happened yet — cancel is free.
  3. UserConfirms End sessions & update.
  4. Web appEnds all sessions (same path as End all), then sends the quiesce command via the relay.
  5. HelperBridges exit; helper quits immediately (no linger). Web shows “Ready to update — the helper has closed” and starts the download.
  6. UserDrags the new app into /Applications. No “in use” dialog — nothing is running.
  7. UserLaunches a terminal; macOS starts the new helper via the deep link. Helper row now shows the new version. Done — one sitting.

Error recovery: if the quiesce ack doesn’t arrive within ~10 s, the web app still offers the download but shows the fallback notice (§6, “quiesce-timeout”) telling the user the helper may still be closing.

B · The everyday user — End all → helper exits v1

  1. UserOpens My sessions, uses End all sessions (existing inline confirm, unchanged).
  2. Web appEnds every session; sessions list empties; Helper row flips to Winding down (amber, §5a-2).
  3. HelperLast bridge exits → 60 s linger timer → clean quit.
  4. Web appOn next open/refresh the Helper row shows Not running with its reassurance line. Nothing of VibeCodes is left running on the Mac.

C · The crash victim — crash → recover v1

  1. HelperHits an uncaught error mid-session. Writes a crash log, exits. No dialog, no orphan processes.
  2. Web appThe open session view loses its stream and shows the rose crash notice (§5d) — plain words, files-are-safe reassurance, one action.
  3. UserClicks Start a new session (the normal Launch path).
  4. macOSDeep link relaunches the helper fresh. No manual cleanup, ever. A later reinstall also succeeds — nothing was left behind.

D · The updater — nudge → quiesce → replace → relaunch (no sessions) v1

  1. Web appRelay reports an old helper version → sky nudge shows (existing surface, now also in the Helper row).
  2. UserClicks Update now. No sessions are running, so there is no confirmation step.
  3. Web appSends quiesce; helper (if lingering) exits at once. Shows “Ready to update” + starts the download. If the helper was already gone, this step is instant.
  4. UserDrag to /Applications → next launch runs the new version → nudge disappears, Helper row shows the new version number.

E · The cautious user — see it, stop it v1

  1. UserOpens My sessions — the Helper row (§5a) answers “is anything running on my Mac?” at a glance: status chip, version, machine name.
  2. UserClicks Stop. With sessions running, an inline confirm states the consequence (ends N sessions); with none, it stops silently.
  3. HelperEnds bridges (if any) and quits immediately. Toast: “Helper stopped…”.
  4. Web appHelper row shows Not running. It stays stopped until the user launches a terminal again — exactly the promise in story 5.

F · Always-on opt-in with its consent moment follow-up

  1. UserFinds Keep helper ready — an off-by-default toggle in the Helper row (§5b footer). It never self-enables; installing/updating never flips it.
  2. Web appThe consent moment, before anything changes: an inline expansion states in full what turning it on means — “The helper starts when you log in to your Mac and stays running so terminals open instantly. It shows an icon in your menu bar, and you can turn this off or quit it there any time.”
  3. UserConfirms Turn on. macOS registers the login item (visible in System Settings → Login Items — we never hide from the OS list).
  4. HelperSwitches lifecycle: linger timer disabled; menu-bar icon (§5b) appears. Quit-on-idle no longer applies.
  5. UserCan reverse it from either surface: the same toggle, or the menu-bar Quit / Keep helper ready items. Turning it off returns the helper to v1 quit-when-idle behaviour (and it exits right away if idle).

Update flows are unchanged in always-on mode except the last step: after the user replaces the app, the login item relaunches the new helper at next login — and the web app’s “launch a terminal” path still starts it on demand before then.

6 · Edge cases

CaseWhat happensDesign rule that makes it safe
End all, then relaunch inside the linger windowHelper is still resident; the new deep link (or direct session request) cancels the 60 s timer and starts instantly — no relaunch, no double process.Lingering must remain fully connectable; the timer is cancelled by any new bridge, and launch never spawns a second helper (single-instance lock — the link is handed to the running instance).
Two browsers ending sessions at onceBoth browsers call the same server-side end route; the helper exits only when the relay reports zero live bridges. Each browser’s Helper row converges on “Not running” on its next open/refresh.The session registry — not any browser — is the source of truth for N. Quit and stop commands are idempotent; a second command to a dead helper is a no-op, surfaced (if user-initiated) by the “may already be stopped” toast.
Helper killed externally mid-session (Activity Monitor, pkill)Bridges die with it; the open session view shows the same crash notice as §5d; the registry expires the sessions. Next launch relaunches cleanly.Crash and external kill are deliberately the same UX — the user never needs to know which happened, and neither leaves state that blocks a reinstall.
Update clicked while a session is streamingAlways the confirmation first (§5c). On confirm: end-all completes, the helper acks, then exits without linger, then the download starts. If the tab closes mid-flow after the command was sent, the helper still quiesces — the exit is helper-side, not tab-side.Nothing is silently killed; the order (sessions → exit → download) guarantees the Finder never meets a running process; the command outliving the tab means a half-finished flow can’t strand the old version in memory.
Crash during the linger windowProcess dies before the timer fires — the end state (“Not running”) is the same one the timer was heading to. The crash log is still written. No sessions existed, so no crash notice interrupts anyone; the Helper row simply shows “Not running”.Crash-to-exit converges with quit-on-idle: every path out of “running” ends at the same clean, dialog-free state. The rose “Stopped unexpectedly” chip is reserved for crashes that took sessions down with them.

7 · Accessibility & conventions checklist

Applies across every surface above:

Status never colour-aloneEvery state is a pill chip with icon/dot + text label; the linger and crash states also carry explanatory sublines.
ContrastAll copy ≥ 4.5:1 on the zinc panels (emerald-400/amber-400/rose-400/sky-300 on #0c0c0e all pass); chip borders ≥ 3:1 for UI affordance.
KeyboardThe Helper row’s Stop, nudge Update, confirm buttons and crash-notice action are ordinary buttons in the popover’s tab order; confirms are inline (focus moves to Cancel first), no focus traps, Esc closes the popover as today.
No modals, nothing behind hoverAll confirmations are inline row-swaps (the existing End-all pattern); Stop/Update are always visible, not hover-revealed.
Jakob’s lawQuit-when-idle mirrors macOS document-app expectations for invisible agents; the follow-up menu-bar presence mirrors Docker Desktop / Tailscale / 1Password exactly where residency begins.

8 · Explicitly out of scope

Not in this design (mirrors the Requirements step):
  • Windows / Linux helpers (separate backlog card).
  • Auto-update mechanics beyond the existing nudge — silent background updating is a future card; this design only makes the manual replace always succeed.
  • Relay/cloud-side changes beyond the lifecycle events used here (quiesce/stop commands, version report, zero-bridge signal).
  • Multi-machine management UI — the Helper row shows the machine a running helper reports; fleet views are out.
  • Changes to session limits (4 h / 30 min) or to the My sessions panel beyond the Helper row and the confirms described here.

9 · Open questions for Design Review

  • Linger length (60 s) — agreed, or do we want telemetry first? (PostHog already captures end-all; a relaunch-within-2-min counter would validate the window cheaply.)
  • Crash-log affordance — is “Copy the crash log location” enough for v1, or should the helper offer “Reveal in Finder” via a deep-link action?
  • Quiesce transport — this design assumes the relay can deliver a stop/quiesce command to a session-less (lingering) helper. If the helper only holds a connection while bridges exist, implementation may need a short-lived control channel during linger — flagging so Implementation costs it.
  • Always-on scope check — the follow-up consent copy promises “terminals open instantly”; confirm the auto-discovery work (story 4) lands in the same follow-up card so the toggle isn’t over-promising.
