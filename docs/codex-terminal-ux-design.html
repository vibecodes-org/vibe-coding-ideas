One changed the design: "Codex isn't installed" on the desktop-window path is now caught before anything fires — the helper's status says whether Codex is present, and the desktop-launch items are disabled with the reason and an install link beside them (§7b, §12d, §12f, §13). The after-the-fact toast survives only as the fallback for a window that fails to open for a reason the pre-flight couldn't predict.
What changed in the rework, in one paragraph. Codex now runs in two places: the in-browser terminal (everything in §1–§7 as before) and a real Terminal window on the user's Mac, opened by our helper app because Codex has no link scheme of its own (Requirements §2.3). The helper opening a Terminal and running a command is new ground, so before Codex actually starts the user sees what is about to run and presses Enter (§12c — the "see and confirm" safeguard, S-5). The board toolbar's dropdown, which the earlier draft wrongly said "lands on the chooser", is in fact a one-click auto-launcher; it becomes four explicit items grouped by agent (§13). A desktop Codex window is not a dock session — no tab, no pill, no Resume row — exactly like Claude's desktop launch today (§14).

This document designs the user-facing pieces the Requirements step asked for. It does not repeat the requirements; it cites them (US-n, FR-n, AC-n) and decides how they look and behave. Every mockup below is built from the shipped terminal components — the session chooser, the per-task launch dialog, the tab strip, the session header, the centred state panels and the helper-update flow — so nothing here is a new design language. Colours, sizes and copy tone match what is already on screen.

Hard rules this design honours (root CLAUDE.md, In-App Terminal): a launch dialog is never a trap — close button, Esc and outside-click always work; nothing is minted until a click; swapping the dock body kills a live terminal, so warnings for a live tab render as overlays and everything else renders in the panel; a popped-out tab's status is never read as ended; Resume keeps whatever agent the session already had; the recorded project folder is always the main checkout.

The user flow

Trigger → completion, including every way back. "Fresh" surfaces are the only places the picker appears (FR-4). A launch from the board toolbar's dropdown or a task card's menu carries its agent and location from the item clicked instead of showing the picker — those paths have their own flows in §7 (card) and §13 (toolbar). The desktop Terminal window path is a different animal (nothing minted, nothing tracked) and has its own flow in §12b.

TriggerDock chevron "Open" (goes through the entry decision and the picker below); board toolbar "Codex › In the browser" or a task card's "Launch Codex in browser terminal" (agent already chosen — skip to Gate). This flow is the browser terminal; the desktop window is §12b.

12 · Codex in a desktop Terminal window New (US-10, FR-11–FR-14, AC-14–AC-19, spikes S-4/S-5)

Claude's "In a terminal window" is a hand-off: VibeCodes builds a claude-cli:// link and Claude Code's own handler (Anthropic's, not ours) opens the window, shows the prompt and runs it. Codex has no such handler, so "Codex in a terminal window" is ours end to end: the app fires a vibecodes:// link with a new action, our helper app opens a real Terminal.app window in the project folder, and that window runs codex with the starting prompt (Requirements §2.3). This section designs what the user sees on that path. The mechanics (launch script vs AppleScript) are Implementation's call after spike S-4; nothing here depends on which they pick.

What a desktop Codex window is not. It is not a dock session. Nothing is minted, nothing appears in the tab strip or "My sessions", it has no "Codex" pill, no Resume row, and it does not count towards the session cap or the "another session is live" check. This is exactly the standing of Claude's claude-cli:// launch today, and the doc keeps the two alike on purpose (§14). Resume = the user types codex resume in that window.

Because any web page can fire a vibecodes:// link, the helper must never start Codex unattended. The safeguard is in the Terminal window itself: the window opens, prints what is about to happen, and waits for a real key press.   • Why it is a real safeguard, not theatre. The waiting line reads from the keyboard of the Terminal window only. A link fired by some other web page can, at worst, open a window that asks — it cannot press Enter, and the script never runs anything before that key. The last line tells a surprised user what to do ("close this window"). The helper still runs only the fixed codex binary, in a folder that must already exist, with the message as one argument (Requirements, security note) — the review step is on top of those, not instead of them.
  • No "don't ask again". Deliberately: the step protects against links that didn't come from the user's own click, and a remembered "skip" would reopen that hole for every future link. One key per launch is the price, and it is the same price Claude's desktop launch already charges.

If Implementation ships that, the review screen still stays — it is where the user reads the prompt and the shared-folder note before Codex acts on them (FR-12's advisory has no other place to be read). What the token would buy is the freedom to make the Enter step optional later; that is not proposed for v1.
  • Ctrl+C or closing the window at the review line prints "Nothing was started. You can close this window." and exits. The temp launch script is removed either way (FR-11) — no leftovers, no half-launch (AC-17).
  • Window title: "Codex · VibeCodes" (agent · board), set by the launch script, so the Mac's window list and Mission Control show which board a window belongs to — the only "label" a desktop window gets (§4 scope note).
  • Accessibility. The review is plain text in Terminal.app, read by VoiceOver like any terminal output; the key line starts with the action word ("Press Enter…") so it is found first. Colour (the amber heading, the sky action) is decoration only; the structure carries in plain text. Terminal's own font-size and contrast settings apply.
