1. Overview

The "user" of this feature is almost always an AI agent, and its "screens" are strings: a server-level instructions block, tool descriptions, JSON tool responses, and a launch prompt. The design problem is therefore a copy system, not a screen system — the same rule ("board data is live; call the tool again; never re-parse old output") must reach the agent at every moment it could go wrong, phrased consistently enough that each encounter reinforces the last (recognition over recall), and placed so that no single failure mode (truncation, context decay, a client that ignores server instructions) removes every copy of the rule.

Four text surfaces carry the rule; one JSON envelope carries freshness metadata; one nullable column plus two documented SQL queries make bypasses visible to the admin. Nothing here prevents bypass — per the Requirements non-goal, this is layered steering plus measurement.

Design principles applied to agent-facing copy:

  • One vocabulary. Every surface reuses the same two clauses: "call the tool again for current state" and "never re-read earlier output … or script-parse it". An agent that has seen any one surface recognises every other instantly (US-4).
  • Say what to do before what not to do. Each surface leads with the positive action (call again), then the prohibition. Prohibition-only copy tells an agent what's wrong without offering the correct move.
  • Redundancy by position, not repetition of bulk. Each layer is short; coverage comes from placement across the session timeline, not from any one layer being long.
  • Metadata looks like metadata. generated_at and _reminder use names and positions that cannot be mistaken for board data (underscore prefix, first/last key positions), following the existing workflow_instruction precedent in get_task.

2. How the rule reaches the agent — steering-layer flow

Chronological path of one launched session, with each layer's failure mode. No layer is a single point of failure; each later layer covers the decay of the one before it.

T0 · Terminal launch
Surface D — launch-prompt directive. One sentence riding the protected head of the compact prompt (essentialSteps) and the full prompt (mcpSetupHead) in launch-claude-code.ts.
Failure mode: deep-link truncation → mitigated: enforcePromptLength trims only the tail; the head survives verbatim (US-2).
↓
T1 · MCP handshake
Surface A — server-level instructions. One shared constant sent by both transports at session init; the client injects it into the agent's system context.
Failure modes: client ignores instructions; or a very long session pushes it out of effective attention → covered by C on every response.
↓
T2 · Tool listing
Surface B — harmonised description sentence on get_board, get_task, get_my_tasks. Read at the moment the agent chooses whether to call a tool — exactly when "just reuse the old output" is the tempting alternative.
Failure mode: descriptions summarised/compressed by the client → key clauses are short enough to survive most summarisation; A and C still cover.
↓ (repeats on every read)
T3 · Every tool response
Surface C — generated_at (first key) + _reminder (last key) stamped by the jsonResult choke point on the three board read tools. The only layer immune to context decay: it re-arrives with every read, closest to where the agent acts next.
Failure mode: a client caps huge outputs from the end → generated_at at the top still lands; A and B still cover.
Measurement (parallel, invisible to the agent): every call already logs to mcp_tool_log fire-and-forget; the additive session_id column ties calls into per-session sequences so the admin can see re-read behaviour — and its absence (US-3). See §6.

3. Copy design — the four text surfaces

The shared vocabulary, then each surface verbatim. Implementation note (for the next step, not this one): surfaces A and B should live as exported constants in one new module (suggested: mcp-server/src/steering-copy.ts) imported by both transports and by register-tools.ts, so they cannot drift — the same single-source pattern buildCompactStepPieces already uses for the launch prompt.

3a. Surface A — server-level instructions (both transports)

Proposed copy · constant SERVER_INSTRUCTIONS
VibeCodes board data is live and shared: humans and other agents change it while your session runs. Every board tool response is a snapshot stamped with generated_at — treat it as already aging. Before acting on board state (choosing, moving, or completing anything), call the tool again for current state. Never re-read an earlier response from your transcript, never save responses to files for later, and never write scripts to parse tool output — present it directly. Tool calls are cheap; stale reads cause double-claimed tasks and lost work.

5 sentences, ~560 chars. Ends on consequences ("double-claimed tasks, lost work") because agents weigh rules with stated stakes more heavily than bare imperatives. Delivery: stdio passes it in the McpServer options (index.ts); remote passes it through createMcpHandler's server options (route.ts) — one imported constant, two call sites.

3b. Surface B — harmonised tool-description sentence

Proposed copy · constant LIVE_DATA_SENTENCE (appended to all three read-tool descriptions)
Live shared data: call this tool again for current state before acting on it — never re-read an earlier response, save it for later, or script-parse this output; present it directly.

~180 chars. Appended as the final sentence of each description so the tool-specific content stays first (information scent: the description's opening still answers "what does this tool return?").

Resulting descriptions (tool-specific text unchanged except where noted):

ToolChange
get_boardIts existing sentence "Present this data directly to the user — NEVER write scripts to parse it." is replaced by LIVE_DATA_SENTENCE (which contains both clauses) — avoids saying the same thing twice in slightly different words, which reads as two different rules.
get_taskLIVE_DATA_SENTENCE appended after the existing workflow/comments guidance.
get_my_tasksLIVE_DATA_SENTENCE appended (its current description is one line; the addition roughly doubles it, which is fine — it is the shortest of the three today).

3c. Surface C — the _reminder response field

Proposed copy · constant RESPONSE_REMINDER (≤ 200 chars required)
Snapshot from generated_at; the board changes live. Call the tool again for current state — never re-read this from your transcript or script-parse it.

151 characters — within the ≤200 budget with headroom for future tweaks. Names generated_at explicitly so the two envelope fields cross-reference each other: an agent that notices either one is pointed at the other.

3d. Surface D — launch-prompt directive

Proposed copy · one sentence, identical in compact and full prompts
Board data is live and shared — always call the MCP tools again for current state; never re-read earlier output or script-parse it.

131 chars raw (~140 URL-encoded). Placement is the design: in the compact prompt it becomes a third entry in essentialSteps (the protected head assembled by buildCompactStepPieces); in the full prompts it becomes the closing line of mcpSetupHead. Both positions are preserved verbatim by enforcePromptLength, which only trims the tail (AC-2.x). Against the compact deep link's real budget (§7, discrepancy 1) ~140 encoded chars is a safe spend: the head is designed to sit well under the ceiling, and this is the shortest of the four surfaces precisely because it pays URL rent.

4. Response-shape design

Both fields are stamped at the existing jsonResult choke point (register-tools.ts:224), but opt-in per tool, not blanket: jsonResult(data, { live: true }) from the three board read handlers only. Rationale in §7 (discrepancy 3).

Placement rationale

  • generated_at is the first key — primacy. The agent reads the timestamp before the data it qualifies, so the payload arrives pre-framed as "a snapshot from this moment". It also survives clients that truncate long outputs from the end.
  • _reminder is the last key — recency. It is the final thing in the agent's context before it acts on the response, which is exactly when the "reuse old output" shortcut would otherwise be taken. The underscore prefix visually marks it as envelope metadata, not board data, and cannot collide with any current or plausible future domain field.
  • Serialisation order is reliable: JSON.stringify preserves insertion order for string keys, so { generated_at, ...data, _reminder } renders exactly as designed. If a tool's own payload ever defines generated_at, the spread lets the tool's value win (the tool knows its data better than the envelope); nothing today defines either key.

Defensive rule: the envelope is applied only when data is a plain (non-array) object — a tool that ever returns an array or primitive through the same helper passes through untouched rather than being re-wrapped into a different shape. Cost note: the envelope adds a fixed ~230 chars per response on three tools; against a typical board payload of several KB this is noise, and it is why the envelope is opt-in rather than applied to all 85 tools.

5. The launch prompt — surviving truncation

launch-claude-code.ts already has exactly the mechanism this needs: every prompt builder splits into a load-bearing head (directory step + MCP connect + record_project_path) and a trimmable tail (the work step), and enforcePromptLength guarantees the head survives any cap. The design adds no new mechanism — it places the directive inside the existing head:

  • Compact prompt (deep link / in-browser terminal, hard URL ceiling): directive appended to the essentialSteps array in buildCompactStepPieces — the array both budgeted builders already treat as untrimmable. It must not ride the tail or the optional protocol/directoryEcho blocks, which are exactly the parts dropped under pressure.
  • Full prompts (copy-command, 5,000-encoded-char cap): directive as the closing line of mcpSetupHead, which both buildBoardBootstrapPrompt and buildTaskBootstrapPrompt place in the head.
  • The only case that can lose the directive is enforcePromptLength's pathological head-trim branch, which its own doc notes never fires for real heads (~1k chars against ≥1,900 budgets). Accepted residual risk; surfaces A–C still cover such a session the moment it connects.

Per Requirements: no dashboard, no alerts. One additive migration, one line in the logger, two documented queries the admin runs in Supabase Studio / SQL editor.

6b. Documented admin queries

-- Q1 · Per-session tool mix, last 7 days.
-- Healthy sessions re-read the board throughout; a session whose board reads
-- all cluster at the start then stop, while other calls continue, is the
-- transcript-re-parsing signature.
select
  session_id,
  mode,
  min(created_at)  as session_start,
  max(created_at)  as last_call,
  count(*)         as total_calls,
  count(*) filter (where tool_name in ('get_board','get_task','get_my_tasks'))
                   as board_reads,
  max(created_at) filter (where tool_name in ('get_board','get_task','get_my_tasks'))
                   as last_board_read
from mcp_tool_log
where session_id is not null
  and created_at > now() - interval '7 days'
group by session_id, mode
order by session_start desc;
-- Q2 · Stale-acting mutations: board writes made > 10 minutes after the
-- session's most recent board read (or with no prior read at all).
-- These are the moments the steering failed — the direct US-3 measure.
with calls as (
  select
    session_id, tool_name, created_at,
    max(created_at) filter (where tool_name in ('get_board','get_task','get_my_tasks'))
      over (partition by session_id order by created_at
            rows between unbounded preceding and 1 preceding) as last_board_read
  from mcp_tool_log
  where session_id is not null
    and created_at > now() - interval '7 days'
)
select session_id, tool_name, created_at,
       created_at - last_board_read as read_staleness
from calls
where tool_name in ('move_task','update_task','complete_step',
                    'claim_next_step','fail_step','approve_step')
  and (last_board_read is null
       or created_at - last_board_read > interval '10 minutes')
order by created_at desc;

The 10-minute threshold is a starting heuristic, tuned by the admin in the query text itself — deliberately not a config value, since the query is the whole UI. Home for these snippets: a short "Measuring MCP usage" section in the admin-facing docs alongside the existing MCP notes (exact page decided at implementation; the queries above are the deliverable).

7. Edge cases and discrepancies

7a. Discrepancies with the Requirements doc (called out explicitly)

1 · Deep-link cap is 1,900, not 2,048. Requirements cites a 2,048-char deep-link cap. The code's actual constants (launch-claude-code.ts): MAX_DEEP_LINK_URL_LENGTH = 1900 — a full-URL ceiling kept under the strictest OS limit (Windows ShellExecute ≈ 2,083) — and MAX_DEEP_LINK_PROMPT_LENGTH = 5000 (encoded prompt, copy-command path). This design budgets against the real 1,900 figure. No requirement is affected: the directive is head-protected either way.

2 · stdio "sessions" are really installs. index.ts sets a static STDIO_SESSION_ID = stdio:<bot_user_id> for the process's whole life — and it is the same string across restarts of the same install. Per-session analysis (US-3) is therefore precise on the remote transport (per-connection JWT session claim) but degrades to per-install granularity on stdio. Q1's mode column makes the difference visible; fixing stdio granularity (e.g. a per-process random suffix) is a one-line option the Engineering step may take, but it is not assumed by this design.

3 · "via the jsonResult choke point" is narrowed to opt-in. Requirements phrases layer 2 as flowing through the shared jsonResult helper. That helper serialises all 85 tools. Stamping everything would put a board-freshness reminder on unrelated responses (idea enhancement prompts, uploads, OAuth-adjacent flows) — noise that erodes the reminder's credibility and pays token rent everywhere. The design keeps the choke point (one implementation site) but gates it: jsonResult(data, { live: true }) from exactly get_board, get_task, get_my_tasks. If Requirements intended blanket stamping, this is a deliberate deviation and should be settled at Design Review.

9. Out of scope (reaffirmed from Requirements)

No detection dashboards or alerts; no client-side enforcement; no TTL/expiry semantics on generated_at (it is information, not a lease); no terminal-relay changes; no scrubbing of step-output context; no edits to users' repos. Guaranteed prevention remains a non-goal — the measure of success is that every path an agent takes carries the rule, and every bypass leaves a queryable trace.
