Agent Compliance Alerts — UX Design

Task e47a2d48 · step 2 of 6 · builds on Requirements (step 1). Next step is your review gate.

The gist: today, when a workflow step runs on the wrong model or ignores its assigned persona, it's recorded silently — you only see it if you open that step's dialog. This adds a bell notification to you (the idea owner) the moment a violation is recorded, plus a settings toggle to turn it off. Two thin UI touches; the rest is server-side in the MCP tools.

1 · What you'll see

A new notification lands in your bell's Mine tab, with a shield icon marking it as a compliance alert (not colour alone — the shield + wording both carry the meaning). Clicking it opens the board with that task, where the step dialog shows exactly what went wrong.

Key trade-off, up front. The notifications table stores only references (idea, task) — no free-text column, and it doesn't even load the step title or model names. So the bell line is one generic sentence; the precise "haiku instead of opus" detail lives in the step dialog you land on after clicking. We keep the specifics exactly where the data already exists, and avoid a schema change to carry text on every notification row. (Alternative — adding a JSON column to notifications — rejected: too much machinery for one feature.)

Why the actor is an agent, not a person. The row's avatar is the agent that completed the step (the "actor"), so at a glance you see which agent misbehaved — the shield badge over the avatar signals it's a system compliance alert, not a normal person-driven notification. The wording reads correctly with an agent name in the lead slot.

2 · Server flow

The check runs in both completeStep and failStep in mcp-server/src/tools/workflows.ts (so it covers stdio and remote MCP modes), placed right after updateFields is written — beside the existing tierHonored === false branch that already auto-posts a step comment. The freshly computed tierHonored / personaHonored locals are already in scope; no recomputation.

The one extra lookup

The step row already carries idea_id and task_id, but not the idea owner or their prefs (and the step title isn't loaded — fine, generic copy doesn't need it). So one new query fetches owner + preferences by idea_id:

const { data: idea } = await ctx.supabase
  .from("ideas")
  .select("author_id, author:users!ideas_author_id_fkey(notification_preferences)")
  .eq("id", step.idea_id)
  .maybeSingle();

Gate + insert (fire-and-forget)

// only explicit violations — nulls (old clients) never alert
const violated = tierHonored === false || personaHonored === false;
const prefs = idea?.author?.notification_preferences;
const enabled = prefs?.compliance_alerts !== false;   // absent key = ON
const ownerId = idea?.author_id;

if (violated && enabled && ownerId && ownerId !== ctx.userId) {
  const { error } = await ctx.supabase.from("notifications").insert({
    user_id: ownerId,
    actor_id: ctx.userId,          // the agent that completed the step
    type: "step_compliance",
    idea_id: step.idea_id,
    task_id: step.task_id,
  });
  if (error) logger.error("compliance alert insert failed", { error: error.message, stepId: params.step_id });
}

Mirrors mention-notify.ts exactly: never throws, logger.error on failure, one lookup + one insert. It runs strictly after the successful step update, so a failed insert can never fail or delay the completion. Deep-link is produced at render time by the existing buildNotificationUrl (task_id present → /ideas/{id}/board?taskId={taskId}) — zero routing change.

Notification body: rendered, not stored. Like task_mention, the bell builds copy client-side keyed on type (add step_compliance to iconMap → ShieldAlert and messageMap → the generic sentence). Nothing extra is written to the row. The precise model/persona detail is read live from the step's attestation fields in the dialog.

3 · Migration

One new file, supabase/migrations/00143_step_compliance_notification_type.sql (next free number after 00142_step_persona_attestation.sql):

-- Add 'step_compliance' to the notification_type enum
ALTER TYPE notification_type ADD VALUE IF NOT EXISTS 'step_compliance';
Keep this file to the single statement — no other DDL. Postgres can't run ALTER TYPE … ADD VALUE inside a transaction block on older versions. Precedent migrations 00026 (task_mention) and 00053 (comment_mention) run it bare, no BEGIN/COMMIT. Follow that: don't mix a transactional statement into this migration.

Also update the type union on the notifications Row/Insert/Update in src/types/database.ts (manually maintained). The preference compliance_alerts is jsonb — no column migration; new users get ON via the absent-key default at read time. Optionally add "compliance_alerts": true to the users default jsonb for tidiness (see open question 2) — not required for correctness.
