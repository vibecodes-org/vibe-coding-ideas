Terminal chooser — board-first grouping (rework v2)

Design step for task e967c4fc · REWORK of the rejected liveness-first design · builds on Requirements v2 · 2026-09-01
Nick's rejection of v1: board affiliation must be the PRIMARY grouping for the whole chooser — all of this board's sessions (running and recent) before anything from another board.
Next step: human Design Review gate. Nothing here is built yet.

1 · Design decision in one paragraph

The whole chooser now sorts by board first, liveness second. Everything belonging to the board you're on — sessions still running and sessions that ended in the last 48 hours — sits above anything from another board. Four sections, in this fixed order: Running now — this board → Recent — this board → Running now — other boards → Recent — other boards. Every heading is the same shipped ChooserSection text treatment (no colour-only separation); empty sections render nothing. Rows, per-row actions (Reconnect / Open board & reconnect / Resume), the takeover warning, rename, dedupe, the 48h window, the 10-row recent cap, and the Start-new block are all unchanged — the visible diff is section order plus one new heading string.

Board wins over liveness — that is the point of the rework. Amber “NEW” tags and the dashed sky “initial focus” marker are annotation only — not part of the UI.

3 · ⚠ Flagged for review: the initial-focus rule vs. the new order

This is a real visual/behavioural quirk we are shipping knowingly — please read before approving.

The shipped focus rule is unchanged in v1 (a Requirements v2 decision, not an oversight): when the chooser opens, keyboard focus lands on the first live session's action — prioritising a row badged “was open in this tab”, wherever it is. A task-scoped open still focuses the “already running for this task” banner first, and with no live rows at all, focus falls to “Start new session”.

Under the old order that focused row was always at or near the top. Under the new order, a live session on another board now renders in section 3 — below “Recent — this board”. So when your only live session is elsewhere (Fig. 2), focus lands mid-list while the eye naturally lands on this board's recent sessions at the top. Pressing Enter immediately reconnects the elsewhere session — correct per the rule, but no longer where the user is looking. On a tall chooser the browser may also auto-scroll to bring the focused row into view, skipping the reader past the top sections.

Requirements v2 decided: keep the current focus targets for v1 — don't invent a new focus rule as part of a reordering card. If field use shows people Enter-ing into the wrong session, a follow-up card can revisit the rule (e.g. “focus the first row of the first rendered section”); that is deliberately NOT designed here.

  • Text, not colour: section membership is carried by the visible heading string, exactly as the live split does today. Nothing added depends on hue alone (WCAG-safe, matches the existing constraint).
  • The “ended in the last 48h” qualifier stays on both Recent headings (Requirements v2 decision — it explains why an older session has vanished, which matters more now that “Recent — this board” sits in the prime slot 2 position). It rides after a mid-dot so the scannable part — Recent — this board — still leads, mirroring the “Running now — …” shape (Gestalt similarity: the 2×2 of “Running now / Recent” × “this board / other boards” parses at a glance once either axis is learned).
  • Board name on other-board rows: unchanged, already satisfied by the existing chip/dedupe logic — named rows show the muted idea-title chip (“Menu importer spike Recipe Roulette”), and fallback-named rows carry the board name inside the label (“Band Practice Log · c7aa”), where isFallbackSessionName correctly suppresses the redundant chip.

5 · Empty-state behaviour under the new order

Same rule as shipped: an empty section renders nothing — no heading, no divider, no placeholder. The case that matters most under the new order is slot 2 going empty: “Running now — this board” is then followed directly by “Running now — other boards”, with no gap and no “nothing recent here” filler. The chooser never manufactures blank space to preserve the four-slot rhythm.

Emptiness is judged on the display-filtered rows (after visibleRecentRows drops null-folder rows), matching how the single Recent section decides to show itself today — a subsection whose only rows are unresumable renders nothing.

Accepted v1 limitation, now more visible: the 10-row recent cap and dedupe apply before the board split. A busy day on other boards can therefore leave “Recent — this board” empty (Fig. 3's shape) even though this board had older ended sessions — the cap ate them. Under the old order that gap hid in slot 3/4; now it is slot 2, right under the live rows, where its absence is noticeable. Requirements v2 accepts this for v1; a per-board cap or reserve is a possible follow-up, deliberately not designed here.

6 · What implements this (for the build step)

  • src/lib/terminal/chooser-data.ts — ChooserSections gains two NEW fields, recentHere and recentElsewhere (partitioned by row.ideaId === currentIdeaId, preserving the newest-ended-first order), alongside the existing recent field, which stays exactly as derived today. Additive on purpose: every existing consumer of recent (findTaskSessionMatch, chooserHeaderCounts, entry-decision.ts's underlying invariants) is untouched. All existing rules — 48h window, RECENT_MAX=10, dedupe, null-cwd handling, machine-identity filtering — apply before the split, unchanged.
  • src/components/board/terminal-session-chooser.tsx — the render becomes four conditional ChooserSection blocks in the new order: liveHere → visibleRecentRows(recentHere) → liveElsewhere → visibleRecentRows(recentElsewhere). LiveRow/RecentRow, actions, confirms, rename, takeover copy, and the focus refs (firstFocusRef/wasOpenSid wiring) are all unchanged — the elsewhere live rows simply render later in the document.
  • Focus rule — no code change (see §3). The only behavioural difference is positional: the same button that gets focus today can now be further down the page.

7 · Fidelity + accessibility check

  • Mock colours/spacing are the app's shipped zinc/sky/emerald/amber tokens lifted from the component's own classes (#111114 section bars, zinc-800 hairlines, sky reconnect / emerald resume buttons) — dark theme, matching the dock.
  • Headings are real text in the DOM (screen-reader visible), not colour or spacing alone; the reorder adds no new interactive elements, so tab order simply follows the new visual order — with the one focus caveat flagged in §3.
  • Heading contrast: zinc-500 on #111114 is the existing shipped treatment; the two new headings are no worse than the two approved ones, and row/action text stays zinc-100 on near-black at well over 4.5:1.
  • 375px: rows already wrap their title/chip cluster (flex-wrap) and truncate the mono identity line; the longer Recent headings (“· ended in the last 48h”) remain single short strings at 10.5px and fit a 375px panel without wrapping.
