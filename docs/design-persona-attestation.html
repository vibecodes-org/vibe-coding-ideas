Persona Embed + Attestation

Ship the assigned agent's persona inside claim_next_step so the orchestrator never has to fetch it, and let it self-report whether it actually used it. This doc leads with the change as you'd live it in a Claude Code session — the same "pick up the next task" flow, before and after. Specs are in the appendices.

When it returns, YOU (the orchestrator) call complete_step with this step's id, the claim_token, the subagent's deliverable as output, and persona_used — "verbatim" if the subagent ran on persona_prompt unchanged, "adapted" if you edited/trimmed/merged it, "none" if you didn't use it. Report honestly: it is recorded as an adherence signal, not verified, and never blocks completion.

Note the shape: this is a rewrite of two existing numbered steps, not an append — net length is roughly flat because the deleted get_agent_prompt sentence is replaced, not stacked on. The separate modelTierClause (which asks for model_used), the claim-token block, the skills block, and the fallback path for unassigned / prompt-less bots are all untouched. Both self-reported signals — model_used and the new persona_used — land on the same complete_step call.

3Guaranteed to Work the Old Way

Nothing an existing client does breaks. Each row below names the mechanism that guarantees it — and what would have to break for it to fail. In every case the answer is "a schema-level invariant would have to break," i.e. nothing this change touches.

Old behaviourStill works because…What would have to break
Old client ignores the 3 new response fields The fields are additive keys on a JSON object. MCP clients read the keys they know and ignore the rest by construction — an unknown key is invisible to a consumer that doesn't reference it. JSON would have to stop being additive — impossible.
Old orchestrator still fetches the prompt itself get_agent_prompt is not removed. A client running its cached old instruction calls it and gets the same system_prompt back exactly as today. The embed is a shortcut, not a replacement. We'd have to delete the tool — we don't.
Old complete_step / fail_step calls stay valid persona_used is .optional() in the zod schema. Omit it → resolver returns {null, null} → both columns write NULL. The call succeeds identically. The field would have to be required — it isn't.
Legacy steps look identical in the UI StepPersonaLine opens with if (step.persona_honored == null) return null;. Every pre-change step has NULL there, so it renders no row — not a warning, not an empty state. The guard clause would have to be removed — it's the first line.
Unassigned / Auto steps byte-identical The bot_id === null branch is untouched: no persona fields emitted, instruction stays today's pick-then-get_agent_prompt fallback. personaEmbeddable gates the whole block off. The fallback branch would have to be edited — this change doesn't edit it.

The guarantee isn't "we tested it and it seemed fine." It's structural: additive JSON, an optional param, a NULL-guarded render, and an untouched fallback branch. For any old behaviour to break, one of those four invariants would have to change — and none of them is on the change list.

A4. resolvePersonaAdherence() — pure, beside resolveTierAdherence (:~137)

export type PersonaAdherenceResult = { personaUsed: string | null; personaHonored: boolean | null };

export function resolvePersonaAdherence(
  personaUsed: "verbatim" | "adapted" | "none" | undefined
): PersonaAdherenceResult {
  if (personaUsed === undefined) return { personaUsed: null, personaHonored: null };
  return { personaUsed, personaHonored: personaUsed === "verbatim" };
}

Gating is simpler than the Execution row: because persona_honored is set only on complete/fail, that one null-check already hides in-flight steps, unreported completions, and every legacy row. No model_tier equivalent to check.

DOut of Scope (Phase II boundary)

  • No hash / no prompt verification. VibeCodes never inspects the spawned subagent's actual system prompt. persona_used is self-reported telemetry, exactly like model_used. (The hash-based verification idea is deferred — task 758b784b.)
  • No enforcement. An "adapted" or "none" report never blocks complete_step, never fails the step, never posts an auto-comment. It only lights up the amber UI row.
  • Fallback path stays silent. The unassigned / prompt-less branch is untouched and does not ask for persona_used, so those steps land at NULL. Adding adherence coverage there is a Phase II option, not this change.
