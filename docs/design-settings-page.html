UX Design: Dedicated Settings Area

Wireframes, interaction flows, and principle validation for moving profile-page settings to /settings

Task: Move profile page settings into a dedicated Settings area Step: UX Design (builds on the Requirements step) Date: 24 Aug 2026

1. Design summary

The Requirements step identified the core problem: "profile page crams 7 settings controls + a Manage-agents link into one packed button row under the stats — hard to scan, no context per item, mixes identity content with app configuration." This design resolves it with a dedicated, protected /settings page using the industry-standard settings-row list pattern: a single vertical column of rows, each with an icon, a title, a one-line description, and the existing, unchanged control on the right.

Crucially, this is a relocation, not a redesign: every dialog, form, and save path behaves exactly as it did on the profile page — per the Requirements constraint "Each row's control behaves exactly as today (same dialogs, same save logic — no functional changes)". Only the entry point changes.

2. User flows

Flow A — Primary: navbar to a saved setting

Avatar in navbarDesktop dropdown or mobile slide-out menu
→
New "Settings" itemGear icon, below Profile / Members
→
New /settings page8 labeled rows, protected route
→
Unchanged Row's controlExisting dialog opens (e.g. Notifications)
→
Unchanged SaveSame save logic → toast confirmation

Everything from "dialog opens" onward is byte-for-byte the pre-existing experience. The user gains one navigational step but loses the scanning cost of an unlabeled icon-button row — a good trade (analyzed under Hick's Law below).

Flow B — From the profile page

Own profile pageIdentity, stats, ideas — content unchanged
→
New "Settings" buttonSingle small outline button with gear icon; owner-only
→
/settings pageSame destination as Flow A

Visitors viewing someone else's profile never see the button. Owners who habitually went to their profile to change a setting have a one-click bridge, so the old habit still works (recognition over recall — the muscle memory path degrades gracefully rather than dead-ending).

Flow C — Signed-out visitor

Direct visit to /settingsBookmark, shared link, stale tab
→
Redirect to /loginMiddleware protected-path list
→
Sign in → back in appStandard auth flow

Error and edge states

  • Settings fetch fails / no row: the page still renders; the five rows that need the user's saved values are simply omitted, while MCP API Keys, GitHub, and Manage agents (which fetch their own state) always render. Not a blank screen. Improvement noted in §5: a visible partial-state message would be better than silent omission.
  • Dialog-level errors: unchanged from today — each existing component keeps its own error handling and toast.error() behavior.
  • Back navigation: closing a dialog returns to the settings list with scroll position intact (dialogs overlay the page; no navigation occurs). Browser Back from /settings returns wherever the user came from — navbar or profile.

4. Validation against UX principles

PrincipleHow this design satisfies it
Hick's LawThe old packed row forced users to decode 7 near-identical unlabeled buttons at once. The new list keeps the same 8 choices but each carries a title and a description, so users scan labels top-to-bottom instead of hovering to discover meaning. Decision cost drops even though the option count is unchanged — the choices became self-describing.
Gestalt (Proximity / Similarity / Continuity)Each row's border groups icon + text + control as one unit (proximity/closure). All rows share identical anatomy (similarity → "these are all settings"). The single vertical column gives one continuous scan path. Separating settings from identity content on the profile page fixes the original category mixing.
Fitts's LawRow controls are real buttons at comfortable size with p-4 row padding; the link row is full-width tappable, far exceeding 44px height on mobile. Nothing destructive sits adjacent to a primary action at this level (destructive actions like key deletion remain inside their dialogs, behind confirmation, exactly as before).
Jakob's LawNavbar avatar menu → "Settings" → vertical list of icon+title+description rows is precisely the pattern of GitHub, Linear, Notion, and Slack. Zero novel interaction to learn; the innovation is in removing friction, not inventing patterns.
Information scentEvery row states what it controls in plain words ("Bring your own Anthropic key, or use platform credits"), replacing icon-only guesswork. Buttons open in place; the chevron-link visibly navigates. The dropdown item is labeled "Settings" with a gear — universally understood destination.
Recognition over recallDescriptions restate each setting's purpose at the point of choice, so users needn't remember which icon did what. The profile-page Settings button preserves the old habitual route.
Accessibility (WCAG 2.1 AA)Every control is a genuine <button> or <Link> — keyboard reachable in a logical top-to-bottom tab order, no hover-only actions (the link's hover tint is decorative, not gating). Titles are visible text, not placeholders or tooltips. shadcn/ui zinc dark theme tokens meet contrast targets (foreground on background well above 4.5:1; muted description text used only at ≥ small-text sizes). Meaning is never carried by color alone — icons pair with text labels everywhere. Dialogs are the existing shadcn/Radix dialogs with focus trapping and Escape-to-close.
All states handledEmpty/error: rows depending on the user's saved values degrade by omission (see improvement E below); loading: server component — page arrives rendered, no client spinner; success: unchanged per-dialog toasts. Signed-out: middleware redirect, never a broken page.
Mobile (375px)Single column, rows compress naturally (description wraps, icon and button are shrink-0), no horizontal overflow. The old mobile-only settings dropdown (ProfileSettingsMenu) is deleted — one responsive page replaces two divergent mobile/desktop presentations, reducing maintenance and inconsistency risk.

5. UX concerns & follow-up recommendations

A. Does "Profile" belong in Settings? (honest trade-off)

Identity editing (name, avatar, bio) is arguably profile-page content, not app configuration — Requirements even framed the problem as "mixes identity content with app configuration". Keeping the Edit Profile row in /settings partially re-mixes them. However, Jakob's Law favors the current choice: GitHub, Notion, and Linear all put profile editing under Settings, and users hunting for "change my avatar" overwhelmingly open Settings first. Recommendation: keep the row here, and optionally also surface an Edit Profile affordance on the owner's own profile page later (both entry points, one dialog). Not a blocker.

B. Group rows under headings when the list grows

Eight rows is fine flat. At ~10+, add section headings — e.g. Account (Profile, Notifications), Workspace (Board Defaults, Manage agents), AI & Integrations (AI API Key, Model Tiers, MCP API Keys, GitHub). The row component already supports this with zero structural change. Defer until needed (out of scope now, per Requirements).

C. Row-click target vs button-click target inconsistency

The "Manage agents" row is clickable across its whole width, but the other rows only respond on their right-side button. On mobile especially, users will tap the row body of "Notifications" and get nothing. Follow-up: make each dialog row's full surface trigger its dialog (keeping the button as the visible affordance and accessible name). Small change, meaningful Fitts's Law win.

D. Button label vs row title redundancy

Some existing trigger buttons carry their own labels (unchanged by design), which can read redundantly next to the row title ("Notifications … [Notifications]"). Acceptable cost of the reuse-as-is constraint; if concern C is adopted, trigger buttons could later be normalized to a uniform "Open"/"Manage" or icon-only-with-aria form. Explicitly out of scope now.

E. Silent partial state

If the settings fetch fails, five rows silently vanish rather than showing a "Couldn't load some settings — refresh to retry" notice. Rare (authenticated fetch of own row), but per the handle-all-states rule a visible partial-state message is the better behavior. Low-priority follow-up.

F. Verify dialog focus return

QA note for the verification step: after closing each dialog via Escape, focus should return to the triggering row button (Radix default — expected to pass, worth a keyboard walkthrough of all 7 dialogs on the new page).
