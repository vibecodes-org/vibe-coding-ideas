Terminal Scrollback Transfer

UX / mechanism design · card 35cffc10 · builds on the multi-session pop-out design (D1–D7) and the host-mounted dock fix (PR #143)

When a terminal session moves between the dock and a popped-out window, its on-screen history must move with it — in both directions, over the existing same-origin BroadcastChannel hand-off, inside the existing ~5s handshake budget. This is mostly message sequencing with one small UI change (a mislabelled pill).

What changed since Requirements — and why it reshapes this design
The host-mounted fix (PR #143) keeps the dock's terminal alive but hidden while a session is popped out. So on bring-back the dock already shows its full pre-pop-out history instantly. The remaining gaps are exactly two: the popped window starts empty at pop-out, and the dock is missing only the slice produced while the session lived in the popped window. Both are closed below. This also retires the “Showing output from pop-out onward” notice banner in the popped window (design §10a said it disappears once real scrollback transfer ships — that is this card).

1Protocol additions

Everything rides the existing per-pop-out BroadcastChannel (nonce-named, same origin — no new transport, no server involvement). The message set grows from three to five, and one existing message gains a field:

MessageDirectionChangePurpose
readypopped → dockunchanged Announce + retry every ~300ms until payload lands (existing hardening).
payloaddock → popped+ optional buffer field Credentials as today, plus buffer: { data, truncated } — the dock's serialized scrollback, captured fresh inside getPayload() at each send so it's as current as possible.
bring-back-requestdock → poppednew “I'm about to reattach — send me your buffer first.”
buffer-replypopped → docknew { buffer: { data, truncated } } — the popped window's full serialized scrollback (pre-pop-out history it was handed plus the popped-out slice).
closedpopped → dockunchanged shape Still the auto-reattach signal. On real window close it is now preceded by a buffer-reply on the same channel (BroadcastChannel preserves per-sender order).
Decision: buffer rides inside payload, not as a sibling message (pop-out direction)
A separate “buffer” message would reintroduce the exact failure class the handshake rework just eliminated: two coupled messages where either half can be the one that got lost, with per-half recovery logic. Embedding it in payload inherits the idempotent ready/re-send hardening for free — retries stop the moment the payload lands, so in practice the ~1 MB clone happens once or twice, well within budget. The field is optional and leniently parsed: a malformed buffer is dropped with a console warning while the credentials still go through — scrollback is never allowed to sink a hand-off. (Optional also keeps deploy-skew graceful: an older popped window simply ignores the field.)

4Flow C — bring-back via window close (buffer, then closed)

The popped window also triggers bring-back by simply being closed. There is no time for a request/reply round-trip inside pagehide — so the window pushes its buffer unprompted, immediately before its existing closed signal. BroadcastChannel guarantees per-sender ordering, so the reply always lands first.

5The three design decisions

D1 — Bring-back REPLACES the dock's buffer with the popped window's (chosen) vs. keep-and-gap (rejected)
Because Flow A hands the full history over at pop-out, the popped window's buffer is always a superset of the dock's: everything the dock has, plus the popped-out slice. Wholesale replace (reset the hidden terminal, write the reply) therefore guarantees completeness with the simplest possible mental model — “the terminal you see is the terminal that comes back.”

Rejected — keep dock's buffer, append nothing: leaves a permanent hole where the popped-out work happened; explicitly rejected by Nick (“sort this out”). It survives only as the timeout fallback, where it is honest and strictly better than hanging. Also rejected — compute and append just the popped-out slice: the relay stream carries no sequence numbers or markers for “where pop-out began”, so a reliable diff isn't computable; a heuristic splice risks duplicated or interleaved lines, which reads far worse than either clean outcome.
D2 — Size cap: 1 MiB per transfer, oldest-first truncation, one dim marker line
Serialized payload is capped at 1 MiB (1,048,576 bytes of serialized data). Rationale: xterm's scrollback is already capped at 5,000 lines, which serializes well under 1 MiB in normal use (heavy full-width ANSI output is the only way near it); a 1 MiB structured clone posts in single-digit milliseconds, keeping both the 5s pop-out budget and the 500ms bring-back reply budget safe, and keeping the pagehide path fast.

Truncation is oldest-first by whole rows, never by bytes: if a full serialize exceeds the cap, the serialize addon is re-run with a smaller scrollback row count (halving until under cap). Slicing the serialized string at a byte offset was rejected — it can cut mid-escape-sequence and corrupt every line rendered after the cut.

Marker copy (exact): when truncated is true, restore writes one dim line at the very top of the buffer before the payload:
— older history trimmed during hand-off —
✓ Ran npm run build (exit 0)
✓ 214 tests passed
› Working on src/actions/ai.ts…
Rendered dim via SGR (\x1b[2m…\x1b[0m) — style is secondary; the em-dash-framed sentence carries the meaning on its own (never colour alone, WCAG 1.4.1). Rejected — no cap: an unbounded clone re-sent on every payload retry, and unbounded serialize work inside pagehide, are exactly the two places this feature could regress the handshake it rides on.
D3 — Bring-back reply timeout: 500ms, falling back to the dock's own buffer
A live popped window answers a BroadcastChannel round-trip in low single-digit milliseconds; 500ms (the midpoint of the 400–600ms band) covers a busy/GC-pausing window with two orders of magnitude of headroom while keeping the button feeling instant — the dock shows its normal “Connecting…” treatment during the wait, no new intermediate state. The fallback (keep own buffer, reconnect) is deliberately the pre-this-card status quo: complete history except the popped-out slice, fully usable session. Rejected — 2s+ “to be safe”: the only scenario a longer wait rescues is a window that is alive but seconds-frozen, vanishingly rare against making every bring-back on an already-closed window feel broken for 2 seconds. Rejected — wait indefinitely: a closed-without-signal window (crashed tab, killed process) would hang bring-back forever.

6Pill fix — the popped window's “brought back” state

When the dock reattaches, the popped window's own leg closes with 4001 and the view shows the calm “Brought back to the dock” overlay — but the header pill still renders from dockStatusMeta("error"): a rose “Error” pill floating above copy that says everything is fine. 7Reusable module boundary

All serialize/restore mechanics live in one new pure module, src/lib/terminal/scrollback-transfer.ts, with the transport kept entirely outside it — the reload-reattach card reuses these functions verbatim with a different transport (e.g. sessionStorage) and a different trigger:

ExportContract
TransferredBuffer { data: string; truncated: boolean } — the only shape that crosses any transport.
serializeScrollback(term, capBytes) → TransferredBuffer. Wraps @xterm/addon-serialize (new dependency); enforces the cap by re-serializing with halved scrollback row counts (oldest-first, whole rows). Never throws — returns { data: "", truncated: false } on internal failure.
restoreScrollback(term, buffer) Resets the terminal (full reset, not clear() — scrollback must actually empty), writes the dim truncation marker when truncated, then writes data. Safe on an empty buffer (no-op beyond the reset).

Both are pure with respect to everything but the passed terminal, so they unit-test against a stub terminal the same way popout-channel.ts tests against a stub channel. The hook surface: useTerminalSession's attachExisting gains an optional initialBuffer (restored after terminal open, before socket attach), and exposes a serializeNow() action for the dock and popped window to call.

8Edge cases

#ScenarioBehaviour
E1 Popped window already closed (or frozen) when “Bring back” is clicked No buffer-reply arrives; 500ms timer fires; dock keeps its own buffer and reconnects. Worst case = pre-this-card behaviour. If the window closed cleanly moments earlier, its pagehide buffer-reply/closed usually landed first and Flow C already completed — the button click then finds no channel entry and is a no-op.
E2 Both paths race: user clicks “Bring back” while the popped window is closing First completed path wins. Restore + reconnect + teardown run once; teardown deletes the channel entry, and every later message on that channel is dropped by the existing getEntry() → undefined guard. A double restore is impossible because restore only ever runs while the entry still exists.
E3 Buffer over the 1 MiB cap Oldest rows dropped at serialize time (halved row counts until under cap); truncated: true rides with the data; restore writes the dim “— older history trimmed during hand-off —” line at the top. Applies identically in both directions.
E4 Serialize throws (or is slow) inside pagehide serializeScrollback never throws by contract; if it returns empty/failed, the handler skips the buffer-reply and posts closed alone — the dock reconnects keeping its own buffer. Work is bounded: one synchronous serialize of a ≤5,000-line buffer (~ms) — no loops, no awaits, no allocation beyond the output string.
E5 Second pop-out immediately after a bring-back Clean by construction: each pop-out mints a fresh nonce + channel, and the dock serializes fresh at payload-send time — so the new window receives the just-restored complete buffer, including the previous popped-out slice. No state survives from the previous pop-out's channel (it was fully torn down).
E6 Output races the hand-off (either direction) Pop-out: lines arriving between the dock's serialize and the 4001 preempt miss the handed buffer (bounded to one round-trip; the dock's fresh-serialize-per-send minimises it). Bring-back: lines arriving after the popped window's serialize but before its preempt miss the reply the same way. Accepted as invisible-in-practice; fixing it needs relay-side sequencing, which is out of scope.
E7 Deploy skew: one side predates this card Old popped window ignores the payload.buffer field and bring-back-request (unknown-type warn, already in the parser) → dock's 500ms fallback covers bring-back; pop-out shows the old empty-scrollback behaviour with its notice banner. Old dock ignores buffer-reply the same way. Nothing breaks; everything degrades to today's behaviour.

9Out of scope

Explicitly not this card
  • Server/relay-side scrollback persistence — no buffering at the relay, no replay-on-attach, no sequence numbers (would also be the only real fix for E6).
  • Reload-reattach transport — that card reuses serializeScrollback/restoreScrollback with its own storage + trigger; nothing here binds to it beyond the module boundary in §7.
  • Raising the 5,000-line scrollback limit or making the cap user-configurable.
  • Cross-browser / cross-device hand-off — BroadcastChannel is same-origin, same-browser-profile by definition; unchanged.
