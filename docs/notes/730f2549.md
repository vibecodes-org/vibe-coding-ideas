# Card 730f2549: usage command refused in a worktree

Root cause (from the card's evidence plus the code, not reproduced in a live worktree): the short usage command
(`stepUsageShortCommand`, src/lib/step-cost/usage-command.ts) is a compound line (variable assignments, `[ -s ]`,
`ls | head` in `$(...)`, `if/then/else`, then `sh "$f"`). Claude Code's safety check in an isolated worktree refuses
`sh` run inside such a construct. The script itself is fine (the same script ran fine as one plain command).

Decisions:
- First-choice `usage_command` (short mode, STEP_USAGE_SHORT_COMMAND on) is now one plain command:
  `sh ~/.claude/vibecodes/step-usage-<hash>.sh <marker> 'AGENT_ID'` (`stepUsagePlainCommand`). The server cannot see
  the machine's home folder, so the path starts with `~`. A non-default CLAUDE_CONFIG_DIR is not honoured by it.
- The old wrapper is kept as `usage_command_if_script_missing` (same marker) so a machine with no saved script
  still gets the "NO_TRANSCRIPT no-script" -> full command route. Only sent in short mode (long mode unchanged).
- Tool descriptions now say: a refused command is not "could not run"; retry as one plain command, and tell the person
  if usage_unavailable is used.
- Not done: board flag for runs with many usage_unavailable steps; rebuild of lost figures (scripts/step-usage-backfill.mjs
  exists for rebuilding from saved transcripts; helper transcripts only if still on disk).
- Impact count could not be run: the Supabase read-only query tool was permission-denied in this session.
  Query to run: select kind, count(*), count(distinct idea_id) from workflow_step_unmeasured group by kind.
- Long (default) mode is untouched; it is also a compound `( ... )` command and might be refused the same way, unverified.

## Stage 2 (9 Nov 2026)

- Gap: a session open in a worktree when the script changes (new hash) lacks the file named in `usage_command`, and the only fallback was the compound wrapper a worktree refuses. Added a middle step, `usage_command_newest_script`: `ls -t ~/.claude/vibecodes/step-usage-*.sh | head -n 1 | xargs -I{} sh {} <marker> 'AGENT_ID'`. Plain commands joined by pipes, no variable, test, substitution or if. A bare glob was rejected: old scripts pile up in that folder (the helper never prunes), so a glob would pass several files to `sh` and shift the arguments.
- Order now: `usage_command` -> `usage_command_newest_script` -> `usage_command_if_script_missing` (wrapper, still hands back the full command). With no saved script at all the newest-script command prints only ls's error and runs nothing, so the session moves on.
- Not proven: Claude Code's real safety check was not run against the pipe form (no way to run it here). The test pins "no variable/test/substitution/list/if". Watch the next worktree session.
- Wording: the "only if the command can't run" text in the complete_step and fail_step tool descriptions, and the missing-usage refusal in step-usage.ts, now say what Stage 1 says: retry a refused command plain, tell the person if usage_unavailable is used.
- CLAUDE_CONFIG_DIR: decided NOT to honour it in the plain forms. The server cannot see the machine's config folder; reading `$CLAUDE_CONFIG_DIR` in the command adds a variable (the kind of construct that got the wrapper refused). Nick uses the default folder. Someone with a custom folder falls through to the wrapper, which honours it. Revisit if that ever matters.
- Left alone: the inline-run line in claim-instruction.ts ("run usage_command as is, or pass usage_unavailable + why"), which is short and pinned by existing tests.
