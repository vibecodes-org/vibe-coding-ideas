# 1117ac6b - steps on board d650f96a with no cost recorded

Status: investigated, cause NOT pinned. No product change made. Escalated.

## What the data shows (read-only queries, 28 Oct 2026)
- Since 26 Oct 00:00, 56 of 156 completed steps on board d650f96a have no workflow_step_usage row.
- It is not spread evenly. It is whole cards, decided when the card's steps were CLAIMED:
  - Until 26 Oct ~08:59 UTC: every step has usage.
  - 26 Oct 09:00 to 27 Oct ~14:40 UTC: no step has usage (cards show as all-missing).
  - From 27 Oct ~14:45 UTC: every newly claimed step has usage again.
  - Steps claimed inside the window but finished after 14:45 (a batch of five finished 16:33:38-16:33:49) are still missing.
- Not explained by: model tier or model, agent role, step title, how many steps ran side by side
  (solo steps are missing as often as busy ones), complete_step vs approve_step, bot id.
- mcp_tool_log cannot tell the sessions apart (one session_id and one user for everything, and no arguments logged).

## Ruled out in the product
- STEP_USAGE_SHORT_COMMAND is blank in production (off), so every Claude claim carries the full inline command.
- claim_next_step has a single return path and always adds usage_command for Claude claims (workflows.ts ~1383).
- Ran the real saved script (stepUsageScript) against synthetic transcripts: one step, back-to-back steps, five steps
  open at once. It prints correct JSON each time (macOS awk 20200816). The 26 Oct change (#401) is not broken.
- Server side (mcp-server/src/lib/step-usage.ts) only skips on bad JSON / wrong shape; the shape allows any real output.
  Runtime logs that would show a skip are not retained (Vercel keeps 1 hour on this plan), so a skip cannot be excluded
  for the window, but nothing in the code explains a whole-card, time-boxed pattern.

## What it most likely is (not proven)
The gap follows the board's own session/job setup, not the product: the bot's cards are finished by its own
long-running session and its background job runner. That runner's own code (private repo, read-only look) has a
"complete step" helper with no usage argument at all. If the step is completed by that runner, usage can never be
passed. The 26 Oct 09:00 start and 27 Oct 14:40 end line up with that setup changing, not with any deploy.
To confirm: the job runner's logs/transcripts on the always-on machine for those two timestamps, and whether the
files in ~/.claude/vibecodes/ exist there.
