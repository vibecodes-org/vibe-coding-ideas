# 1117ac6b - steps on board d650f96a with no cost recorded

Status: cause found, fixed in the MCP server (complete_step / fail_step), PR open. Backfill proposed, not run.

## Heads-up (agent-facing behaviour change, release-coupled)
complete_step and fail_step now REFUSE a Claude step finished with a claim token but no `usage` and no
`usage_unavailable`. Nothing is changed on refusal and the claim token stays valid, so the caller just calls
again. No stored data, auth or payments touched; no screen changes (one guide sentence added).

The bot's own background job runner finishes some steps itself with a complete-step call that sends no usage.
Once this ships, those calls are refused until the runner sends `usage` (run the claim's usage_command against
the child's transcript) or `usage_unavailable: "<reason>"`. Update the runner first, then merge.

## Root cause
Recording a step's cost depended entirely on the orchestrating session remembering an optional extra step:
run the claim's usage_command and pass its line as `usage`. The claim instruction even said "never let it hold
up the step", the parameter was optional, and complete_step accepted a missing report silently. When a session
skipped it, the cost was lost with no signal anywhere.

Evidence:
- 56 completed steps on d650f96a claimed since 26 Oct have no workflow_step_usage row. Nothing in the stored
  claim differs inside vs outside the window (executed_model, effort, persona, tier, match, override all the
  same), and the usage marker is never stored, so nothing at claim time decides it.
- The bot's dev session read its own transcripts (relayed by the coordinator, not re-verified here): one laptop
  session made about 72 complete_step calls with no usage between 26 Oct 18:50 and 27 Oct ~14:40 UTC, ran the
  usage command only twice, and from 14:57 passed usage nearly every time. A second session finished 4 steps
  26 Oct 08:42-09:40 with no usage. Other sessions in the window reported usage reliably.
- 26 Oct 09:40-18:50: no step on d650f96a was claimed at all, so there is nothing to explain there.
- The five finishes at 16:33 on 27 Oct were approve_step calls (mcp_tool_log, remote, one session): Nick
  approving gated steps. approve_step doesn't lose usage; it is recorded at complete_step time (outcome
  awaiting_approval), and those five complete_step calls carried none.
- 89449cba (28 Oct 06:35-06:45, "Implement, deploy and check") was finished with no complete_step row in
  mcp_tool_log near it and no model reported; it matches the bot's job runner path, which never sends usage.

Ruled out (first pass): short-command switch (off), claim return path (always adds usage_command for Claude),
the usage script itself (correct on synthetic transcripts), server-side parsing.

## Fix
- mcp-server/src/lib/step-usage.ts: `missingUsageError()` - refuses a Claude attempt with a claim token and no
  usage/usage_unavailable. Codex claims (no usage command) and a human rejecting an approval gate (no claim
  token) are not affected. New `usage_unavailable` parameter is the escape hatch so a step can never be trapped.
  A "NO_TRANSCRIPT" line now counts as a report (logged at info, nothing stored).
- mcp-server/src/register-tools.ts: the check runs in the complete_step / fail_step handlers before anything is
  read or written. Put there rather than inside completeStep so the 100+ existing direct unit calls stay as
  they are; the handler is the only production entry point.
- mcp-server/src/lib/claim-instruction.ts: finish item now says pass the line it prints, NO_TRANSCRIPT included,
  and that it is required. Pinned instruction hashes regenerated on purpose.
- Tool descriptions and the admin guide say the same.

Review rework (same PR):
- The inline-run EXCEPTION sentence now says to pass usage (run usage_command as is) or usage_unavailable + why;
  without it every inline run's first complete would have been refused. Step 4 says usage is required.
  Wording trimmed to stay inside the claim size budgets (7,400 / 6,100 characters); hashes regenerated again.
- A NO_TRANSCRIPT line and a usage_unavailable reason are both logged at warn with the step id.
- .claude/rules/workflows-mcp.md no longer says usage "never blocks".

Not done (no evidence for it): accepting a late usage report for an already finished step (option b).
Malformed usage still never blocks: no sign that was a cause.
