# 52c1f2e9 — template edits leave the wrong agents on same-step-count runs

Card: "Editing a workflow template leaves the wrong agents on cards whose step count didn't change (and reports 0 updated)".
Planner step: 13 Oct 2026. User-facing change: NO new screens. Visible effect: cards show the right agent on their steps after a template edit, and one sentence is added to the workflows guide page. Touches stored data: yes, agent assignments on 246 waiting steps (repaired through the normal rematch code path, no data migration). No auth or payments. No mock.

## Reproduction (evidence, 13 Oct 2026, prod read-only)
1. On a board, have a template with active runs whose step count equals the new template's (this board's Bug Fix template `ea504731`, 4 steps before and after).
2. Change a step's role in `update_workflow_template` (or the app's template editor / resync).
3. Result: pending steps get the new title/role/wording, keep the old agent, tool reports `runsUpdated: 0`, `stepsUpdated: 0`, and nothing is rematched.
4. Calling `rematch_workflow_agents` on an affected task changes nothing (0 matched, 0 upgraded).

Live data proving it (all four `update_workflow_template` calls are in `mcp_tool_log` at 05:05–05:09 UTC; the Bug Fix one ran ~71 s; step `updated_at` 05:05:17–05:06:09; the `rematch_workflow_agents` try is logged at 05:09:55):
- Stale steps = pending steps of active runs where `match_tier = 'exact'` but the assigned agent's role is not the step's role (case-insensitive, trimmed). Across ALL boards: **246 steps on 86 tasks, all on this board (62e57071), all Bug Fix**. The 86 task ids match the orchestrator's `bugfix-wrong-agents-tasks.txt` exactly (79 never-started + 7 running).
  - role Planner on Sentinel (QA Engineer): 79
  - role Code Reviewer on Sentinel (QA Engineer): 81 (79 + 2 running)
  - role QA Engineer on ProdOwner (Product Owner): 86 (79 + 7 running)
- Mechanism of bug 1 reproduced with the real client library (postgrest-js 2.95.3, fake HTTP layer): an `.update()` with no count option returns `count = null`; `{ count: "exact" }` returns 1; `.select("id")` returns 1 row. Library: `node_modules/@supabase/postgrest-js/dist/index.cjs` ~L1086 (`Prefer: count=` header only set when asked) and ~L107-109 (count parsed only when that header was sent). Script kept in the planner's scratchpad (`repro52/count.cjs`), not committed.

## Root cause
1. **Count never requested** — `propagateTemplateEdits` (`src/lib/workflow-helpers.ts` ~L549-578), same-step-count branch: `const { count } = await supabase.from("task_workflow_steps").update({...}).eq("id").eq("status","pending")` never asks for a count, so `count` is always null, `stepsUpdated`/`runsUpdated` stay 0, and the task never enters `affectedTaskIds`. All four callers (app `updateWorkflowTemplate` ~L214, app `resyncWorkflowTemplate` ~L560 in `src/actions/workflow-templates.ts`; MCP `updateWorkflowTemplate` ~L347, `resyncWorkflowTemplate` ~L389 in `mcp-server/src/tools/workflows.ts`) rematch only `affectedTaskIds`, so nothing is rematched.
   - Present since the function was written (commit 4b688f1, 17 Mar 2026). The rematch-after-propagation added on 23 Mar (80fe02a) never fired for this branch. Only the step-count-mismatch swap (00188, added 12 Oct) reports tasks correctly.
   - Why tests didn't catch it: the mock in `src/lib/workflow-helpers.test.ts` (`createPropagationMockSupabase`, ~L537) returns `{ count }` from the update chain whether or not a count was asked for. The real library doesn't.
2. **Stale "exact" can't be beaten** — the rematch rule (three copies: MCP `rematchWorkflowAgents` ~L2190-2204, app `rematchWorkflowAgentsWithClient` ~L503 in `src/actions/workflow-templates.ts`, app `rematchActiveWorkflows` ~L82 in `src/actions/idea-agents.ts`) only replaces an agent when the new tier ranks strictly higher than the stored `match_tier`. Template propagation rewrites `agent_role` but leaves `bot_id` + `match_tier = 'exact'`, so the new exact match ties and loses. The stored tier describes a match to a role the step no longer has.
3. **Same cause elsewhere (not fixed in this card — follow-up):** editing a single pending step's role — MCP `update_step` (`mcp-server/src/tools/workflows.ts` ~L1907) and app `updateWorkflowStep` (`src/actions/workflow.ts` ~L61) — also rewrites `agent_role` without clearing `bot_id`/`match_tier` and doesn't rematch. The rematch guard below repairs those the next time a rematch runs on that card, but nothing triggers one. Recommend a follow-up card.

## Decisions
1. **Fix at the source:** in the same-count branch, when a pending step's role changes (compare normalized: trim + lowercase, same as exact matching), write `bot_id: null, match_tier: null` in the same update. Unchanged role (including case-only change) → agent and tier untouched. Count rows with `.select("id")` (not `{count}`) so the result is the real row list; count `stepsUpdated`, `runsUpdated`, push the task to `affectedTaskIds` when any pending step was rewritten (as the code always intended).
2. **Hand-picked agents** (`match_tier = 'manual'`, set per role by `setManualRoleMatch`): on an unchanged step they survive (not cleared; rematch never beats manual). On a step whose role changes they ARE cleared — the hand-pick was for the old role. Today there are 0 manual pending steps live.
3. **Rematch guard (one shared rule, three callers):** a stored `exact` tier only counts while the assigned agent's current role still equals the step's role. If not ("stale exact"), treat it as no match: replace with the new match, or clear to unassigned if nothing matches (a wrong agent is worse than none). `manual` is never touched. `ai`/fuzzy tiers can't be checked without an AI call, so they keep today's rule (fix 1 covers them on template edits). Pure helper in `src/lib/role-matching.ts`; also add `.eq("status","pending")` to the rematch writes (concurrency rule).
4. **Repair of the 86 tasks: no data migration.** After deploy, one `resync_workflow_template` on `ea504731` runs the fixed code: it rewrites the 89 runs with waiting steps (content identical), reports real counts, and rematches every one; the guard replaces the 246 stale exact steps. Why not the migration the orchestrator preferred: the guard is needed anyway (stops the tie bug for any path), so the code path repairs the data on its own; no irreversible bulk SQL write; no 5,000-character apply limit; the repair itself proves the fix live. Selection rule and counts are written below in case the code path fails and a migration is needed after all.
   - Scope: rule is global (any board), because stale exact is wrong by definition; today it only hits this board (246/86). Board 7e571896 has 86 pending steps whose agent role differs from the step role, but they are `ai` tier (Developer→Full Stack Engineer, UX→UX Designer, QA→QA Engineer, …) — legitimate AI matches. That's why the rule must include `match_tier = 'exact'`; "role doesn't match" alone would wrongly strip them.
5. **Guide wording:** add one sentence to "Template Edit Propagation" on /guide/workflows (`src/app/guide/workflows/page.tsx` ~L614): a step whose role changes gets its agent re-picked for the new role; a step whose role is unchanged keeps its agent, hand-picked ones included.

## Fallback selection rule (only if the resync repair fails)
```
pending step (s.status='pending') of an active run (r.status not in completed/failed)
AND s.match_tier = 'exact' AND s.bot_id IS NOT NULL AND s.agent_role IS NOT NULL
AND lower(trim(bot_profiles.role of s.bot_id)) <> lower(trim(s.agent_role))
→ SET bot_id = NULL, match_tier = NULL
```
Expected: 246 rows before, 0 after (86 tasks, this board only). Then `rematch_workflow_agents` on the 86 tasks (old or new code both fill null agents).
