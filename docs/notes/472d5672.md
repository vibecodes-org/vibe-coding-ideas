  - Migration `00186_bot_profile_prompt_backups_pre_layout_conversion.sql` snapshots ALL rows under reason `pre-layout-conversion-00186`, following the 00148/00174 pattern.
  - In apply mode, the script also inserts a fresh backup under the same reason for any row whose text changed since the snapshot.
  - Restore uses the latest backup per agent.
- **Safety:**
  - Each update is compare-and-set on `updated_at`, so an agent edited mid-run is skipped, not overwritten.
  - Each row passes three checks, or it's reported as failed and left untouched: (1) the new text parses as the new layout; (2) the parsed fields equal the converted fields; (3) no words are lost (old-layout markers and an exact "You are a/an <role>." prefix excepted).

- **Restore:** script restore only puts back agents still exactly as the conversion left them. A blunt SQL restore is documented in the migration header, as a last resort.
- **Converter fixes found while specifying this:**
  - The legacy markdown parser drops any text before the first `## Goal`-style heading. The converter keeps it, as the start of the goal.
  - The legacy "You are a X." strip could eat a real first sentence. The converter strips it only when it matches the agent's own role exactly.
- **Fingerprints:** every converted agent's in-app fingerprint changes. Every browser-terminal session started before the apply must be relaunched before the next step is claimed, including the one orchestrating this card. Otherwise steps quietly run on general helpers. This is release step 4.

## Stage 2 build (Atlas, 12 Oct 2026): code and migrations (plan parts 2a and 2b)

### Decided while building
- **2a swap function.** `replace_unstarted_workflow_run(p_run_id, p_steps)` (migration 00188) locks the run and all its steps, returns false unless every step is pending with no start time, claimer, either token hash, output or comment (it checks the comments table as well as the trigger-kept counter), then deletes and re-inserts the steps. New steps get no agent; the caller rematches. Tried on a scratch local Postgres with a minimal copy of the three tables: untouched run swapped, started run and commented run refused and left as they were.
- **Counters.** The board-task progress counters come from a row trigger (00071, latest body 00129) that recounts from scratch on every insert, update and delete of a step, so the delete-then-insert ends with the right totals. No change needed.
- **Agent rematching.** App `updateWorkflowTemplate` / `resyncWorkflowTemplate` and MCP `update_workflow_template` / `resync_workflow_template` already rematch every task in `affectedTaskIds`. A swapped run's task is added to that list, so nothing changed in the callers except returning `runsReplaced` from both resync paths. The MCP edit tool returns the whole `propagation` object, so it carries `runsReplaced` too.
- **Failure of the swap is a skip.** An error from the function is logged and counted as `skippedStructuralMismatch`, never thrown, so one bad run cannot stop the others.
- **Guide page.** The "Template Edit Propagation" paragraph on /guide/workflows said step-count changes are skipped; it now says an unstarted workflow is switched and a started one is left alone.
