# f4be2981: in-app terminal sessions survive the Mac locking or sleeping

Working notes for the Plan step (11 Nov 2026). Code read from origin/master at 6f3997b (helper 0.3.33).

## Settled by Nick (11 Nov, do not re-ask)
1. Keep the session alive while the agent is still running on the Mac. No timer ends it. Keep the 24h backstop.
2. Stay awake only while an agent is busy. Not always on, not a setting.
3. The browser reconnects to the same session by itself on wake, with an honest "reconnecting" state.

## What the code does today (checked)
- Relay `pairing.js:223` `RECONNECT_GRACE_MS = 90_000`. `index.js` `handleDetach` opens a grace hold. `alarm()` tears down with PEER_GONE (`endGrace`, notifies the app `peer_gone`) when both legs are still missing. If only the browser is gone and the bridge is attached, the hold is already released and the session lives on (backgrounded-tab fix).
- Relay idle cap: `DEFAULT_IDLE_MS` 2h of no traffic ends a whole session (`idle_timeout`). Heartbeats do not count as traffic. This would end an idle-at-prompt session after 2h even with the Mac awake, so it breaks decision 1 and the "overnight" acceptance. It has to stop applying to sessions from the new helper.
- Relay backstop: `DEFAULT_MAX_MS` 24h from session start. Kept. Registry `expires_at` mirrors it, so the lazy reap stays consistent.
- Bridge `index.js:672` `BRIDGE_RECONNECT_MS = 90000`, and `handleRelayClose` ~L1537-1565 shuts down (kills the agent) when the budget runs out. Backoff 1-8s. Terminal codes: 4001/4002/4005/4006. 1000 and 4004 also end it.
- Bridge `preOpenBuffer` (~L892) holds output while the link is down and has no size limit. A long gap with a busy agent could grow it without bound.
- Bridge max self-kill 25h (`--max-seconds` 90000). Kept.
- Credentials: `authorizeAttach` (`terminal/shared/session-token.mjs:266`) already waives token expiry for the bound owner, up to the max session age from the token's issue time. So once the relay keeps holding the session (owner binding kept), a bridge or browser can come back after hours with its original token. No re-mint is needed for A3.
- Browser: `use-terminal-session.ts` `scheduleReconnect` has a 90s deadline. Timers freeze during sleep, so on wake the deadline has already passed and it gives up straight away. The `peer-degraded` wait is also a 90s timer (~L2263-2279).
- False "Connected": while the Mac is gone but the browser link is up, the status is "connected" with `peerDegraded`, so the pill says Connected while the bar says reconnecting (`terminal-session-view.tsx` ~L1133 and `dockStatusMeta`).
- Helper idle-quit (A6) is already right: `lifecycle.decideLingerAction({ bridgeCount: children.size })` counts running bridges, whether or not a browser is attached (`terminal/helper/main.js` ~L464).
- Registry and chooser (A5): a held session's row stays `active` because the relay no longer reports `peer_gone`. `entry-decision.ts` reconnects to active rows. No change, but tests must cover it.
- Bridge to helper messages already exist (`process.send({type:"pty-pid"})`, helper `child.on("message")` ~L606), so "busy" can use the same channel.
- Helper is Electron ^33, so `powerSaveBlocker.start("prevent-app-suspension")` is available.

## Decisions made in planning (with reasons)
- **Version gating.** The relay only holds without a time limit when the bridge says it can (new `hold=1` on its attach URL, stored as `bridgeLongHold`). An old bridge still gives up at 90s, and the relay keeps its 90s grace for it, so nobody waits for a dead session. The browser drops its 90s limit only when the bridge's announced helper version is at least the new one.
- **The idle cap is skipped for long-hold sessions.** This follows from decision 1. It is flagged in the summary so Nick can object.
- **Ending while the link is down.** If the agent exits or the helper quits while the link is down, the bridge makes one short reconnect attempt (up to about 10s) just to send its clean "ended" close. If that fails, the relay holds until the backstop, and the browser's long-wait wording (mock scene 3) is the honest fallback. A relay to helper cross-check was ruled out as too much for this card.
- **Busy signal.** The agent printed anything in the last 2 minutes. Claude Code's and Codex's working indicators redraw every second while they work and go silent at the prompt. Agent-agnostic, needs no hooks.
- **One stage.** Every part has to ship in the same helper release, and a notarized helper plus a relay deploy is expensive, so stay-awake is not split out.
- Ruled out: re-minting tokens through the helper control connection, since the existing waiver covers it. Also ruled out an always-on stay-awake and a setting, per Nick.

## Build (11 Nov 2026), stage 1, one PR

Decisions made while building, with reasons:
- **Relay hold marker.** A long-hold session stores `graceDeadline = LONG_HOLD_DEADLINE` (a huge number) instead of a real time. That keeps every existing "was it held" check working, and `armAlarm`/`alarm()` ignore the value and the idle cap for such sessions. Only the max-age backstop is armed.
- **Bridge.** `BRIDGE_RECONNECT_MS` now defaults to 0 = no limit (the env override stays for tests). Backoff caps at 30s. A 5s timer spots a sleep (gap over 20s) and either reconnects at once or pings and drops a stale socket after 6s. Catch-up buffer is 1 MB, oldest dropped. If the link is down when the agent exits (10s) or the helper sends SIGTERM (3s), the bridge makes one short attempt to deliver the clean 1000 close before the verified kill. A helper crash (IPC drop) gets no courtesy attempt; there is no time and no one to tell.
- **Helper.** `stay-awake.js` is a new CommonJS file and is listed in `electron-builder.yml` `files` (a missing entry crashes the packed app). The menu-bar item only exists when "Keep helper ready" is on, so the helper now creates the menu-bar item while the stay-awake lock is held and removes it afterwards if "Keep helper ready" is off. Otherwise Nick would never see why the Mac stayed awake. This is a small addition beyond the plan.
- **Browser.** With a long-hold helper (version 0.3.34+, known from the bridge's version frame) `scheduleReconnect` has no deadline and no 90s peer-degraded timer. The old deadline value is still set once so the "how long have we been away" figure for refused reconnects stays correct. Old helpers keep the 90s window. Wake triggers (visible, online, 20s clock jump) only act while disconnected; the connected case relies on the existing silent-link watchdog, which already runs on visibility and online events.
- **Wording.** One bar for "disconnected" and "connected but Mac away" (`reconnect-copy.ts`); after 3 minutes it says "Still waiting for your Mac." with Reconnect now and End session. Status pill says "Reconnecting…" in the panel, the collapsed bar and the pop-out.
- Guide pages searched: nothing describes the old 90s or 2h limits. `terminal/RUN.md` updated.

Not done (by instruction): relay deploy, helper build/release, minimum-version bump. Live sleep tests are the Test step.

Known gaps to check at Test: the registry-ended case on wake is left to the dock's existing recheck (the reconnect loop stops itself when the relay answers with an ended close); no dedicated hook test for the wake reattach (covered by pure helper tests and the existing reconnect tests).
