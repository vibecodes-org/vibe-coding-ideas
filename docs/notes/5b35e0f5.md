# Card 5b35e0f5: stale rework feedback on re-claimed review/test steps

## Root cause
A send-back stores the same text twice: a `failure` comment on the step that complained (e.g. Code review) and a
`changes_requested` comment on the step it went back to. claim_next_step (mcp-server/src/tools/workflows.ts) read every
`failure` + `changes_requested` comment on the claimed step as its "own" rework, so a re-claimed Code review was told its
own old complaint was rework (scope this_step, "REWORK REQUIRED"). The run-wide lookup ran only when the step had none of
its own, so a newer tester complaint was never considered. Logic: mcp-server/src/lib/rework.ts. Wording:
mcp-server/src/lib/claim-instruction.ts. No parallel copy in the web app (src/ only mentions "rework" in terminal-session
comments, unrelated).

## Fix
- buildReworkInstructions: own `failure` comments are never rework; the newest comes back as `own_last_list`.
  Pool = own `changes_requested` + run-wide feedback from other steps; the newest wins. It is this_step only if that
  newest item is a changes_requested on this step, otherwise earlier_step (background).
- claim reply always loads run-wide feedback (limit 20).
- New line in the claim text for own_last_list ("not rework, check those points were fixed").

## Decision / ruled out
- "Newer than the step's last completion": not used. A cascade reset clears completed_at/started_at on the step, so that
  timestamp is gone by the time of re-claim. Newest-in-run ordering gives the same result (a send-back always writes a
  fresh changes_requested on the target, which is newer than anything it supersedes).
- Stored data and web UI unchanged; only the claim reply shape changes (rework_instructions.scope/feedback can now be
  null, new optional own_last_list).
