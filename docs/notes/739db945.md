## Facts verified by reading the 2.x packages (not guessed)

1. `createMcpHandler(init, options)`: one options object = SDK ServerOptions + `serverInfo`,
   `verboseLogs`, `onEvent`, `maxSubscriptions`. `streamableHttpEndpoint`/`basePath`/redis keys are
   REMOVED in 2.1.0 (passing them is a type error).
2. mcp-handler 2.3.1 hard-codes `legacy: "stateless"` when it builds the SDK handler. There is no
   option to set `'reject'`, so "never reject old clients" is guaranteed by the library. Old-era GET
   and DELETE get 405 with `Allow: POST`.
3. Auth reaches tools as `ctx.http?.authInfo` (was `extra.authInfo`). `withMcpAuth` sets `req.auth`;
   the handler passes it to the SDK as `authInfo`. Our `verifyToken` return shape
   (`token, clientId, scopes, extra, expiresAt`) still matches `AuthInfo`.
4. The 401 body is still JSON `{ error: "invalid_token", ... }` with a `WWW-Authenticate` header, so
   the e2e pin's `mcpBody.error === "invalid_token"` should still hold.
5. `.tool()` is gone from McpServer. `registerTool(name, { description, inputSchema }, cb)`;
   `inputSchema` takes a zod object (raw shape only via a deprecated overload).
   All 91 registrations already pass `XxxSchema.shape` of a `z.object`, so the rewrite is
   `inputSchema: XxxSchema`. No tool schema uses transform/preprocess/coerce/pipe (checked), so the
   handlers' own `.parse(args)` on already-parsed args is safe. Two `.refine`s exist (workflows.ts
   l.102, l.1908); refinements are dropped from JSON Schema but still run on validation, same as v1.
6. The codemod does NOT rewrite "import-less or injected SDK surfaces". register-tools.ts and
   instrument.ts are exactly that (duck-typed), so the 91 rewrites and the wrapper are by hand (or a
   one-off sed), not codemod. The codemod only helps index.ts and the package.json files.
7. Cache hints: option is `cacheHints: { "tools/list": { ttlMs, cacheScope } }`, scope values
   `'public' | 'private'`. The card's `cacheHints.tools` / `'shared'` are wrong names.
   Hints affect only new-era responses; old-era replies are unchanged.
8. Stdio: `serveStdio(factory)` from `@modelcontextprotocol/server/stdio`. The factory can be called
   twice (a discarded probe instance + the real one), so the server must be BUILT inside the factory.
9. JSON Schema is now made by `z.toJSONSchema(schema, { io: 'input', target: 'draft-2020-12' })`.
   The advertised tool schemas may change shape slightly: hence the before/after tool-list diff.
10. Neither package writes `globalThis.Response/Request` (grepped dists): the b6e5c728 regression
    should not return, and the pins stay.
11. No hono/express dependency in server 2.4.0 (deps: zod + core only).

## Decisions (planner's recommendations; Nick approves)

- D1 Split Client ID Metadata Documents out of this change into stage 2 of this card. Reason: needs a
  migration (uuid -> text on two tables), a server-side fetch of a client-supplied URL (needs SSRF
  guards, size/time limits, caching), and no client needs it today because we don't advertise it.
  Stage 1 keeps the two small, safe auth items: `iss` on the redirect + metadata flag, and the
  `application_type` test.
- D2 Tool-list cache time: recommend 5 minutes, `public`. The card suggested 1 hour. Shorter keeps a
  newly shipped tool visible within minutes to any client that honours the hint; the list is the same
  for every user so `public` is safe. Alternative: 1 hour (card's figure).
- D3 Testing route: no temporary API key or impersonation for the preview. Prove both protocol eras
  locally in an in-process test with a fake token checker, smoke the preview without a login, then do
  the logged-in checks on production straight after release with instant rollback ready.
  Alternative: Nick makes a temporary MCP API key so the preview can be tested logged-in first.
- Ships alone (different scope from anything in flight), one PR to master, no migration, no
  production approval gate needed.

## Ruled out

- Setting `legacy: 'reject'`: would cut off claude.ai connectors, Claude Desktop, Codex and Claude
  Code's old modes. Not even possible in mcp-handler 2.3.1.
- Keeping `@modelcontextprotocol/sdk` 1.x at root: mcp-handler 2 needs `server` 2 as its peer.
- Adding `@modelcontextprotocol/core` as a dependency: nothing we write imports its schema constants;
  add it only if the code ends up importing from it.
- Running the codemod on register-tools.ts / instrument.ts: it skips import-less seams.
- Changing the protected-resource `resource` value (`https://vibecodes.co.uk`, not `/api/mcp`): out
  of scope, not required by this change.
- Annotations, structured output, finer scopes, Tasks, MCP Apps: other cards (a36d7d63, c7ada119,
  970ac294).

## Implementation notes (Implement step, 11 Nov 2026)

Built on branch `feat/mcp-protocol-2026-07-28` (new branch from `origin/master`; the earlier
unrelated notes commit on the worktree branch was left behind, only this card's notes were carried over).

Decisions made while building, and why:
- Handlers keep the parameter name `extra` (type `ServerExtra`, now `{ http?: { authInfo } }`) instead of
  renaming to `ctx`: every handler already has `const ctx = await getContext(extra)`, a rename would collide.
  The route's two `getContext` callbacks name the SDK object `ctx` and read `ctx.http?.authInfo`.
- `sync_board_agents` used to set `_meta` by mutating the returned tool object. v2's `registerTool` config
  takes `_meta` directly, so it moved into the config (the existing test still pins the same value).
- Rewrite of the 91 `server.tool` calls was done by a one-off script (89 single-line descriptions) plus
  two multi-line ones by hand; schemas pass the `z.object` itself (`inputSchema: XxxSchema`).
- Added `@modelcontextprotocol/client` as a root devDependency (tests only). `@modelcontextprotocol/core`
  not added (nothing imports it).
- New `src/app/api/mcp/two-eras.test.ts` imports the REAL route (only `@supabase/supabase-js` faked) and
  drives both eras: raw old-era JSON-RPC and a real v2 `Client` pinned to `2026-07-28` (pin = no fallback,
  so a pass proves the new era works). Asserts same 91 tools in the same order on both, `mcp_tool_log`
  entry with user id and `session_id` on both, 401 and 405 behaviours.
- Tool-list before/after diff (scratchpad, not committed): names and order identical; descriptions and
  input schemas identical apart from `$schema` moving from draft-07 to 2020-12 and v1's per-tool
  `execution: { taskSupport: "forbidden" }` no longer being advertised (91 of 91). Neither changes
  what a client sends.
- Stdio smoke: `initialize` (server `vibecodes-local`, instructions present), `tools/list` (91) and a
  `tools/call` reaching the handler all worked, but the Supabase project in the main checkout's
  `.env.local` (zndmozhgtuerxvkuktdh) no longer resolves in DNS, so the tool's own DB call failed
  ("fetch failed") and no log row was written. A successful stdio data call is NOT proven. Nothing has
  used stdio in the last month and I did not point it at production with a service key.
- Build needs the three Supabase env vars and `NEXT_PUBLIC_APP_URL`; with throwaway values it passes.
- Local e2e pin could not run (needs the E2E database); the same canary was checked by hand on the
  built app (`GET /api/mcp` -> 401 `invalid_token` JSON, then `POST /api/terminal/session` -> proper JSON
  response, not the poisoned empty 500). CI's E2E job runs the real spec.
