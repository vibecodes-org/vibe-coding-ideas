# Card 802e4589: adding/removing an agent on a big board times out

## Reproduction
Unit test mcp-server/src/tools/idea-agents-rematch.test.ts: a board with 120 active
workflows, one waiting Planner step each. Before the fix, `allocateAgent` and
`removeIdeaAgent` made 120 role lookups (one per card, each may call the AI) before
replying; test expected 1 and failed (120 calls). Not reproduced against live prod
(would change real data); the 28 Oct report (125 steps, change worked, re-pick finished
later) matches exactly.

## Root cause
`rematchActiveWorkflows` in mcp-server/src/tools/idea-agents.ts looped over every card
with an active workflow and awaited `rematchWorkflowAgents` per card (3 reads + a role
lookup + one update per step, all sequential) before returning. Shared by
allocateAgent, removeIdeaAgent, allocateAllAgents. The pool change itself was already
saved, so the call "failed" only from the client's view.

## Fix (decision)
Do the whole idea in one pass: page-read active runs and pending steps, read the pool
once, ONE role lookup for the distinct roles, updates in parallel. Same decision
function (`decideStepRematch`), same status guard, same result.
Chose this over "reply first, work after": no dependence on `after()`/waitUntil being
reliable in the MCP route, and the caller still gets a truthful "done". Reads are paged
(1,000-row limit) and scoped by idea, not `.in(ids)`.

## Web screens
src/actions/idea-agents.ts already uses this batched approach plus `after()`; no change.
Not touched: the per-card `rematchWorkflowAgents` tool (still used per card elsewhere).

## Stage 2

### 1. Slow AI lookup on the board tool's add/remove reply
Chose: cap the AI wait and fall back to the plain (non-AI) role match. Added an optional
`aiTimeoutMs` to `matchRolesWithAi` / `matchRolesWithAiOrFuzzy` (src/lib/ai-role-matching.ts,
default stays 90s for every other caller); `rematchActiveWorkflows` in
mcp-server/src/tools/idea-agents.ts passes 10s. On timeout the existing error path returns
null and the fuzzy tier runs. Did NOT choose "reply first, work after": background work
surviving in the MCP route was not verified, and the capped wait needs no such guarantee.
Tests: ai-role-matching.test.ts (hung model call, 50ms cap, falls back; failed before: hung
to test timeout) and idea-agents-rematch.test.ts (tool passes a cap; failed before).
Trade-off: a slow-but-would-succeed AI lookup now yields the plain match for that call;
later re-picks (resync, adding another agent) can upgrade it, since "ai" outranks fuzzy tiers.

### 2a. Web re-pick read waiting steps unpaged
src/actions/idea-agents.ts `rematchActiveWorkflows` now pages with .range() (1,000/page,
ordered by id). Test: src/actions/idea-agents-rematch.test.ts (1,500 steps; got 1,000 before).

### 2b. Removed agent's waiting steps
Finding: on production the database already clears pending steps of a removed agent
(trigger on_idea_agent_remove_unassign, migration 00094; live check: 0 of 4,808 pending
steps point at an agent outside their board's pool). So the user-visible symptom does not
occur today. The code gap was real but masked: the web re-pick returned early on an empty
pool, and ignored a step whose agent was no longer in the pool unless its tier was "exact".
Added a code-side safeguard: such a step is treated as unassigned and cleared if nothing
replaces it; hand-picked (manual) steps are never touched. Tests: same file (2 tests).
Not changed: the board tool's re-pick has the same orphan blind spot, also covered by the
trigger; left alone (out of scope). awaiting_approval/in_progress steps are not touched
(by design, and the trigger only covers pending).
