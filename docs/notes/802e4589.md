# Card 802e4589: adding/removing an agent on a big board times out

## Reproduction
Unit test mcp-server/src/tools/idea-agents-rematch.test.ts: a board with 120 active
workflows, one waiting Planner step each. Before the fix, `allocateAgent` and
`removeIdeaAgent` made 120 role lookups (one per card, each may call the AI) before
replying; test expected 1 and failed (120 calls). Not reproduced against live prod
(would change real data); the 28 Oct report (125 steps, change worked, re-pick finished
later) matches exactly.

## Root cause
`rematchActiveWorkflows` in mcp-server/src/tools/idea-agents.ts looped over every card
with an active workflow and awaited `rematchWorkflowAgents` per card (3 reads + a role
lookup + one update per step, all sequential) before returning. Shared by
allocateAgent, removeIdeaAgent, allocateAllAgents. The pool change itself was already
saved, so the call "failed" only from the client's view.

## Fix (decision)
Do the whole idea in one pass: page-read active runs and pending steps, read the pool
once, ONE role lookup for the distinct roles, updates in parallel. Same decision
function (`decideStepRematch`), same status guard, same result.
Chose this over "reply first, work after": no dependence on `after()`/waitUntil being
reliable in the MCP route, and the caller still gets a truthful "done". Reads are paged
(1,000-row limit) and scoped by idea, not `.in(ids)`.

## Web screens
src/actions/idea-agents.ts already uses this batched approach plus `after()`; no change.
Not touched: the per-card `rematchWorkflowAgents` tool (still used per card elsewhere).
