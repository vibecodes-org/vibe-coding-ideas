## Root cause (confirmed)
Claude Code's skills/agents watcher polls. It does not use file events. Read from the 2.1.300 binary (the `skillChangeDetector` module) and confirmed with headless probes:
- Watched folders: the user and project `skills`, `commands` and `agents` folders that existed at session start. chokidar runs with `usePolling: true`, `awaitWriteFinish` stability 1 s, and a 300 ms reload debounce.
- While a human has typed in the last 60 s, it polls every 2 s. After 60 s with no human input (checked every 10 s), it switches to polling every **30 s** (`[skills] idle — switching poll interval to 30000ms`). Only a real user message counts as input (`recordUserDrivenInbound`). A background-task wake, a tool call or the model's own turns do not.
- So an unattended orchestrator is "idle" from about its second minute. A file written then is noticed on the next 30 s poll, which is up to ~31.5 s later. The shipped command waits 5 s and the retry another 5 s, so the wake turn's agent list doesn't have it yet.
- **Second failure mode: lost files.** Switching between idle and active closes the watcher and builds a new one with `ignoreInitial: true`. A file written in the ~2–3 s before the switch to idle, and not yet emitted, goes into the new watcher's initial scan and is **never** announced. It stays unloaded until some other change happens in a watched folder, or a human message triggers the idle→active reload.
- The agent list a turn offers is fixed when the turn starts (the `system/init` agents list). An Agent call later in the same turn uses that list.
- **Changed descriptions are never re-announced.** The model learns about agents through `agent_listing_delta` attachments, which are keyed by agent *name* only. When a file with an existing name is replaced, a spawn runs the NEW definition, but the model's listing keeps showing the OLD description and tag for the rest of the session.

How the live run matched (Sentinel, session_01KeF4zf…, 15 Oct):
- Nick's message landed at 06:54:40. Step 1 was written at 06:55:20, still active, and loaded by the 06:55:25 wake.
- Step 2 was written at 06:56:15, after the session went idle at ~06:55:41. It was missing at the 06:56:20 wake and present at the 06:56:39 turn.
- Step 3 was written at 06:57:28. It was missing at the 06:57:33 and 06:57:52 turns because the next 30 s poll fell after the second check. Every Agent call ran inside a turn that started before the reload.
- Count, name prefixes and file replacement played no part.
- When it started: the VibeCodes side since 775b31c (15 Oct), which relies on a 5 s settle. Before that (#360) a human's next message reset the watcher to active, which hid the problem.

## Decisions (recommended; Fix builds these)
1. **One sync saves the whole run's agents.** `sync_board_agents(idea_id, step_id)` also saves the agents of the same run's steps that are still pending, failed or in progress. The claimed step's agent comes first, then step_order, deduped by name, persona only.
   - Budget: the claimed agent as today (≤ `AGENT_FILE_MAX_BYTES`). The others are added while the total stays ≤ 60,000 bytes, which keeps the result under the 25k-token MCP limit and keeps the copy cost bounded. One that doesn't fit is synced at its own claim.
   - Result: `agents: [{name, tag, sha256, bytes}]` (claimed first), `instruction`, plus the command in block 2.
2. **The command confirms the load instead of sleeping.**
   - It writes every file to a temp file and verifies them all. One mismatch lands nothing (MISMATCH).
   - Self-test: it checks whether this filesystem updates atime on read (`touch -a -t 200001010000`, read, stat).
   - It sets each file's atime to 2000 and moves the files into place.
   - It then waits until Claude Code has read every file (atime > 2001), plus 1 s, and prints READY.
   - If nothing has been read after 5 s, it re-touches the files (mtime bump, atime reset) once. That recovers a file lost at the idle switch. Then up to 2 rounds of 35 s, each ending in a re-touch. After ~75 s it prints NOT_LOADED.
   - No atime support (noatime): write, `sleep 4`, re-touch, `sleep 34`, READY (unconfirmed, sized to the 30 s poll).
   - Stat portability: `stat -c %X` (GNU), else `stat -f %a` (BSD/macOS). zsh-safe: `set -- …` / `"$@"`, no command in a variable, no `status`/`path` variables.
   - The output names every saved agent with its tag.
   - Wait limits are parameters, so tests run in under a second.
   - Ruled out: a longer fixed sleep. 38 s every time, and it still can't detect a lost file without a re-touch. Also ruled out: polling the Agent tool alone. Each check costs a turn and can't recover a lost file.
3. **Claim hint and tool instruction:**
   - After a READY sync, every agent it saved is loaded for the session. Spawn them by name at their steps without syncing again, provided the claim's tag equals the tag the sync printed, even if the listing still shows an older tag (deltas are by name only).
   - Not offered at all after READY: run the same command once more (at most 2 syncs per step).
   - NEW_FOLDER, MISMATCH, NOT_LOADED or a failed command: general path, and no more syncs this session.
   - Replaces "Sync each agent at most once per session". The claim hint stays one line, for the `workflows.test.ts` hash pins.
4. **Stale copies** (the marker rule from b9205d04) now actually work. Before this fix, a re-synced name kept its old tag in the listing, so the step always fell back. Same root cause (name-keyed deltas), same fix (decision 3).
5. Unchanged: fingerprint check, marker rule, folder choice, `.gitignore` handling, the stdio path, no network.

## Can't be guaranteed (say so plainly)
- **NEW_FOLDER:** neither `.claude/agents/` nor the user agents folder existed at session start. Claude Code never watches a folder created mid-session, so that session can't be native. The closest options are the committed `.claude/agents/.gitignore` (the sync adds it for next time), `mkdir -p ~/.claude/agents` once on a Mac, or a cloud setup-script line.
  - Ruled out: calling the cloud-only `register_repo_root` tool to force Claude Code's `RegisterRepoRoot` → cache clear and rehome. It's undocumented and it misuses a tool meant for clones.
- **A session that can't run background tasks** (a subagent orchestrator, `CLAUDE_CODE_DISABLE_BACKGROUND_TASKS=1`): the list only refreshes at a turn start, so the first step after a sync uses the general path. With the up-front sync, the later steps are native.
- **It depends on Claude Code internals** (30 s idle poll, name-keyed deltas). The confirmed wait adapts to latency up to ~75 s. A future change could still break it, which is why the e2e acceptance check below exists.
- **macOS: not tested here.** Not tested: atime behaviour on APFS (if reads don't update atime, the self-test picks the 38 s branch), zsh, and Spotlight reading new files (an early READY is caught by the "run once more" rule). Owed to Verify on Nick's Mac.

## Rework after review (PR #365)

- The READY clause ("spawn by name even if the listing shows an older tag") now applies only when the name is not offered at all, or is offered with a description starting with SYNC_MARKER. A name offered without the marker is a VibeCodes launch copy (`--agents` beats files on a clash), so it takes the general path even after READY, otherwise a stale launch copy would be spawned and reported "verbatim". Changed in both `sessionAgentClaimHint` and the `sync_board_agents` INSTRUCTION, kept consistent.
- The hint's tail now reads "If the sync is skipped, fails, or doesn't end READY with that tag, or the spawn still isn't found after the second sync, ignore this note..." - the old "still isn't offered with that tag" contradicted the READY clause for a marked stale copy (listing keeps the old tag). Still one line, so the `workflows.test.ts` hash pins hold.
- The sync command sets its cleanup trap before the mktemp calls, so a failed later mktemp leaves no `.vc-*` dotfile (unset vars expand to empty args; `rm -f` ignores them).
- Guide copy no longer says "no second sync" or "the first one included" unconditionally: one retry is allowed, and the no-wait first step needs background tasks.
