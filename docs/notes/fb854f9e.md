# fb854f9e — Terminal "+" sometimes opens a new terminal instead of the list

## Status
Investigated (Planner, 20 Oct 2026). Root cause reproduced in a component test. Fix planned, not built.

## What Nick saw
Two connected terminals in the dock (one Codex, one Claude Code), viewing another board (d650f96a). "+" opened a new terminal straight away instead of the "Start new session" list. After a refresh, "+" showed the list again.

## Root cause (reproduced in a test)
`deliverLaunch` in `src/components/board/terminal-dock.tsx` decides "+" (and the toolbar's "In the browser" launch, which shares the path) from `entryDecisionRef.current.kind`, which is the PAGE-LOAD decision from `decideEntryBehaviour` (`src/lib/terminal/entry-decision.ts`). It shows the list only when that is `"chooser"`; anything else mints directly.

When the page loads with a fresh (<60s) saved snapshot for a live session this tab held, the decision is `"instant-continue"` (quietly reattach). That decision is right for the page load, but it STAYS the decision. `entryDecision` is memoised on `registryRows` and only re-runs when the registry list changes. That happens on a tab becoming visible again, going back online, a failed reattach, a rename, or a pre-load row being marked ended. Until one of those, every "+" mints directly, even with live and recent sessions to offer.

Why a refresh "fixed" it: whether a reload gets instant-continue depends on whether a snapshot was saved in the last 60s. The pagehide save in `use-terminal-session.ts` (`doSnapshotNow`) only writes when output has arrived since the last save (`snapshotDirtyRef`). Its comment says "unconditionally", but the code checks `snapshotDirtyRef`. So a reload while a session is busy gives instant-continue (bug armed). A reload while both sessions are idle gives "chooser" ("+" works).

Proof: a temporary component test (same harness as `terminal-dock.test.tsx`'s "multi-terminal reload restore") showed:
- Fresh snapshot + live and recent rows: "+" minted a 2nd tab and no dialog appeared. The test expecting the chooser FAILED.
- Same rows, stale snapshot (chooser load, then Reconnect): "+" showed the chooser. PASSED.
The temporary file was deleted; nothing was committed.

At 04:41:30 Codex dbc03947 was reattached separately, 58s later, so it was not part of instant-continue (that reattaches every fresh sid at once). At 04:41:37 came a direct mint on board d650f96a (1c331aae). That last one is consistent with Nick's report: Claude and Codex tabs open, viewing d650f96a, "+" minted.
- The new deploy (PR #377) went live between 04:12 and 04:40, so Nick probably reloaded after the release. Claude ceb6c56d was likely busy (fresh snapshot) and Codex was idle (stale), which gives instant-continue for the Claude tab only.
- Ruled out "empty-launch": the list route returns every active row plus every row ended within 48h, across all boards. Nick had many recent ended rows (e.g. bc383103 ended 04:12, f8d1790e ended 04:11). The decision could not have been empty-launch.
- A null decision (registry still loading) queues the launch and replays it as chooser or mint. It never mints blindly.
- So the only path that mints on "+" with Nick's data is a non-chooser page-load decision, which means instant-continue. This is inferred from code plus data, and matches the test. Exactly which clicks produced each mint can't be pinned from logs.

## Ruled out
- PR #377 (chooser-data.ts / terminal-session-chooser.tsx): it only filters which Recent rows the list displays. Routing reads `entryDecisionRef` (from raw `registryRows`), never `chooserSections`, for a no-task launch. An empty filtered list still renders the chooser.
- Empty-launch for Nick today: see above.
- Pop-out: not involved in the routing.

## When it started
The bug has been latent since card cbe60db5 (Aug 2026): e79a5e9 on 14 Aug made launches route on `entryDecisionRef`, and rework 11 removed the tab-count gate. "+" at one tab arrived on 23 Aug (3c2fe48). Not new today.

## Same cause, also fixed by the plan
- The toolbar "In the browser" launch (bus event, no task) goes through the same `deliverLaunch` branch and also mints directly after an instant-continue load.
- After instant-continue, a live session whose snapshot was stale is NOT restored, and "+" can't offer it. Today it's only reachable via My sessions.
- A launch clicked while the registry is loading is replayed in the seed effect (`entryDecision.kind === "chooser"` at ~line 2230). On an instant-continue load that replay also mints.
- Empty-launch at load (a new user, nothing recent): after starting a session, the decision stays empty-launch, because `registryRows` never learns about sessions minted in this pageview. A session minted then ended here isn't offered as Recent until a refresh. This is inferred from code; not seen in Nick's data.

## Decision (Nick, in card)
"+" shows the list whenever there is anything to choose between (a live or recent session), whatever the page-load decision was. It mints directly only when there is genuinely nothing to resume or reconnect.

## Fix plan
1. `src/lib/terminal/entry-decision.ts`: add a pure helper, e.g. `hasSessionChoice(rows, openSids, nowMs): boolean`. It is true when any row is a recent ended row (same 48h rule as `isRecentEnded`), or an active row whose sid is NOT open as a tab in this dock. Page-load `decideEntryBehaviour` is unchanged; instant-continue stays a page-load-only auto action.
2. `terminal-dock.tsx` `deliverLaunch`: keep the `null` guard (still loading → queue) and the task-launch branch. Replace `entryDecisionRef.current.kind === "chooser"` with `hasSessionChoice(registryRowsRef.current ?? [], <sids of open tabs>, Date.now())`. Get the open sids from `summariesRef.current`, the same way `ownSessionIds` is built; they need a ref because `deliverLaunch` must stay stable. When the chooser opens this way, also `void refreshRegistry()`, as `openChooserToBrowse` already does, so the list isn't stale.
3. Seed/replay effect (~line 2230): use the same helper for the queued-launch replay instead of `entryDecision.kind === "chooser"`.
4. Keep `registryRows` aware of sessions started in this pageview. When an open tab first reports a sessionId that isn't in `registryRows`, call `refreshRegistry()` once for that sid. This makes the empty-launch case, and sessions minted then ended here, count.
5. Leave `showingChooser` (no tabs, body swap) and instant-continue's auto-reattach alone.
