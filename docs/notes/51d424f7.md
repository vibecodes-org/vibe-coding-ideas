## Mac-only assumptions found in the helper/bridge (the stage 1 worklist)
1. `terminal/shared/binary-check.mjs` splits PATH on `:` and ignores `.exe/.cmd`, so on Windows it would report Claude "not installed". It must handle `;`, drive letters, PATHEXT and backslashes.
2. Spawning `claude` on Windows: the native installer gives `claude.exe`; an npm install gives `claude.cmd` (needs `cmd.exe /d /s /c`). The bridge spawn calls in `bridge/src/index.js` (~1210, ~1658) assume a direct exec.
3. Stopping processes: the bridge and helper use POSIX signals and process groups (`shared/reap.mjs` is POSIX-only; the bridge already guards some win32 cases at ~850 and ~1108). Windows needs a tree kill (`taskkill /PID <pid> /T /F`) plus a confirmed-dead check.
4. `electron-builder.yml` has only a `mac:` section, and its filter drops node-pty's win32 prebuilds for every build. It needs a `win:` section (NSIS, per-user) and per-platform filters.
5. Deep-link delivery on Windows comes through command-line args (cold start, `main.js` ~1510) and `second-instance` (warm). `main.js` already has `urlFromArgv` for both; it has never run on Windows. Scheme registration relies on the runtime `setAsDefaultProtocolClient` call in packaged builds (writes the per-user registry key on Windows).
6. Link length: `MAX_LAUNCH_URL_LENGTH` is 2700, sized for macOS; `src/lib/terminal/deep-link.ts` says this card must re-check it against Windows limits (about 2083). Unknown until measured on a real Windows machine with Chrome and Edge. This is the biggest technical risk.
7. The tray icon (`helper/tray-icon.js`) is a black "template" image that macOS re-tints; on a dark Windows taskbar it would be invisible.
8. Codex "open in a desktop terminal window" uses Terminal.app (`open -a Terminal`): Mac-only. Same-machine messaging (`bridge/src/local-mail.js`) writes a bash script: Mac-only. Both must be rebuilt for Windows in stage 1 (parity rule).
9. Machine name: `scutil` runs only on Mac; Windows falls back to `os.hostname()`, which does not drift on Windows. Fine; add a test.
10. The spawn-helper chmod fix and the login-shell PATH probe already skip Windows.

## Certificate facts (checked on the web 13 Nov 2026)
- The card says an EV certificate gives instant SmartScreen trust. That stopped in 2024: Microsoft now treats EV and ordinary certificates the same for SmartScreen. EV is no longer worth the premium or the company requirement.
- Microsoft's own signing service (Azure Artifact Signing) is open to individuals only in the US and Canada; in the UK it needs a company. Ruled out for now.
- Certum "Open Source Code Signing in the Cloud": listed from about EUR 49 (renewal price not confirmed), for individuals; the publisher shows as "Open Source Developer, <name>". Keys live in Certum's cloud; signing goes through their SimplySign app plus a phone code, so it is a hands-on step per release.
- SmartScreen reputation is per file, so each new release may show "Windows protected your PC -> More info -> Run anyway" to early downloaders, fading as people install it. The setup screen must say so.

Government ID check, no hardware posted; signing is officially automatable from GitHub Actions with stored login + one-time-code secret. Least ongoing effort: nothing per release. RECOMMENDED for least effort.

Signing needs their SimplySign app and a phone code; automating it means storing the phone-code seed as a secret (community tooling, Certum's terms not checked). Cheapest; a little effort per release unless automated.
- Azure Artifact Signing: individuals only in the US/Canada. Not open to Nick.
- EV: needs a company and no longer gives instant trust. Ruled out.

## Release 1a build decisions (core helper and bridge)
- Starting a program on Windows goes through `terminal/shared/spawnable.mjs`. An npm `.cmd` launcher is read to find the real script and run as `node script args`, so a prompt keeps its line breaks. Only if that fails does it fall back to `cmd.exe`, which flattens line breaks to spaces and may still expand `%NAME%` in a prompt (known limit).
- Stopping a session on Windows uses `taskkill /T /F` (`reap-win.mjs`), wrapped by `reapProcessEscalated` in `reap.mjs`; Mac/Linux behaviour is unchanged.
- PATH on Windows is merged from the live environment plus the registry user and machine PATH plus `~\.local\bin` (`resolveWindowsPath`).
- Bridge wording says "PC" instead of "Mac" on Windows; git-missing points to the Git for Windows download and never runs xcode-select.
- Helper: light tray icon on Windows, login item starts with `--hidden`, `launch-argv.js` finds the link in the argument list (tolerates quotes), stay-awake label says "this PC".
- Web: `home-short-path.ts` shortens `C:\Users\x\...` to `~\...`.
- New CI: `.github/workflows/terminal-windows.yml` runs the terminal suites on Windows and macOS runners.
- Link-length probe: `terminal/test/link-length-probe.html`. OPEN GATE: not yet run on real Windows. If anything under 2700 characters is cut, the plan's fallback (short one-time launch id from the server) is needed; that is a design change, not built.
- Deviations: `reapProcessEscalated` in `reap.mjs` (no separate `pidAlive`); Windows tray icon in `tray-icon.js`; `toSpawnable` parses npm shims (beyond plan); small early slice of the copy work.
- Not in 1a: installer, release, download route, web setup screens (1b); Codex window, messaging, in-app setup (1c).

## OPEN GAP: Windows test coverage (read before calling 1a "proven")
Windows CI runs only: the bridge suite (287 tests), the shared suite, and four shell-free helper tests (launch-link parsing, stay-awake label, control-url, agent-availability). The full integration suite (terminal/test, about 50 files) is run on macOS only, because it starts bash, sleep and sh scripts.
NOT yet proven on Windows: starting an agent in a real pseudo-terminal, reconnect and reattach after a dropped link, long-gap reattach, the owner-mismatch check, the grace window after a bridge drops, the heartbeat, end-of-session handling, resume, same-PC messaging (the mail command is a shell script; release 1c), worktree fallback, auto-compact and effort launches, orphan cleanup, and the helper control connection and open-terminal paths.
Covered by Windows tests: Windows path handling, binary lookup, PATH merge, program launching and stopping (unit level), bridge wording, folder guard, link parsing in the helper.
To close the gap: either (a) make Windows versions of those integration tests (replace bash/sleep with node child processes), or (b) run the full manual checklist on the Windows 11 virtual machine. Green CI is NOT proof that Windows behaves like the Mac.
