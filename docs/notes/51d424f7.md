## Mac-only assumptions found in the helper/bridge (the stage 1 worklist)
1. `terminal/shared/binary-check.mjs` splits PATH on `:` and ignores `.exe/.cmd`, so on Windows it would report Claude "not installed". It must handle `;`, drive letters, PATHEXT and backslashes.
2. Spawning `claude` on Windows: the native installer gives `claude.exe`; an npm install gives `claude.cmd` (needs `cmd.exe /d /s /c`). The bridge spawn calls in `bridge/src/index.js` (~1210, ~1658) assume a direct exec.
3. Stopping processes: the bridge and helper use POSIX signals and process groups (`shared/reap.mjs` is POSIX-only; the bridge already guards some win32 cases at ~850 and ~1108). Windows needs a tree kill (`taskkill /PID <pid> /T /F`) plus a confirmed-dead check.
4. `electron-builder.yml` has only a `mac:` section, and its filter drops node-pty's win32 prebuilds for every build. It needs a `win:` section (NSIS, per-user) and per-platform filters.
5. Deep-link delivery on Windows comes through command-line args (cold start, `main.js` ~1510) and `second-instance` (warm). `main.js` already has `urlFromArgv` for both; it has never run on Windows. Scheme registration relies on the runtime `setAsDefaultProtocolClient` call in packaged builds (writes the per-user registry key on Windows).
6. Link length: `MAX_LAUNCH_URL_LENGTH` is 2700, sized for macOS; `src/lib/terminal/deep-link.ts` says this card must re-check it against Windows limits (about 2083). Unknown until measured on a real Windows machine with Chrome and Edge. This is the biggest technical risk.
7. The tray icon (`helper/tray-icon.js`) is a black "template" image that macOS re-tints; on a dark Windows taskbar it would be invisible.
8. Codex "open in a desktop terminal window" uses Terminal.app (`open -a Terminal`): Mac-only. Same-machine messaging (`bridge/src/local-mail.js`) writes a bash script: Mac-only. Both must be rebuilt for Windows in stage 1 (parity rule).
9. Machine name: `scutil` runs only on Mac; Windows falls back to `os.hostname()`, which does not drift on Windows. Fine; add a test.
10. The spawn-helper chmod fix and the login-shell PATH probe already skip Windows.

## Certificate facts (checked on the web 13 Nov 2026)
- The card says an EV certificate gives instant SmartScreen trust. That stopped in 2024: Microsoft now treats EV and ordinary certificates the same for SmartScreen. EV is no longer worth the premium or the company requirement.
- Microsoft's own signing service (Azure Artifact Signing) is open to individuals only in the US and Canada; in the UK it needs a company. Ruled out for now.
- Certum "Open Source Code Signing in the Cloud": listed from about EUR 49 (renewal price not confirmed), for individuals; the publisher shows as "Open Source Developer, <name>". Keys live in Certum's cloud; signing goes through their SimplySign app plus a phone code, so it is a hands-on step per release.
- SmartScreen reputation is per file, so each new release may show "Windows protected your PC -> More info -> Run anyway" to early downloaders, fading as people install it. The setup screen must say so.

## Release 1a build decisions (core helper and bridge)
- Starting a program on Windows goes through `terminal/shared/spawnable.mjs`. An npm `.cmd` launcher is read to find the real script and run as `node script args`, so a prompt keeps its line breaks. Only if that fails does it fall back to `cmd.exe`, which flattens line breaks to spaces and may still expand `%NAME%` in a prompt (known limit).
- Stopping a session on Windows uses `taskkill /T /F` (`reap-win.mjs`), wrapped by `reapProcessEscalated` in `reap.mjs`; Mac/Linux behaviour is unchanged.
- PATH on Windows is merged from the live environment plus the registry user and machine PATH plus `~\.local\bin` (`resolveWindowsPath`).
- Bridge wording says "PC" instead of "Mac" on Windows; git-missing points to the Git for Windows download and never runs xcode-select.
- Helper: light tray icon on Windows, login item starts with `--hidden`, `launch-argv.js` finds the link in the argument list (tolerates quotes), stay-awake label says "this PC".
- Web: `home-short-path.ts` shortens `C:\Users\x\...` to `~\...`.
- New CI: `.github/workflows/terminal-windows.yml` runs the terminal suites on Windows and macOS runners.
- Link-length probe: `terminal/test/link-length-probe.html`. OPEN GATE: not yet run on real Windows. If anything under 2700 characters is cut, the plan's fallback (short one-time launch id from the server) is needed; that is a design change, not built.
- Deviations: `reapProcessEscalated` in `reap.mjs` (no separate `pidAlive`); Windows tray icon in `tray-icon.js`; `toSpawnable` parses npm shims (beyond plan); small early slice of the copy work.
- Not in 1a: installer, release, download route, web setup screens (1b); Codex window, messaging, in-app setup (1c).

## Windows test coverage (rework round 1, after code review)
Earlier wording here said the integration suite was Mac-only "because it starts bash, sleep and sh scripts". That overstated it: about 23 of the files start the bridge with plain node and needed no shell, and most of the rest only used a shell script as a stand-in agent. Corrected:
- CI (`terminal-windows.yml`) now runs EVERY file in `terminal/test/package.json` on both Windows and macOS, each file on its own time limit (`terminal/test/run-each.mjs`), so a stuck file is named instead of the job timing out.
- Stand-in agents on Windows are real npm-shaped `.cmd` launchers (`terminal/test/fake-agent.mjs`), so those tests run the shipped launch route (read the shim, run `node script`).
- Marked long-lived children (`terminal/test/sentinel.mjs`) are a node process on Windows, found by exact command line through the process table.
- Real Windows-only tests with no fakes (`terminal/shared/windows-real.win32.test.mjs`): a real parent and child ended with taskkill, the real reap function, a real `.cmd` launched through the cmd.exe route with the exact arguments checked, real cmd expansion of `%VAR:~0%` (proving why `%` is refused), and the real registry PATH read (a folder is added to the user PATH, found, then removed).
- cmd.exe fallback: any `%` in the program path or an argument now makes `toSpawnable` throw `CMD_PERCENT_REFUSED` (no escape works for `%` on a command line, and cmd expands the edit forms `%X:~0%` and `%X:a=b%`). The bridge already catches spawn errors and ends the session with `spawn-failed`. Standard npm shims never take this route, so ordinary prompts containing `%` are unaffected.
Tests skipped on Windows, each with its stated reason in the test itself:
- `open-terminal.test.mjs`: runs the Mac Terminal.app launch script with bash. The Windows window is release 1c and gets its own tests there.
- `setup-launch.test.mjs`: drives the Mac in-app setup (curl, chmod, sh installer). Windows setup is release 1c.
- `orphan-cleanup.test.mjs` (b) SIGTERM, (c) SIGKILL'd bridge, and the two reap-module tests: they test POSIX signals (SIGTERM handler, SIGHUP, process groups) that do not exist on Windows. The Windows tree kill is covered by the real taskkill tests.
- `resume-agents-launch.test.mjs` slow login-shell test: Windows has no login shell (it reads the registry).
- `local-mail.test.js` same-PC message command tests: a shell script today; Windows version is release 1c.
- Mac wording tests in `bridge-copy.test.js` (the PC wording is covered in `windows-paths.test.js`), and the executable-bit test in `binary-check.test.mjs` (Windows decides by PATHEXT; see the win32 tests).
Still NOT proven on real Windows: the link-length gate and the installed app (deep links, tray, login item); those need the Windows 11 virtual machine (stage 1b/test).

### Rework round 1, later findings
- REAL Windows bug fixed: the bridge's Claude version check (`probeClaudeVersion`) ran the bare name, which cannot start an npm `claude.cmd` shim, so on Windows the memory-limit flag was silently never added. It now uses the same launch target as the real start. Mac unchanged. (The same weakness exists in the setup sign-in status check; that belongs to release 1c.)
- Test helpers: `winEnv` (system variables a Windows child needs), `killBridge` (kills the whole tree on Windows), `rmDir` (retries; on Windows a still-held temp folder only warns), `exitCmd` + `exit-code.mjs` (an exit-code agent without `sh`), `macWording` (maps "this PC" and `~\` paths back so the Mac-worded assertions check the same facts on Windows).
- Skipped on Windows with reasons in the test: SIGKILL and bridge-SIGTERM cases in `fresh-mac-folder`, the SIGTERM-while-fetching case in `resume-agents-launch`, POSIX file-mode checks. The parent-death log line check in `orphan-cleanup` (d1) is POSIX-only: on Windows the bridge and child still die (asserted) but the log line is not captured; cause not found.
- Result: the full terminal suite passes on both Windows and macOS CI (one unrelated macOS timing flake in `long-gap-reattach` passed on re-run).

## Release 1b build (Build step, 24 Nov 2026)
What was built: the Windows installers (x64 + ARM, per-user one-click NSIS, VibeCodes logo, uninstall removes the link handler and start-at-login entry but keeps the saved sign-in), `.github/workflows/helper-windows.yml` (builds and smoke-tests both on GitHub's x64 and ARM Windows machines; on a published `terminal-helper-v*` release it uploads them to the same release), the 6-file release check (`scripts/check-helper-release.mjs` + `.github/workflows/helper-release-check.yml`), the download route by OS and chip, Windows wording on every web screen, the hidden 1c features, helper 0.4.0 and the update nudge moved to 0.4.0.

Decisions and why:
- **Wording by rewriting, not by copying.** `forMachine` / `forMachineDeep` (`src/lib/terminal/machine-words.ts`) rewrite the Mac strings for Windows ("this Mac" -> "this PC", Finder/Terminal names, `~/` paths). The Mac strings stay byte-identical, so no Mac screen can drift; a sweep test checks no Mac-only word survives on any Windows screen. `useTerminalOs()` reads the machine after hydration; the server render uses the Mac wording.
- **One list of file names.** `src/lib/terminal/helper-assets.ts` names all 6 files; the download route and the release check both import it, so they can't disagree. The release check runs that TypeScript file directly, which needs Node 22.18+ / 24, so its workflow uses Node 24 (the rest of CI stays on 20).
- **Chip choice.** The main Windows button is x64 with an "ARM PC?" link, as mocked. The browser's reported chip is used only by "Update now", which has no button to choose from. The alternate link moved into the platform object (`altDownload`), optional, so screens without one show nothing.
- **Unsupported machines' button now reads "Download"** with no machine name (the coming-soon panel lost its Windows button, decision 3).
- **Hiding 1c features on Windows (decision 1):** the Codex terminal-window menu items are hidden; on Windows Codex launches in the browser only. The bridge refuses the install/sign-in commands on Windows (`setupCommand` returns null, the session ends with "setup-refused"); the web never offers them there, so that reason is never shown. Same-PC messages are not started on Windows (`sameMachineMessagesSupported`). The Windows setup screen asks the user to install the agent with the maker's own instructions, then click Start again, and says "Some features are still coming to Windows." That screen's wording is new (the mock shows only the Mac one-click flow): **decision for Nick**.
- **Logo** generated from `public/icons/icon-512x512.png` into `terminal/helper/build/` (.icns, .ico with 16-256 px, .png).
- **Notifications on Windows** need an app id: `app.setAppUserModelId("co.uk.vibecodes.helper")` on Windows only.
- **Smoke test** (`terminal/helper/scripts/smoke-win.mjs`): silent install, checks the bridge and this chip's node-pty build are packed (and no Mac ones), starts the app and checks it is still running after 10 s, silent uninstall.
- **Signing**: unsigned, with a marked slot in the workflow for a certificate later.

- Releasing 0.4.0 still needs the Mac build and notarising on Nick's Mac, then publishing the release (which triggers the Windows build and upload).
