# Card 9efc01c3 - helper accepts launch links for any account

## Result
Reproduced at code level (not live): a launch link whose tokens name another account started a bridge and overwrote the saved control credentials. Live two-account check NOT done; owed after the helper release.

## Cause
`terminal/helper/main.js` `handleLaunchUrl` (and `handleOpenTerminalUrl`) checked the link shape and relay host but never the account (`sub`) in the tokens, because the helper holds no signing secret and kept no notion of its own account. The relay's OWNER_MISMATCH only compares the bridge and browser legs with each other. A `helperToken` in a link was also written by `saveControlCredentials` and used by `connectControl`, so a foreign link re-pointed the persisted always-on connection. Open-terminal had the same gap (it saved credentials before the relay ack).

## Decisions
- Owner = the `sub` the helper first paired with, pinned in userData `helper-owner.json`. An existing helper with no pin adopts the `sub` of its saved control credentials (Nick's already-paired Mac is protected with no action).
- Launch links: session token and helperToken must both carry a `sub`, agree, and match the owner. Checked before saving, connecting or forking.
- Open-terminal: checked before the cooldown, save and socket; pinned only after the relay ack.
- Refusal: log plus a Mac notification; nothing forks, nothing saved.
- Legit change of account: new tray item "Sign out this Mac" clears the pin and saved credentials.
- Known limit: a never-paired helper pins the first account whose launch link it sees (trust on first use), since the helper cannot verify signatures. Stronger option (a decision for Nick): pair via a relay-verified step before pinning.
- Not changed: relay, minting route, link contents.

## Ruled out
Link cannot carry a command (`--cmd`/`BRIDGE_CMD` are CLI/env only); permission mode allowlist unchanged.

## Where
Fix: terminal/helper/main.js (loadOwner, ownerAllows, forgetOwner, tray). Tests: terminal/test/helper-owner.test.mjs; control-connection.test.mjs now uses one fixed owner. Needs a notarized helper release plus minimum-version bump.

## Stage 2 (hardening from the code review; the "never-paired helper pairs first" part is NOT done, it needs a design for Nick)
- **A. Helper token saved only after the relay accepts it.** The owner check can't spot a hand-made token carrying the owner's own `sub` (no signing secret on the Mac). Before: `handleLaunchUrl` saved it at once and `connectControl` closed the working connection, so the relay's 4006 left the helper offline with bad saved credentials. Now `connectControl` keeps the accepted connection as a standby, opens the new one, sends a heartbeat on open and treats the first `hb-ack` as proof of acceptance (the relay answers heartbeats only on accepted legs: auto-response or the `webSocketMessage` fallback; a rejected leg is closed at once). Only then are credentials saved and the standby closed. A 4006 before acceptance falls back to the standby. Open-terminal now saves only after its `open-terminal-authorized` ack (it used to save before the ack, contrary to what the review assumed). No relay change.
- Side effect, intended: the reconnect backoff resets on acceptance, not on bare `open` (a rejected leg also opens).
- **B. Resume waits for the relay.** A resume (`--continue` / `--resume <id>`) now spawns on the relay's `attached` frame, like a fresh launch, with the same 10s confirm timeout. Only the dev/test `direct` mode (explicit `--cmd`, not reachable from a link) still spawns first. Cost: a resume starts after the relay round trip instead of in parallel with it.
- Stand-in relay now echoes heartbeats on helper legs, as the real relay does.
- Tests: helper-owner (3 new, fail before), resume-auth-gate (2 of 4 fail before), open-terminal-relay-auth (5).
- **Review follow-up (blocking):** a connection is only kept as a standby once fully open and accepted, so a forged link arriving during a reconnect wait (or before the live connection was confirmed) had nothing to fall back to and the helper stopped on the 4006. Now, when a new pass is refused and nothing is kept, the helper reconnects at once with the saved pass if it differs from the refused one (same pass refused = stop, as before; no loop).
- **Review follow-up (non-blocking, done):** a new connection that gets no heartbeat reply within 10s is closed, nothing is saved, and the helper falls back the same way (kept connection, else saved pass, else the normal reconnect).
- Left as review notes, not done: a stray connection when two links arrive at once; a resume's exit reason on the attach timeout.
