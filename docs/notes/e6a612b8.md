# e6a612b8: the board raises the next-card bar itself

Follow-up to 7c728159 (the "Card finished. Next up" bar) and 99b2d0b2.

## The bug

The bar never appeared on one board (idea b7b21b93) although about 80 cards'
workflows finished there between 14 and 24 Nov 2026. No offer row was ever saved
for that board.

Cause: the bar only appeared if the session itself called `offer_next_card`
after reading the finish reply. That tool is deferred, so the session must load
it first. The long-running session on that board never loaded or called it; it
only said the wording. Nothing on the server ever raised the bar on its own.
Sessions on other boards did call it (13 to 16 Nov), which is why it "worked
when first tested". It is a design gap, not a regression: it has been this way
since the bar shipped (#468).

Reproduced in a test: `workflowFinishedReply raises the bar for the calling
session > stores the offer when the finishing call carries the session's proof,
without the session calling anything else`
(`mcp-server/src/tools/session-offers.test.ts`) failed before the change (no
offer stored, reply still asked the session to call `offer_next_card`) and
passes after.

## How the server knows which session is calling

It doesn't, by itself. In-app sessions use the person's normal board connection,
shared by every session, so nothing in the request says which tab it came from.
`offer_next_card` "works without from_session" only because the Mac helper adds
a pre-tool hook to every Claude launch (`terminal/bridge/src/peer-bridge.js`,
`SEND_TOOL_MATCHER`) that fills in `from_session` (the session's signed proof)
on that one tool. Codex has no such hook: it must pass the value itself.

## What changed

- `complete_step`, `approve_step`, `skip_step` and `claim_next_step` take an
  optional `from_session` (`finishingSessionParam` in `session-identity.ts`).
- `workflowFinishedReply(ctx, taskId, fromSession)` (`next-card.ts`) calls the
  new `raiseNextCardOffer` (`session-offers.ts`), which verifies the session
  with the same `verifyCallingSession`, checks it is on the card's board, and
  saves the offer row with the same next-card choice and the same
  one-row-per-session upsert as `offer_next_card` (shared `saveOffer`).
- `still_working_on` is worked out on the server (`countStillWorkingOn`): cards
  on the same board, other than the finished one, with a workflow step in
  progress right now (Nick, 24 Nov 2026: not cards waiting for approval, not
  cards that merely sit in the In Progress column), leaving out any card another open in-app session of the
  same person was launched for. Claims don't record which session made them,
  so this is the closest the server can tell without a new column.
- The finish reply no longer asks the session to call `offer_next_card`. It has
  `next_card_offer: { shown }`; when shown, the instruction says the bar is
  already up and gives the closing line; otherwise it is wording only.
- Any failure to verify or save is logged (`logger.error`) and falls back to the
  wording. It never fails complete_step / approve_step.
- If this session already has an offer for this same card, it is left alone, so
  `claim_next_step` re-reporting the finish never brings back a dismissed bar.
- Bridge: the hook now also fills `from_session` on the four workflow tools.
  Only `offer_next_card` stays pre-approved; for the workflow tools the hook
  gives no permission decision, so the user's own permission rules still apply
  (Claude Code applies a hook's changed input when no decision is given; checked
  in Claude Code 2.1.331).
- `offer_next_card` stays, mainly for withdraw ("keep going here"). Its tool
  description, the guide pages and code comments now say the board shows the bar.

## Decisions

- Last step approved on the website (no session calling): no bar, as today. The
  session shows the bar the next time it checks the card (`claim_next_step`
  reports the finish and carries the proof). Listed for Nick.
- Codex: covered only when it passes `from_session` itself (its parameter
  description tells it how). No Codex hook can fill it in.

## Release order (important)

1. Merge and deploy the server change first. Claude Code checks a hook's changed
   input against the tool's input list, so a helper that adds `from_session` to
   `complete_step` before the server accepts it would get that call refused.
2. Then release a new Mac helper with the bridge change and bump
   `MINIMUM_RECOMMENDED_HELPER_VERSION`. Until then nothing changes for Claude
   sessions (they still get wording only).
3. Sessions already running keep their old hooks until restarted or resumed from
   the browser.

## Ruled out

- Guessing the session from the board (the only open in-app tab on that board):
  would show the bar in a tab that didn't finish the card when Nick works from
  his own terminal, and tell the caller a bar was shown when it wasn't.
- Rewording the finish message only: rejected by Nick (still relies on the
  session obeying).

## Stage 2: an open board page could miss the saved offer (27 Nov rework)

The server saved the row (sid 0305f1d5, 07:27) but the open page only learned of it through the live feed, and a missed live event was never made up. Fix in src/components/board/use-session-offers.ts:

- Re-read the offers on SUBSCRIBED, on tab visible again, and every 45s (one small filtered read per open board; short enough to feel prompt).
- CLOSED now retries like TIMED_OUT / CHANNEL_ERROR. No loop: channel is set to null before the old feed is unsubscribed, and the subscribe callback ignores any feed that is not the current one (and the cancelled flag).
- A re-read cannot undo an answer being saved: pendingRef holds in-flight answers and load() applies them over the fresh rows. Out-of-order reads are dropped by a sequence number.
- Bar look and behaviour unchanged.
