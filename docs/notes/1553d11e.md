# 1553d11e: model settings changed mid-session should reach helpers without a restart

Working notes for the card. Planning step done 27 Nov 2026. Code read at origin/master 6963acff.

## What is actually happening (checked)

- An in-app session gets the board's helpers once, when it launches or resumes. The bridge
  passes them on the command line (`claude --agents`), and Claude Code keeps that copy for
  the whole session. It cannot be replaced while the session runs. Each copy's description
  ends with a tag `[vc <hash> <model> <effort>]`. The hash does not cover the model or effort.
- Every claim works out the model live from the current settings, so the claim reply is
  always right. Only the session's own helper copy is out of date.
- Since 28 Oct the claim tells the session: if the copy has the same hash but a different
  model or effort, spawn it anyway and pass the model and effort explicitly. Claude Code's
  Agent tool honours an explicit `model` (it beats the definition) and also takes `effort`.
- Evidence from local session transcripts (helper launch records plus each helper's own
  transcript):
  - It works when followed. On 24 Nov one session's copies said opus while claims said sonnet.
    The session passed sonnet and the helpers ran on sonnet (55 launches across sessions).
  - It is often not followed. The exact-match text says "pass no model parameter". Sessions
    seem to match by name and skip the tag comparison. Example: 13 Nov, a reviewer claim asked
    for fable/high, the session's copy said opus/medium, no model was passed, the helper ran
    opus, and the step recorded opus as "tier honoured". Counts on old long-resumed sessions
    are less reliable, because the scan may pair a launch with the wrong listing.
  - Unexplained (not investigated): about 300 launches where the listing matched the claim
    and no model was passed, yet the helper's transcript shows a different model. The builder
    should look at two or three before relying on "definition decides".
- The recorded model on a step is self-reported. Measured token rows (workflow_step_usage)
  are the truth. Over the last 14 days the self-report disagreed with the measured main model
  on 7 of about 735 tiered steps. It is also sometimes free text or a full id. The cost
  report already prices from measured rows, but its "model" column and the tier-adherence
  dashboard read the self-report.
- Completion judges "tier honoured" against the settings live at completion, not at claim.
  A change made while a step runs can flip the verdict. (This is a documented limitation in
  resolveTierAdherence.)
- Codex: uses a role file only on an exact tag match, otherwise its general path with explicit
  spawn settings. It already follows a settings change. No change needed.
- Hand-started sessions: synced helper files can be re-synced mid-session. Explicit passing
  covers them too.

## Decision (recommended, awaiting approval)

Stage 1, no screen changes:
1. Always pass the model and effort. For a tiered Claude step the claim says, in every case,
   spawn the named helper with model X and effort Y on the Agent tool. Drop "pass no model
   parameter". The out-of-date copy then stops mattering. The claim also adds structured
   `spawn_model` and `spawn_effort` fields on native_subagent.
2. Backstop at completion. When measured usage exists, take the helper's main model (most
   output tokens) and compare it with what the claim asked. Record the measured model, mark
   the tier not honoured on a mismatch, and add a plain step comment plus a notice in the
   complete_step reply. The notice tells the session to pass the model from now on, or to
   tell the user to restart or resume the session if it can't.
3. Snapshot the asked-for model and effort on the step at claim (two new columns), so the
   verdict is judged against what the claim asked. Decision for Nick: include it (recommended)
   or skip it and keep the live-settings comparison.
4. One guide sentence: a model change applies from the next step a running session picks
   up; no restart needed.

## Ruled out

- Refreshing the launch-flag copy mid-session: Claude Code reads `--agents` only at start.
- Switching in-app sessions from the launch flag to synced files so they can be rewritten:
  a large change, and unnecessary once the model is always passed.
- Having the bridge report its launched tags so the server can spot stale copies: a claim
  does not know which terminal session made it, so this needs new plumbing for no extra gain.
- Putting the model into the hash, which would force a re-sync or restart: the opposite of
  what the card wants.
