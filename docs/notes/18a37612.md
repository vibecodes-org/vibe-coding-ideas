### What I checked (facts, with sources)
- **Claude Code has a launch flag for effort.** `claude --help` on Nick's Mac (Claude Code 2.1.299) lists `--effort <level>` with low/medium/high/xhigh/max.
  CLI reference (code.claude.com/docs/en/cli-reference): `--effort` takes low/medium/high/xhigh/max/ultracode, and "Overrides the modelSettings and effortLevel settings for this session and does not persist".
- **Other routes are worse.** Docs (code.claude.com/docs/en/model-config):
  - Env var `CLAUDE_CODE_EFFORT_LEVEL`: it would also override the effort in our board subagents' definitions. Frontmatter effort overrides "the session level but not the environment variable".
  - Settings `effortLevel` / `modelSettings`: the app can't write the user's settings file, and these keys refuse `max`.
- **Precedence (docs):** explicit choice (env var / `--effort` / `/effort`), then saved settings, then the model's default. Opus 5.5, Sonnet 5.5 and Haiku 5.5 default to medium, Opus 4.7 to xhigh, and others to high. An unsupported level falls back to the highest supported one below it.
- **Observed live: a resumed conversation does NOT keep its effort.** `claude -p --effort low --model haiku --session-id <new>`: the transcript recorded `"effort":"low"`. Resumed with `claude -p --resume <id>` and no flag: the next turn recorded `"effort":"medium"`. Probe files deleted. Caveat: headless (`-p`) mode.
- **Board subagents keep their own effort.** The `--agents` definitions carry `effort` per tier (`src/lib/terminal/session-agents.ts` ~L150), and frontmatter beats the session level.
- **The helper must change.**
  - The bridge builds the `claude …` command (`terminal/bridge/src/resume-cmd.js` `resolveClaudeLaunch`) and reads `effort` only on the Codex branch.
  - There's no env or settings channel from the app.
  - `model` can't carry a second flag (spaces are rejected).
  - So: helper 0.3.24, and a `MINIMUM_RECOMMENDED_HELPER_VERSION` bump (now 0.3.23; latest GitHub release `terminal-helper-v0.3.23`).
- **Old helpers degrade safely.** Their parser keeps `effort=low|medium|high|xhigh` and drops `max`, and their Claude branch never reads it.
- **Launch-link budget holds.** I ran a temporary copy of `src/lib/launch-claude-code.guide-bootstrap.test.ts` with `effort: "medium"` (Claude's longest level) on every Claude launch, then removed the copy. All 66 cases pass.

### Decided
- **User setting (approved):** a "Starting effort" row in Settings → Model Tiers → Terminal sessions, under the Claude "Starting model". It's the Codex effort strip plus a leading "Default" segment. Options: Default, Low, Medium, High, X-High, Max.
- **Default says its fallback (Nick's point 3):** the Default segment gets a second, smaller line: "site: <Level>" when a site default is set, "Claude's own" when not, and nothing while the site default is loading.
  - To fit six segments on a 375px phone, the Default segment is about 1.7× wider, and every segment in this strip uses 2px side padding instead of 4px.
  - Measured in the mock at 375px: Default 70px, others 43px, nothing clipped, no sideways scroll. That's tight, so the builder must re-measure in the real app font (Geist).
  - The Codex strip and the tier grid are unchanged.
- **Site default (new):** a new admin card "Claude terminal starting effort", directly under the existing "Claude terminal starting model" card on Admin → Platform.
  - The 5-level strip (no Default segment); nothing pressed = no site default.
  - An audit row, Clear/Cancel/Save, and toasts, mirroring the model card.
  - No seed: until an admin sets it, behaviour is exactly today's.
- **Storage: a SEPARATE `platform_settings` key `terminal_effort_default`, value `{"effort":"high"}`,** not an extension of `terminal_model_default`. Why:
  1. The model row's validator requires a non-empty `model`. A row holding only an effort would read as malformed: it would log a warning and drop the site model default too.
  2. The model card's Clear DELETEs the whole row, which would silently wipe the effort.
  3. For Claude, model and effort are independent choices (unlike Codex's atomic pair), so the existing reasoning applies: "separate key ⇒ one setting, one save, unambiguous errors, own audit line".
  4. It leaves the working model-default code paths untouched: no regression risk, and no data reshaping of the live row.
- **Resolution (user → site → none),** used identically at mint, at reattach, in the Settings help line and in the launch line:
  - user value is a valid Claude level → it;
  - else site value is a valid Claude level → it;
  - else undefined (send nothing).
  - Invalid stored values count as unset, and are never mixed.
- **Applies to new AND resumed Claude sessions** (Nick: yes). Never Codex.
- **Launch surfaces:** the existing grey line gains "· <Level> effort" for the resolved effort, whether it's the user's or the site's. It's unchanged when nothing resolves. The source isn't named for the effort; the model part already names its own source.
- **One stage, one PR,** including the helper bump.

### Ruled out (and why)
- Env-var route: it overrides board subagents' tier effort, and still needs a bridge change.
- Settings-file route: the app can't write it, and `max` is refused.
- Typing `/effort` as the opening prompt: it fights the bootstrap, and a typed level is SAVED as the user's default.
- Smuggling a flag through `model`: rejected by validators, and an injection hole.
- A picker at launch time: Codex doesn't have one.
- Extending the `terminal_model_default` row with `effort`: reasons 1-4 above.
- A seed value for the site default: it would change behaviour for everyone on deploy. It mirrors the binding "no seed" rule of the model default.
- A per-user "Claude's own even though the site has a default" choice (like the model's "My machine's default"): it would add a 7th button and break the approved look, and Nick didn't ask for it. A user can still pick any explicit level. Easy to add later if wanted.

## Requirements (stage 1 = the whole card)

User-facing change: YES

- **R1** In Settings → Model Tiers → Terminal sessions, a signed-in user can pick a Claude starting effort: Default, Low, Medium, High, X-High or Max. It saves with the dialog's Save and survives a reload.
- **R2** The Default segment states its fallback: "site: <Level>" when a site default exists, "Claude's own" when none. The help line matches the state (mock v2).
- **R3** A super-admin can set, change or clear a site-wide Claude starting effort on Admin → Platform, in a card under "Claude terminal starting model". It shows who changed it last and when. Non-super-admins see the existing access-denied state.
- **R4** Resolution: the user's level → the site level → none. With none, no effort is sent anywhere, and links and commands are byte-identical to today.
- **R5** A resolved effort starts new in-browser Claude sessions with `--effort <level>`.
- **R6** A resolved effort also applies to resumed Claude sessions (`--resume <id>`, `--continue`, and the reattach relaunch).
- **R7** Codex launches never carry the Claude effort; the Codex pair is unchanged.
- **R8** The chooser footer and the per-card "Start fresh anyway" line name the resolved effort, and are unchanged when none resolves.
- **R9** Unknown or tampered values are never sent: whitelists at user save, admin save, site read, mint, link build, link parse and command build.
- **R10** Old helpers (≤0.3.23) still launch normally (the effort is ignored). The minimum-version bump nudges the update.
- **R11** The browser launch-link budget still passes for every realistic Claude launch with an effort (pinned test).
- **R12** An admin change takes effect on the next launch with no deploy. Already-open Settings and launch surfaces in the admin's own tab update immediately via the cache setter.

### Edge cases
- A model without effort support: Claude Code caps or ignores it (docs).
- `/effort` mid-session wins for that session; a later resume re-applies the resolved setting.
- An old Claude Code without `--effort` would exit at once with "unknown option". Nick runs 2.1.299. If it's ever seen, reuse the Remote Control early-exit hint pattern.
- The site default changing between a launch and its resume: the resume uses the value at resume time (read per request), which is correct for a session-only flag.
- A user on Default while the site default loads: the sub-label is hidden and the line is omitted until the hook resolves. There are no flashes of a wrong value.
- Codex rows on reattach never read either Claude value.
- `max` is session-only in Claude Code anyway, so we never change anyone's saved default.
