# Card 2bc396fd - board crash while dragging a card up to another column

User-visible effect of the fix: none except removing the crash (no layout or behaviour change for a normal drag).
No stored data, auth or payments involved.

## Symptom
Dragging a card from the bottom of a long column towards another column showed the app error
screen: "Minified React error #185" (maximum update depth exceeded). Mid-drag, reproducible.

## Reproduction (local, real KanbanBoard component, headless Chromium, fake data)
A temporary page (not committed) rendered the real `KanbanBoard` with Backlog (7 cards), To do
(26 cards, taller than the window), In Progress (2); window 1280x773.
1. Scroll the page to the very bottom (To do is the tallest column, so it sets the page height).
2. Press on the drag handle of the last To do card and move the pointer to x=100, y=124 (over Backlog).
3. Scroll the wheel up while still holding the card.
Result: "Maximum update depth exceeded". Logging handleDragOver showed it hopping
todo -> backlog -> todo -> backlog ... with scrollY alternating 669 / 742 and the pointer not moving.
Found by random-walk fuzzing: 3 of 25 runs crashed before the fix, 0 of the same runs after
(and the 4 hand-picked cases that crashed no longer do).
A bare dnd-kit harness with fixed-height cards did NOT crash: it needs the real page layout.

## Root cause
`handleDragOver` in `src/components/board/kanban-board.tsx` moves the dragged card to whichever
column the collision check reports, with no memory of the hop it just made.
When the card leaves a tall column the page gets shorter, the browser clamps the scroll position,
and every column shifts under the stationary pointer. `multiContainerCollision`
(pointerWithin, then closestCenter fallback) then reports the column the card just left, so it
hops back, the page grows, the scroll shifts again, and the first column is reported again.
Each hop is a state update inside the previous one's effect, so React stops at its nested-update
limit (error 185). Nothing in the code ever damped this; the pointer position was never compared.
Same cause would hit any board where the tallest column loses a card while the page is scrolled to the bottom.
Not related to the edge-scroll hook, the sideways scrollbar, or realtime refresh (ruled out: no
setState in them runs from the drag path; the loop log shows only handleDragOver flips).

## Fix
`src/components/board/drag-column-hop.ts` - `isLayoutEchoHop`: ignore a hop straight back to the
column we just left when the pointer travel (`event.delta`) is identical to the previous hop's.
Real pointer movement or a hop onward to a third column (sideways edge scroll) is still allowed.
`kanban-board.tsx` records the last hop in `lastColumnHopRef` (reset on drag start) and consults the guard.
Drop handling already uses the tracked current column, so the final drop is unaffected.

## Test
`src/components/board/drag-column-hop.test.ts` pins the guard. The crash itself only shows with real
layout (scroll clamping), so it cannot be reproduced in jsdom; the browser repro above is the
before/after proof.

## Decision / limit
Alternative considered: dnd-kit's "recently moved to new container" example guard - it only covers one
frame, and this loop spans several, so a pointer-based check was chosen.
