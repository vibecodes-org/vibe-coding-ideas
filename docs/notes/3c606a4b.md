# Card 3c606a4b: claiming can hand out a leftover step from an abandoned attempt

Working notes. Started 24 Oct 2026 by the Planner (Investigate and plan the fix step).
Code read from origin/master at dea922d. Production data read with read-only queries only.

## Where things are
- The claim: `mcp-server/src/tools/workflows.ts`, `claimNextStep` (pending-step query ~lines 732-739;
  run status update ~895-911, which also accepts a `failed` run and so revives it).
- The card lookup's rule: `mcp-server/src/tools/board-read.ts`, `currentRunKey` (~line 262), private
  to that file; `getTask` uses it (~335). Its `workflow_instruction` pending count (~402) is still card-wide.
- Tests: `mcp-server/src/tools/workflows.test.ts` (`describe("claimNextStep"...)` at ~361,
  `makeClaimContext` mock returns ONE pending step, so it must learn to return a list);
  `mcp-server/src/tools/board-read.test.ts` (~552 "prefers the newer running run..." and ~576
  "falls back to the newest unfinished run..." - the second one changes under the recommended rule).
- How a second attempt gets made: `applyWorkflowTemplate` (MCP ~551, web `src/actions/workflow-templates.ts`
  ~320) only refuses when a run is NOT completed/failed (unique index `idx_unique_active_workflow_run`,
  migration 00081). A failed run's leftover steps are never closed.
- fail_step without reset marks the run failed ("the workflow stops", per its tool description) but
  claim_next_step ignores run status and failed steps.

## Root cause
`claimNextStep` picks `status in (pending, in_progress)` across every step of the card, ordered by
step number only. It never asks which attempt is current, and it never stops at a failed step.
- Two attempts with the same step numbers tie; Postgres does not promise which tied row comes first.
- Once the live attempt finishes, the old attempt's leftovers are the only pending rows, so they are
  handed out for certain, and the claim's run update flips the dead run from failed back to running.
- In a single attempt, a failed step is skipped and the next pending step is handed out.
Latent since board-level workflows (11-13 Mar 2026): runs per card became possible then.

## Evidence (checked live, read-only, 24 Oct)

- Only ONE card on prod has leftovers in a non-current attempt (12b963f0: 2 pending + 1 failed).
- No step in an older attempt has ever been started after a newer attempt existed: the bug has not
  yet handed out a wrong step on prod.
- Skip-past-a-failed-step HAS happened: d7dd76f1 (archived, this board) step 1 failed 11 Oct 10:20:28,
  step 2 started 8s later; run now "running" forever with a failed step. d3b1c1c4 (another board,
  March) similar. bff2816e (this board, not archived; run failed at step 3 of 6): the claim query
  would hand out step 4 today.
- Board card counters (trigger `update_workflow_step_counts`, migration 00129) count every attempt:
  all 54 cards with more than one attempt show inflated totals; 12b963f0 shows 2/8 done, 1 failed.

## Decisions (proposed; Nick to confirm)
1. One shared rule for "current attempt", used by get_task and claim_next_step: the newest attempt
   always wins (newest step created_at per run). Drop the stage-2 fallback to an older unfinished
   attempt. RECOMMENDED. Why: an older attempt can only be unfinished if it was abandoned; the fallback
   is exactly what would hand out 12b963f0's old steps after the live attempt ends.
2. Claim stops at a failed step in the current attempt (returns a "workflow stopped" answer, no token,
   no write) instead of skipping it. RECOMMENDED: matches fail_step's own promise.
3. Steps waiting for approval: leave as today (claim moves past them). Out of scope.
4. No one-off data tidy: with rule 1, leftovers are inert. RECOMMENDED.
5. Stage 2 (same card): board card counters, card dialog and dashboard agent panel show only the
   current attempt. User-facing + a migration that recomputes stored counters; needs a mock.

## Ruled out
- Closing leftovers when a new attempt starts (instead of rule 1): needs a status for them ("skipped"
  would count as done in the counters; a new status means migration + UI), must be added to every apply
  path (MCP, web, auto-rule, retroactive), and still needs a data tidy. More moving parts, same result.
- Sorting by run created_at as a tiebreak only: fixes the tie, not the end-of-attempt handout.
- Reproducing by calling claim_next_step on a live card: forbidden (changes live state). Proven from
  the exact query run read-only plus the code.

## Stage 1 build (Fix step) - decisions
Nick confirmed A-D on 24 Oct (E is stage 2, not started; no UI or stored-data change here).
- New pure module `src/lib/workflow-current-run.ts` (`pickCurrentRunKey`): newest run by latest step
  `created_at`, any status; steps with no run are one group; exact ties go to the larger run id.
  Used by `getTask` (replaces the private `currentRunKey`, fallback dropped) and `claimNextStep`.
- `claimNextStep` now reads ALL the card's steps in one read (still the first and only step read before
  the claim write), keeps the current run, sorts by step_order (nulls last), position, id, and takes the
  first step that is not completed/skipped/awaiting_approval (C unchanged). pending/in_progress: claim as
  before. failed: returns `{ done:false, workflow_stopped:true, failed_step, instruction }`, no token, no
  write, before the suggestion lookup. Nothing left: existing suggestion / done branch.
- `getTask`'s workflow_instruction counts the live run only (was card-wide).
- Tool description for claim_next_step gains one sentence about this.
- Tests: new `workflow-current-run.test.ts`; new describe "claimNextStep - current attempt only" in
  `workflows.test.ts` (abandoned + live at the same step numbers in both row orders, finished live run
  with leftovers -> done, failed step stops, approval still passed over, in-progress re-claim);
  `board-read.test.ts` fallback test now expects the newest run. Before the change the "finished live
  run" and "failed step stops" tests failed; the same-step-number test first passed for the wrong reason: the mock answered the claim write with a fixed row whatever step the code aimed at, so the test could not see which step was chosen. It now checks the id the claim write was aimed at, and fails on the old code.
- Deviation from the plan: no separate test feeding the same rows to both get_task and claim_next_step.
  Both call the one shared function, which is what guarantees agreement, and it has its own tests.
- Not done on purpose: the one remaining card with leftovers (D), runs stuck "running" with a failed step.
