## Root cause (proven)
1. **Fixed 8,000-token output cap** (`maxOutputTokens: 8000`, `src/app/api/ai/generate-tasks/route.ts` ~L185). A long idea needs more than that for its whole task list.
2. **A length cut is treated as a normal finish.** Proven with the ai SDK's own mock model (scratch probe, ai 6.0.86): when the model stops at the cap mid-JSON,
   - `partialObjectStream`'s last value contains the half-written task (e.g. `columnName: "Backl"`);
   - `result.finishReason` resolves to `"length"`;
   - `result.object` rejects with `NoObjectGeneratedError` (the full JSON doesn't parse);
   - `onError` is **not** called.
   The route only looks at `partialObjectStream` and `onError`, never `finishReason` or `object`, so it forwards the half task and logs "completed". The "interrupted" error line never fires.
3. **The dialog trusts the last line it got** (`handleGenerate` in `src/components/board/ai-generate-dialog.tsx` L183-280; final list + column mapping ~L255-265): `lastParsed.tasks` becomes the final list, `autoMapColumns` (`src/lib/import.ts` L318) maps an unknown column name like "Backl" to `"__new__"`, the preview table counts it as a new column, and `insertTasksSequentially` would create it on Apply.

Not a cause: **reading the idea.** Nothing limits or slices the input — the route reads the whole description from the database and `buildPromptContextParts` (`src/lib/ai-prompt-helpers.ts` L26) passes it in full. 19.9k input tokens is a small fraction of what the model accepts.

## When it started
- The silent cut has existed since the route went streaming on **25 Feb 2026** (commit 281da9d; cap 8,000 from day one, length finish never checked). `ai_usage_log`: **31 of 145 `generate_board_tasks` runs hit exactly 8,000** — 29 of 118 on Sonnet 4.6 (Feb-Jul), 0 of 11 on Sonnet 5, 2 of 3 on Sonnet 5.5 (plus my reproduction = 3 of 4).
- Why today: Nick applied the enhanced description at 12:42 today, so idea b7b21b93 grew from 31,644 to 50,367 characters (input 13k → 20k tokens). On 11 Sep (Sonnet 5, shorter idea) the same idea used 4.1-6.1k output.
- Possible extra factor (inference, not proven): since 10 Oct (commit cda1d0b) this call uses the native structured-output mode instead of a forced tool call. A forced tool call can't think; the native mode lets Sonnet 5.5 think first, and thinking shares the cap. Screenshots in my run showed only 2 tasks ~10-15 s in, then ~70 in the next ~35 s — consistent with a short think up front. The provider doesn't report thinking tokens separately, so the share is unmeasured.

## Second limit on the same path
`GENERATE_TIMEOUT_MS = 120_000` (route L20) aborts the stream at 2 minutes → `onError` → error line → the dialog **throws away every task** and goes back to the first screen (code reading + the route's own comments; not observed live — no run has reached 2 minutes). Measured speed: 8,000 tokens in 49-50 s (~160 tokens/s, three runs). So a bigger cap alone would turn a long-but-working run into a total loss at 2 minutes. The timeout has to become a deadline near the 300 s function limit, and hitting it has to keep the finished tasks.

## "Generate the rest" — full spec (decision 2)

### One change to the base plan: the route always sends a final line
So the dialog can tell "finished with nothing new" from "nothing arrived", every run that doesn't end in the error line ends with exactly one **final line**:
`{"tasks": [...], "final": true}` on a clean finish, or `{"tasks": completeTasksOnly(latest), "final": true, "cutShort": "length" | "time"}` on a cut.
- Clean finish: `tasks` = the last partial (all complete). Zero tasks is allowed here (needed for a continuation that finds nothing more).
- Cut with zero complete tasks: on a **first** run, the existing error line (unchanged); on a **continuation**, a final line with `tasks: []` and the cut flag (the dialog keeps the existing list — see "Failures").
- `"connection"` is never sent by the server; the dialog sets it itself when the reader throws after tasks arrived (decision 3).
- Base-plan tests 1, 3, 4 assert this shape (`final: true`).

### Bar and button (dialog, above the table)
Copy Enhance's bar exactly (`src/components/ideas/enhance-dialog-shell.tsx` ~L696-712), so same-kind controls look the same:
```tsx
<div className="flex items-center justify-between gap-3 rounded-md border border-amber-500/30 bg-amber-500/10 px-3 py-2 text-xs text-amber-600 dark:text-amber-400">
  <span>{message}</span>
  <Button variant="outline" size="sm" onClick={handleGenerateRest} disabled={busy}
    className="h-6 shrink-0 border-amber-500/30 text-xs hover:bg-amber-500/10">
    Generate the rest
  </Button>
</div>
```
- Label: **"Generate the rest"** (Nick's words, sentence case like "Continue").
- Shown only when `cutShort` is set and nothing is generating; placed directly above `ImportPreviewTable` inside `ai-generate-dialog.tsx` (NOT inside the shared table, which the import tabs also use).
- Messages (N = total tasks now in the list):
  - length: "The list was cut short — the AI ran out of room after N tasks, so later parts of the idea may be missing. The unfinished last task was left out."
  - time: same with "ran out of time".
  - connection: "The connection dropped before it finished."
- The button appears for all three.

### Request (what the route receives)
New optional body field on `POST /api/ai/generate-tasks`:
`continueAfter: { title: string; columnName?: string; labels?: string[]; dueDate?: string }[]` — the tasks already in the list, in order (the dialog sends the **whole** current list, ticked or not).
- Validation (pure helper `parseContinueAfter` in `src/lib/generate-tasks-stream.ts`):
  - Not an array, or any item without a string `title`: **400** `{"error":"Invalid continueAfter"}`.
  - More than 1,000 items: 400.
  - Trim each title to 200 characters and each column/label to 60; keep at most 10 labels per task.
  - Empty array: treated as absent (a normal first run).
- Other body fields as today (`ideaId`, `prompt`, persona fields). The dialog re-sends the prompt and persona of the run being continued (stored in a ref at Generate time), so editing the configure screen in between can't change them.

### Prompt (continuation only)
`buildContinuationTasksInstruction(continueAfter)` in `src/lib/generate-tasks-stream.ts`, pushed to `contextParts` as the **very last part, after the large-idea nudge** (Enhance learned the instruction must be the last thing the model reads):
```
---
**Tasks already generated for this idea (the list was cut off before it finished):**
- <title> [<column>] (<label>, <label>) due <date>
...

Generate ONLY tasks for parts of the idea that this list does not already cover, continuing in the same order, level of detail, column names and label names, with due dates continuing after the last date above. Do NOT repeat, rephrase, split or merge any task in the list. If the list already covers the whole idea, return an empty task list.
```
- Leave out the bracket/parenthesis/due pieces when a task has none. About 25 tokens per task (72 tasks ≈ 2k extra input tokens).
- Same schema, 32k cap, deadline and cut handling as a first run.
- Log `continuation: true` and `continueAfterCount` in the "stream completed" / "ended in error" logs.
- Usage row: same `actionType: "generate_board_tasks"` (no schema or admin change).

### Dialog behaviour
- New `handleGenerateRest()`, separate from `handleGenerate` (which starts with `setGeneratedTasks([])` — that must NOT happen here):
  - Snapshot `base = generatedTasks` and keep the current selection.
  - Set `cutShort = null` and `generating = true`.
  - Send the request with `continueAfter = base`.
  - While streaming, show `mergeContinuation(base, streamedNew)`.
- **Merge and dedupe** (pure, `src/lib/generate-tasks-stream.ts`): `mergeContinuation(base, incoming)` returns `base` followed by each incoming task whose normalised title isn't already in `base` or earlier in `incoming`.
  - Normalise: lowercase, NFKD, strip everything that isn't a letter, digit or space, collapse whitespace, trim.
  - Exact match on that only — no fuzzy matching.
  - Applied on every streamed update and on the final line. A row may briefly appear and then vanish if it turns out to be a duplicate; that's acceptable.
- **Selection**: rows aren't editable in this preview (only checkboxes), so ticks are the only user state.
  - Remove the `useEffect` that ticks everything when `generating` turns false (~L145) — it would re-tick rows the user unticked.
  - Instead, `handleGenerate` ticks all tasks on success.
  - `handleGenerateRest` keeps the existing ticks and adds the new rows (indices `base.length` to `merged.length - 1`). Existing rows keep their indices because new ones are appended.
- **Column/label mapping**: `setColumnMapping(autoMapColumns(getUniqueColumnNames(merged), columns))` after the final line, over the whole merged list.
- **The bar after a continuation**:
  - Final line has `cutShort`: the bar comes back with the button, N = the merged total.
  - Clean final line: the bar clears.
  - Connection drop mid-continuation: keep the merged list so far minus the unfinished last new task (`completeTasksOnly` on the new part only), and show the connection bar.
- **Zero new tasks** (clean final line and the merge adds nothing):
  - The list is unchanged and the bar clears.
  - `toast.info("Nothing more to add — the list already covers the whole idea.")`
  - It stays on the review screen. The existing "AI did not generate any tasks" error stays for first runs only.
- **Failures**:
  - The continuation fails before any line arrives (non-OK response or the error line): keep `base` and the ticks unchanged, and restore the previous `cutShort` (bar and button stay). `toast.error(message)`. Never go back to the configure screen.
  - A cut with zero new tasks (`final` + `cutShort` + empty `tasks`): same handling, with the toast "Couldn't generate more tasks — please try again."
- **Regenerate** resets everything (list, ticks, `cutShort`, the stored prompt and persona). It's a fresh run with no `continueAfter`. Closing the dialog (`resetState`) clears the same state.
