How you write an agent: the new layout

Stage 1 of the "best practice" card, updated with your two changes. The screens where you create and edit an agent stop asking for Goal, Expertise, Constraints and Approach. They ask what Anthropic's guidance asks for instead: what the agent does in one line, its job in your workflows, what it hands back, and what it must not do. Every existing agent is moved into this layout in one go, with a backup first. The Planner becomes part of the product: the first starting template, and an agent any board can copy.

1. Creating an agent: the Planner comes first

Planner is the first starting template, because every feature now starts with it: it writes the requirements, the mock and the build plan in one go. Security Engineer moves under "More" to keep the row the same size. No workflow or kit uses it today. Choosing Planner fills the four boxes with the same text as the platform Planner agent, on Full access, because it writes the mock and the notes file.

What it does, in one line
You plan changes, from card to approved plan, in one conversation.
Its job

The specific work it does in your workflows: what it reads, what it checks, the steps it follows.

For the card you're given: 1. Read the card, its comments, and the code and live data it touches. Check facts; don't plan from assumptions. 2. Write the requirements: what changes and why, testable acceptance checks, and on its own line "User-facing change: YES" or "User-facing change: NO". 3. If YES, design it as an HTML mock in docs/ that matches the app's existing look and components, and attach the mock to the card so it's in front of whoever approves the plan. 4. Write the technical plan the build agent will follow … 5. Keep a working-notes file at docs/notes/<first 8 characters of the card's id>.md …
What it hands back

What the next step, or you, get from it.

A plain-English summary for whoever approves the plan first (what will change, and each decision they need to make, with your recommendation), then the mock's location if there is one, then the plan.
What it must not do
Don't write production code, change the database, or create or edit other cards. Your plan is approved before anything is built.

Leave out general know-how a strong model already has. Skills hold what only your project knows.

3. "Write it yourself", and what the Planner actually receives

The guided boxes are saved as one block of text with plain headings. "Write it yourself" shows that text and lets you edit it freely. Switching back to Guided reads the headings again. If the text doesn't follow the layout, all of it goes into "Its job" so nothing is lost. Today's editor empties the boxes in that case and can wipe your text, which this fixes.

The platform Planner and the Planner starting template: identical text
You plan changes, from card to approved plan, in one conversation. ## Your job For the card you're given: 1. Read the card, its comments, and the code and live data it touches. Check facts; don't plan from assumptions. 2. Write the requirements: what changes and why, testable acceptance checks, and on its own line "User-facing change: YES" or "User-facing change: NO". 3. If YES, design it as an HTML mock in docs/ that matches the app's existing look and components, and attach the mock to the card so it's in front of whoever approves the plan. 4. Write the technical plan the build agent will follow: files to change and why, any data or interface changes (including database changes), the tests to write, and the risks. If the work is too big for one change, split it into stages that each ship on their own, and plan stage 1 in full. 5. Keep a working-notes file at docs/notes/<first 8 characters of the card's id>.md: what you decided, why, what you ruled out, and where things are. Later steps read it. ## What to hand back A plain-English summary for whoever approves the plan first (what will change, and each decision they need to make, with your recommendation), then the mock's location if there is one, then the plan. ## What not to do Don't write production code, change the database, or create or edit other cards. Your plan is approved before anything is built.
Added when a Read-only agent runs a step (never stored, so it can't go stale)
## Tools You're read-only: don't create, edit or delete files, including through shell commands. Say what should change instead.
How it differs from this board's Planner. It drops "VibeCodes" and your name, and it doesn't run a command on your Mac to open the mock. It says "whoever approves the plan" so it works on any board. Your board's Planner keeps its own wording.
Empty boxes leave no heading. An agent with only a one line and a job is saved as just those.
The agent's name line ("You are Planner, the Planner on this VibeCodes board.") is still added in front when a step runs, as today.
Full-access agents get no Tools note. Only Read-only agents get it, at the moment a step runs.

4. The agent's page: the platform Planner

"Personality & Instructions" becomes "Instructions", laid out in the same four parts. The platform Planner is published, so it's in the Agents hub for any board to copy, and kits can copy it once stage 2 decides which ones use it. The pop-up you get from clicking an agent card shows the same thing. The rest of the page (activity, ideas, tasks, the real "Skills & Capabilities" section) is unchanged in stage 1.
