UX Design · Terminal mode (task d3de150c)

Terminal auto-accept mode — an opt-in that stays visible while it's on

Nick asked why the in-app terminal starts in "manual mode" (Claude Code asks before every edit/command) instead of auto. Requirements answered: manual stays the default — it's the safe posture for a feature running real commands on Nick's own machine — and auto-accept becomes an opt-in toggle that appends --permission-mode acceptEdits to the launch, mirroring the shipped "Terminal starting model" pattern (task c4ca2d95) exactly. This document designs the toggle, its launch-time visibility, and — the part the model feature never needed — a persistent in-session indicator, because a forgotten safety toggle is a different class of surprise than a forgotten model.

0 · Decisions at a glance

QuestionDecisionWhy (short)
Where does the user set it? A switch "Start in auto-accept mode" in the existing Profile → Models dialog, inside the Terminal sessions group, directly under "Starting model". Default OFF. One home for "how do my fresh terminal sessions launch" (recognition over recall). The model setting trained users where this lives; a second surface for one switch would fail Jakob's Law and Hick's Law both.
What kind of control? A two-state Switch — no dropdown, no free text, ever. The only value that can exist is acceptEdits. AC-6: bypassPermissions must be unofferable. A boolean control makes the forbidden value structurally impossible, which is stronger than validating it away.
Platform-wide admin default? No. Deliberately none. Unlike the model, this setting gets no Platform-tab card. An admin switching every user's machine into auto-accepting real file edits is an unacceptable blast radius. The model precedent is mirrored for mechanics, not for governance.
Visible at launch? Yes — the existing model line in the chooser footer and per-task dialog gains an amber auto-accept chip when ON. Nothing added when OFF. Same passive-visibility posture that fixed the "why am I on Opus 4.8?" surprise; zero-friction paths stay dialog-free.
Visible during the session? Yes — a persistent amber "⚡ Auto-accept" badge in the session header, same slot and anatomy as the shipped Read-only badge. Shown for the session's whole life, in the dock, split view, and pop-out alike. The forget-scenario is the core risk: Nick toggles it on, forgets, and a week later a session silently edits files without asking. A settings toggle he saw once is not an answer; a badge on the running session is.
Applies on resume? No — fresh launches only, exactly like the model flag (bridge branch 4 only). §4. Forgetting to apply it costs two keystrokes (Shift+Tab); applying it unexpectedly to an old session escalates silently in the unsafe direction. Asymmetric costs → pick the recoverable miss.
Old bridge ignores the param? Silent graceful degradation — no banner, no error. The header badge shows "requested"; Claude Code's own status line is the live truth. §5. The failure direction is safe (Claude asks when it needn't). The existing helper-update nag is the remedy path; inventing a new warning surface for a fail-safe miss isn't worth it.
Task-pickup behaviour (fix #188)? Untouched, by construction: this feature only changes the claude argv on fresh mints. AC-7. Ask-first task pickup is app-side flow, not CLI permission mode; no shared code paths change.

1 · The toggle — Profile → Models → Terminal sessions

The Terminal sessions group (added by the model feature in model-tier-settings.tsx) gains a switch row under the Starting model field. Everything else — staged-until-Save, Cancel/Esc discards, "Save enables when…" helper, toast on save — is inherited unchanged.

1.2 · Toggled ON — consequence stated before Save warning

Flipping the switch swaps the help line for an amber consequence statement (icon + text, never colour alone) that also teaches the indicator: the user learns at opt-in time what the badge in §3 means, so the badge never needs explaining later. No confirmation dialog — the switch is staged behind the dialog's existing Save, which is already a deliberate second step, and the setting affects only this user's own launches (matching the model feature's "personal blast radius = no extra gate" reasoning). ON-state switch track is amber, not the usual primary colour — the same hue the chip (§2) and badge (§3) use, one colour vocabulary for "auto-accept is on" everywhere.

2 · Launch surfaces — one chip on the existing model line

The model feature already put a passive one-liner wherever "start fresh" lives (chooser footer, per-task dedupe dialog) and deliberately left instant direct launches dialog-free. This feature adds one amber chip to that same line when the toggle is ON — no new line, no new dialog, and nothing at all when OFF (criterion 3's byte-identical spirit applies to the UI too: OFF looks exactly like today).

Same terse variant as the model line here — no link, three actions already compete. The line scopes itself to "Start fresh": reconnecting or resuming never gains the flag (§4), so the chip correctly describes only the fresh path. Dialog stays dismissable in every mode — close, Escape, outside-click — per the project's "never trap the user in a dialog" rule.

2.3 · Direct instant launch — nothing new, on purpose

A direct task launch with no existing session mints instantly, no dialog — the model feature fought to keep that path zero-friction and this feature doesn't reopen it. The user's confirmation arrives seconds later twice over: Claude Code's own status line (⏵⏵ accept edits on) and the header badge (§3), which is present from the session's first frame.

3 · The persistent in-session indicator — the part the model never needed

The forget scenario is the design driver. Nick enables the toggle for a heavy refactor day, forgets, and two weeks later opens a terminal on production-adjacent work. With only a buried settings switch, the first sign auto-accept is on is an edit happening without a prompt — discovering a safety setting by watching it fire is the failure this section exists to prevent. The mode must be legible at a glance on the running session itself, for the session's entire life, everywhere the session renders.

3.1 · Session header badge

The session pane header (terminal-session-view.tsx) already has exactly this pattern shipped: the violet Read-only badge — a bordered pill sitting after the status pill. Auto-accept reuses that anatomy one-for-one, in amber, placed immediately after the status pill (before Read-only when both show):

● Connected ⚡ Auto-accept VibeCodes · session 3f9a02c1 ⧉ Pop out 🔓 Read-only ✕ End session
~/projects/vibe-coding-ideas
✻ Welcome to Claude Code
⏵⏵ accept edits on (shift+tab to cycle)
▌

The badge is always-visible text with an icon — never hover-only, never colour-only (amber pill + ⚡ glyph + the word "Auto-accept"). It renders whenever the session was launched with the flag, for the whole life of the tab — connected, disconnected, reconnecting — because the underlying conversation keeps the mode across reconnects. Claude Code's own status line (bottom of the stream) remains the authoritative live truth; the two agree in the normal case and the terminal wins when they don't (§3.3).

3.2 · Where the badge follows the session

  • Dock panel & split view — the badge lives in the pane header, so both split panes carry their own truthful badge independently (one session can be auto-accept while its neighbour isn't).
  • Pop-out window — the popped window renders the same terminal-session-view header, so the badge travels with it for free. The dock-side popped-out chip does not gain a glyph: that chip already reports misleading status mid-preemption (a known hard-won rule) and stays minimal.
  • Tab strip — no per-tab glyph. Tabs are ~“label + status glyph” at 12px; a second glyph per tab would collide with the existing status→glyph vocabulary and the armed close/rename states (fix #202's reflow lesson). The pane header is one glance away and is the designed home. If field use later shows Nick switching among many tabs and losing track, a tab-strip dot is the v2 slot — deliberately deferred, not forgotten.
  • Title attribute (supplementary, never the only channel): "Launched in auto-accept mode — file edits proceed without confirmation. Shift+Tab in the terminal changes the live mode."

3.3 · Honesty limits of the badge

The bridge and relay never parse the stream (hard architectural rule), so the app cannot observe the live permission mode — the user can cycle it any time with Shift+Tab inside Claude Code. The badge therefore asserts exactly what the app knows: "this session was launched in auto-accept mode". That is the right claim for the forget-scenario (the danger is the launch state persisting unnoticed), and the terminal's own status line covers live changes. The badge never toggles off in response to stream content — there is no stream parsing, and a badge that silently vanished would imply a live-tracking fidelity the system honestly doesn't have.

4 · Resume decision — fresh launches only (AC-8)

Requirements left this call to design: permission mode isn't conversation state (unlike the model, which --resume can't change), so the flag could technically apply on resume. Decision: it doesn't. The flag rides only bridge branch 4 — a genuinely fresh session — exactly like the model flag.

If we're wrong this way…Cost
Toggle ON, user resumes, session asks before edits anywayTwo keystrokes (Shift+Tab) fixes it, in the exact spot the user is already looking. Fail-safe, self-evident, instantly recoverable.
(the rejected alternative) Toggle ON weeks ago, user resumes an old conversation to inspect it, session silently auto-editsEscalation in the unsafe direction, on the path (revisiting old work) where the user's mental model is most stale. Not recoverable after the fact.

Secondary reasons, each independently sufficient:

  • One pattern, one audit. The model flag already established "launch-time flags apply to branch 4 only" in resolveClaudeLaunch; mirroring it keeps criterion 3's byte-identical-when-off guarantee trivially checkable and reuses the existing tests' shape.
  • The badge stays honest cheaply. "Launched with the flag" is knowable from the mint path alone. Applying the flag on resume would require threading launch-mode tracking through resume/continue paths too — more surface for a claim the terminal's status line already makes better.
  • The copy already says it. The Profile help line (§1.1) and the dedupe dialog's "Start fresh starts on…" scoping (§2.2) both state the fresh-only rule at the moments it's relevant — the decision is communicated, not just made.

5 · Version skew — silent graceful degradation, and why that's right here

An older helper/bridge that predates the param ignores it and launches normally (criterion 5 — the same guarantee the model param shipped with). Should the UI warn that the setting may not have taken effect? No — silent degradation, deliberately:

  • The miss fails safe. The only consequence is Claude asking before edits when the user hoped it wouldn't — the default behaviour, the safe direction. Warning banners are for failures that hurt; this one merely under-delivers a convenience.
  • The mismatch is its own signal. The header badge says "Auto-accept" while the terminal visibly prompts and the status line lacks accept edits on — a user who cares notices within one edit, and the badge's title text plus the guide sentence (below) name the fix.
  • The remedy already exists. Outdated helpers get the shipped update nag (helper-version.ts / helper-update-flow.ts); updating is the fix for this and every other skew. Building a bespoke "your helper ignored a param" surface would duplicate that flow for one fail-safe case — and would require the app to know the bridge ignored it, which the no-stream-parsing rule forbids anyway.
  • One guide sentence on guide/launching-claude-code's troubleshooting list closes the loop: "Turned on auto-accept but the terminal still asks before every edit — your helper app is out of date; install the update it's offering, then start a fresh session. (Shift+Tab in the terminal switches the mode live meanwhile.)"
Note the asymmetry with the model feature's failure story: a bad model value fails loud (CLI error in the stream), so that design invested in pre-placed guidance. A skew-dropped permission flag fails quiet and safe, so this design invests nothing beyond one guide sentence. Effort proportional to harm.

7 · Accessibility notes (WCAG 2.1 AA)

  • The switch is a real labelled control — Radix Switch with role="switch", aria-checked, and a visible <Label htmlFor> ("Start in auto-accept mode"); the help/consequence line is wired via aria-describedby so the recommendation and the ON-state warning are announced, not just painted.
  • State is never colour-only. The switch thumb position, the ⚡ glyph, and the words "auto-accept" each independently carry the state — in the dialog, the chip, and the badge. The amber ON track pairs with the amber help text (icon + words), not instead of it.
  • Badge and chip are plain visible text — no tooltip-gated information (the title attribute is supplementary detail only). No hover-dependence anywhere; everything reads on touch.
  • Contrast: amber #fbbf24 on the header/panel darks (#141417/#18181b) is ≈9.6:1 — comfortably past 4.5:1 for the badge, chip, and warning text. The chip border (rgba(251,191,36,.35)) is decorative; the text carries the meaning.
  • Keyboard: the switch sits in the existing Radix Dialog's tab order and toggles with Space/Enter; "Change" in the chooser footer remains a real link in the tab order; the badge is a static status element (not focusable — it's information, not an action). Launch dialogs stay dismissable via close button, Escape and outside-click in every state.
  • Screen-reader parity for the session state: the badge renders as text inside the header, so it's read in the header's natural order ("Connected, Auto-accept, VibeCodes…") — the mode is announced wherever the status is.
  • Target size: the Switch control renders at the shared shadcn size with the full label row as its click target (label click toggles — Fitts's Law on a small control); ≥8px from adjacent fields.
  • 375px screens: the switch row's label wraps above the control; the chooser footer line already wraps above the button (model-feature behaviour) and the extra chip wraps with it; the header badge participates in the header's existing flex-wrap.

Handoff notes for Implementation

  • Storage: a boolean beside users.terminal_model (e.g. terminal_auto_accept, default false) — same fetch/staging path through model-tier-settings.tsx and the profile server action. No platform_settings key — there is deliberately no platform default (§0).
  • Deep link: one non-secret param (e.g. permissionMode=acceptEdits) inserted before prompt, mirrored in terminal/shared/deep-link.mjs with the drift test extended; redactDeepLinkToken leaves it untouched (not secret, not user text). Parser accepts only the literal acceptEdits; anything else drops the param.
  • Bridge: resolveClaudeLaunch branch 4 only — claude --session-id <id>[ --model m][ --permission-mode acceptEdits]; branches 1–3 never read it (§4). Unit tests mirror the model flag's suite shape.
  • Badge: mint response / session-registry entry records the launch's permission mode so terminal-session-view.tsx can render the pill (amber, Zap icon, after the status pill, before Read-only) — same conditional pattern as the Read-only pill. Pop-out inherits for free; add nothing to tabs or the popped-out chip (§3.2).
  • Launch lines: extend terminalLaunchModelLine / terminalDialogModelLine (or sibling helpers) in model-resolution.ts-adjacent pure code — unit-test the copy variants including "machine default + auto-accept on".
  • Copy inventory: switch label "Start in auto-accept mode"; help OFF (§1.1); consequence ON (§1.2); chip "⚡ auto-accept on"; badge "⚡ Auto-accept" + title text (§3.2); guide troubleshooting sentence (§5).
  • Do not touch: task-pickup flow (#188), resume/continue argv, the dedupe dialog's dismissability, tab-strip layout (#202 regression risk).
